# 03. 개선 제안

> 이 문서는 **방향 제시**만 한다. 실제 코드 수정은 포함되지 않는다.
> 이슈 번호는 [02-이슈목록.md](02-이슈목록.md)를 따른다.

## 1단계 — 즉시 수정 (국소 변경으로 해결)

변경 범위가 파일 1~2개로 닫히고, 다른 시스템에 파급이 없는 항목들이다. 먼저 처리하는 것을 권장한다.

### 1-1. `EnemyDetector` 카운트 정합성 재설계 (C-2, C-3, M-9)

**근거**: 이 파일 하나가 자동공격 발사 여부와 공격 애니메이션 전환을 동시에 결정한다. 현재 `Count`는 enter, exit, 사망 콜백 세 경로에서 각각 증감하는데 서로를 모른다. 증감 방식으로는 정합성을 보장하기 어렵다.

**방향**: `int Count` 대신 `HashSet<Collider>` 또는 `HashSet<GameObject>`로 **집합 관리**로 전환한다.
- 중복 추가/제거가 자연스럽게 무시되므로 C-3의 이중 감소가 원천 차단된다.
- Boss/Enemy를 같은 경로로 처리하면 C-2도 함께 해결된다(태그 분기 자체를 없앨 수 있다).
- 집합 크기가 1→0으로 바뀌는 지점을 **한 곳**에서 판정해 `OnEnemyEnter(false)`를 발행하면, 사망 경로와 exit 경로의 발행 누락(C-3 증상 B)이 사라진다.
- 파괴/풀 반환된 오브젝트가 집합에 남는 경우를 대비해, 조회 시 `null`(fake null 포함) 항목을 걸러내는 방어를 함께 둔다.

**영향 범위**: `EnemyDetector.cs` 단일 파일. 외부 계약(`HasEnemy()`, `OnEnemyEnter`)은 그대로 유지되므로 `AutoAttack`, `PlayerMove`는 수정 불필요.

### 1-2. 사망 가드 추가 (C-1)

**근거**: 사망은 되돌릴 수 없는 상태 전이인데 진입 가드가 없다.

**방향**: `PlayerStats`에 `bool isDead` 필드를 두고 `TakeDamage` 진입부에서 조기 반환, `Die()` 진입 시 `true`로 설정한다. `PlayerMove`가 이미 동일한 `isDead` 패턴을 쓰고 있으므로(`PlayerMove.cs:15`) 일관성도 맞는다.

**영향 범위**: `PlayerStats.cs` 단일 파일.

### 1-3. `CameraShakeManager` 안전화 (H-2)

**근거**: 파괴된 Unity 객체에 대한 `?.` 우회는 조용히 잠복하다가 스테이지 전환 후에야 터지는 유형이라 디버깅 비용이 크다.

**방향**: 두 가지를 함께 처리한다.
1. `Awake`에 중복 인스턴스 가드를 추가한다. 카메라가 씬마다 새로 생성되는 구조라면 `DontDestroyOnLoad` 대신 **씬 로드 시 재등록** 방식이 더 적합할 수 있다(어느 쪽이든 정책을 하나로 정할 것).
2. 호출부의 `Instance?.Shake(...)`를 **Unity의 null 비교를 거치는 형태**(`if (Instance != null)`)로 바꾼다. `?.`는 Unity 객체에 쓰지 않는 것을 프로젝트 규칙으로 정해두면 유사 버그를 예방할 수 있다.
3. `impulseSource` null 검증도 함께 추가한다.

**영향 범위**: `CameraShakeManager.cs`, 호출부 `PlayerStats.cs:72`. 프로젝트 전역에서 `Instance?.` 패턴을 한 번 검색해보는 것을 권장한다.

### 1-4. 파티클/대기시간 정리 (M-2, M-3)

- `Destroy(particle, ...)`를 `ps != null` 블록 **밖으로** 옮겨 항상 정리되게 한다.
- `DeathSequence`의 `WaitForSeconds(3)`를 `[SerializeField]` 필드로 빼거나, `Die()`에서 계산한 `delay`를 실제로 사용한다.
- `EndingDieAnim()`이 애니메이션 이벤트 전용이라는 사실을 **주석으로 명시**한다. 안전장치로 `Die()` 시점에 타임아웃 코루틴을 함께 걸어두면, 이벤트 누락 시에도 게임오버 UI가 뜨도록 보장할 수 있다.

## 2단계 — 구조 정리

파급 범위가 있어 1단계 이후 별도로 진행하는 것이 좋다.

### 2-1. 플레이어 스폰 일원화 (H-4)

**근거**: 현재 두 시스템이 동시에 살아 있으면 플레이어 중복, 한쪽만 살아 있으면 HUD·카메라 참조 실패다. 어느 조합도 안전하지 않으며, 새 씬을 추가할 때마다 지뢰가 된다.

**방향**: `GameAppManager`를 단일 소유자로 삼는 것을 권장한다.
- 근거: `sceneLoaded` 훅으로 자동 동작하고, `OnPlayerSpawned` / `OnCameraReady`를 발행하며, Intro/Ending 씬 처리 로직까지 이미 갖추고 있다. `RunManager`가 가진 기능은 `SpawnPlayer` / `DestroyPlayer` / 씬 로드 버튼 정도로 `GameAppManager`의 부분집합에 가깝다.
- `PlayerSpawnPoint`는 "플레이어를 생성하는 주체"에서 **"스폰 위치를 알려주는 마커"**로 역할을 축소한다. `GameAppManager.SetupPlayer`가 씬에서 `PlayerSpawnPoint`를 찾아 그 위치를 쓰도록 하면, 현재 하드코딩된 `new Vector3(0,1,0)`(`GameAppManager.cs:13`)도 함께 해소된다.
- `RunManager`는 씬 로드 버튼 기능만 남기거나 제거한다. 단, 프리팹/씬에서 참조 중일 수 있으므로 삭제 전 확인이 필요하다.

**영향 범위**: `GameAppManager.cs`, `RunManager.cs`, `PlayerSpawnPoint.cs` + 이들이 배치된 모든 씬. **씬 검증이 필수**이므로 1단계와 분리해서 진행할 것.

### 2-2. 상태이상 코루틴 호스트 명시 (H-1)

**근거**: `GetComponent<MonoBehaviour>()`는 결과가 컴포넌트 순서에 의존해 재현성이 없다. 이런 코드는 "가끔 슬로우가 안 풀린다"는 형태로만 드러나 원인 추적이 매우 어렵다.

**방향**:
- `StatusEffect.Apply`의 시그니처를 `Apply(GameObject target)`에서 **`Apply(MonoBehaviour host)`** 또는 `Apply(PlayerStatus receiver)`로 바꿔, 코루틴 호스트를 타입 수준에서 고정한다.
- `PlayerStatus`가 호스트가 되면 `IStatusReceiver` 구현체가 곧 코루틴 소유자가 되어 책임이 명확해진다. 현재 `PlayerStatus`는 3줄짜리 위임만 하고 있어 실질 역할이 없는데, 이 변경으로 존재 이유가 생긴다.
- 더 나아가 `PlayerStatus`가 **활성 상태이상 목록을 보유**하면 이런 것들이 가능해진다: 중복 적용 정책(갱신/중첩/무시) 결정, 사망 시 일괄 해제(M-6 동시 해결), 상태이상 아이콘 UI 연동.

**영향 범위**: `StatusEffect.cs`, `SlowEffect.cs`, `StunEffect.cs`, `StunZone.cs`, `BossSlowSkill.cs`, `PlayerStatus.cs`.

### 2-3. UI 구독 생명주기 정리 (H-3)

**방향**: `SetPlayer`가 새 `stats`를 받을 때, **기존 구독을 먼저 해제**한 뒤 새로 구독하는 형태로 바꾼다. 해제 로직이 `OnDisable`과 `SetPlayer` 두 곳에 필요하므로 `Unsubscribe()` 같은 private 메서드로 묶어 재사용하는 것이 좋다.

이 패턴(`OnPlayerSpawned`로 참조를 다시 잇는 구독자)은 `PlayerStatsUI` 외에 `CameraController`, `EnemyManager`, `BossBrain`, `UpgradeManager`에도 있다. `PlayerStatsUI`만 인스턴스 이벤트(`stats.OnHpChanged`)를 추가 구독하므로 현재 문제가 되는 건 여기뿐이지만, **동일 패턴을 쓰는 곳에서 인스턴스 이벤트를 구독할 때는 항상 해제를 짝지어야 한다**는 규칙으로 정리해두면 좋다.

### 2-4. 방어 코드 및 정리 (M-4, M-5, M-9, M-10, L-1~L-9)

- `PlayerMove.OnDestroy`에서 `playerInput.Dispose()` 호출 (M-4)
- `Update`의 `cam` / `Mouse.current` 가드 (M-5)
- `AutoAttack`, `Gun`의 인스펙터 참조를 `Awake`에서 한 번 검증하고 누락 시 명확한 에러 로그 + `enabled = false` (M-10)
- 죽은 코드 삭제: `WeaponController`, `WeaponBase` (L-1), `PlayerStats.level` (L-4), `ResetState` — 단 플레이어 재사용 정책이 확정된 뒤에 판단 (L-5)
- `MarkerFollow`를 `Boss/` 폴더로 이동 (L-3)
- 디버그 로그 제거 (L-9), 오타 수정 (L-8), 불필요 using 제거 (L-7)
- `PlayerMove.AddSpeed`가 `CurrentSpeed`를 발행하도록 수정 (M-1)
- `GameEvents.Player` 제거 — `BossBrain`이 `OnPlayerSpawned` 구독만으로 충분한지 확인 후 진행 (L-6). 현재 `BossBrain`은 이미 `OnPlayerSpawned`를 구독하고 있고 `GameEvents.Player`는 "구독 시점에 이미 스폰된 경우"를 위한 폴백이다. `GameAppManager`가 **늦게 구독한 대상에게도 현재 플레이어를 전달**하는 방식(예: 스폰 상태를 유지하는 프로퍼티 + 구독 시 즉시 통지)으로 대체하면 정적 필드를 없앨 수 있다.

## 3단계 — 확장성

당장 버그는 아니지만, 무기·스탯을 늘릴 계획이 있다면 그 전에 처리하는 편이 비용이 적다.

### 3-1. 무기 인터페이스 실체화 (L-1, L-2)

**근거**: `AutoAttack`이 `Gun` 구체 타입을 직접 들고 있어(`AutoAttack.cs:6`) 두 번째 무기를 추가하는 순간 `AutoAttack`을 수정해야 한다. `IWeapon`, `WeaponBase`, `WeaponController`라는 이름이 이미 있다는 건 이 구조를 의도했다는 뜻인데, 내용이 비어 있어 오히려 혼란만 준다.

**방향**:
- `IWeapon`을 진짜 `interface`로 만든다 — 최소한 `Shoot()`, 스탯 조회/증감 정도.
- `Gun`이 `IWeapon`을 구현하고, `AutoAttack`은 `IWeapon` 참조를 갖는다. (인스펙터 할당이 필요하면 `WeaponBase : MonoBehaviour, IWeapon` 추상 클래스를 두고 `Gun : WeaponBase` 형태가 실용적이다.)
- `DamageUpgrade` / `GunSpeedUp`도 `GetComponentInChildren<Gun>()` 대신 `IWeapon`으로 접근하면 무기 교체에 영향받지 않는다.
- `WeaponController`는 무기 교체/장착을 담당하게 하거나, 계획이 없다면 삭제한다.

### 3-2. 스탯 데이터의 ScriptableObject화

**근거**: 밸런싱 값(`maxHp`, `baseSpeed`, `attackRate`, `bulletDamage`, `bulletSpeed`, 크리티컬 확률/배율)이 프리팹의 여러 컴포넌트에 흩어져 있어, 수치를 조정하려면 프리팹을 열고 컴포넌트를 오가야 한다. 값 이력 추적도 어렵다.

**방향**: 프로젝트에 이미 `EnemyData`, `StageData`, `UpgradeData`라는 SO 패턴이 자리잡고 있으므로 동일하게 `PlayerData` SO를 만들어 초기값을 모은다. 런타임 값(현재 HP, 누적 업그레이드)은 컴포넌트에 두고, SO는 **초기값 소스**로만 쓰는 것이 안전하다(SO는 에디터에서 값이 영구 변경되므로 런타임 상태를 담으면 안 된다).

### 3-3. 크리티컬을 업그레이드 대상으로 승격 (M-8)

크리티컬 확률/배율을 `Gun`(또는 3-2의 `PlayerData`)이 소유하고 `Bullet.Init`에 전달하도록 바꾸면, `DamageUpgrade`와 동일한 형태로 `CritChanceUpgrade`, `CritDamageUpgrade`를 추가할 수 있다. 현재 업그레이드 풀이 5종(공격력/탄속/이동속도/최대HP/회복)뿐이라 선택지 확보 측면에서도 효과가 있다.

### 3-4. 피격 관련 게임플레이 보강

- **무적 시간(i-frame)**: `PlayerStats.TakeDamage`에 짧은 쿨다운을 두면 다단 히트 순삭이 방지된다. `Bullet`이 `DamageInfo`를 이미 쓰고 있으므로 무시된 피격을 구분해 처리하기도 쉽다.
- **총알의 지형 충돌** (M-7): `Bullet`이 벽/바닥 레이어와 충돌 시 피격 이펙트 없이 풀로 반환되도록 하면 엄폐 개념이 생기고, 벽 너머 적을 맞히는 문제도 해소된다.
