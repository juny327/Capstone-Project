# 07. 무기 종류 확장 설계 (기관단총 · 스나이퍼 · 검 · 드론)

> **목적**: 소총 한 자루뿐인 현재 무기 구성을 **기관단총 / 스나이퍼 라이플 / 검 / 드론**으로 확장한다.
> **관계**: [05-무기시스템설계.md](05-무기시스템설계.md)가 "무기 여러 개를 담을 그릇"을 설계한다면, 이 문서는 **"그 그릇에 담을 실제 무기들"** 을 설계한다.
> 이슈 번호는 [02-이슈목록.md](02-이슈목록.md)를 따른다.

## ⚠ 선행 조건 — 05번이 아직 구현되지 않았다

현재 코드를 확인한 결과다.

| 파일 | 상태 |
|---|---|
| `Player/IWeapon.cs` | **빈 Unity 템플릿** (16줄, `Start`/`Update`만) |
| `Player/WeaponBase.cs` | **빈 Unity 템플릿** |
| `Player/WeaponController.cs` | **빈 Unity 템플릿** |
| `Player/EnemyDetector.cs` | `int Count`만 노출 — `ITargetProvider` 미적용 |
| `Player/Bullet.cs` | `Init(float, float)`, 크리티컬 하드코딩, 관통 없음 |

즉 **이 문서의 모든 내용은 05번의 기반 타입이 먼저 있어야 성립한다.** 순서는 8장에 정리했다.

## 1. 4종을 분류하면 유형은 3가지다

| 무기 | 유형 | 새 코드가 필요한가 |
|---|---|---|
| 소총 (현재) | 투사체 | — |
| **기관단총** | 투사체 | **불필요** — `WeaponData` 에셋만 |
| **스나이퍼 라이플** | 투사체 | **거의 불필요** — 관통만 `Bullet`에 추가 |
| **검** | 근접 | 필요 (`MeleeWeapon`) + **애니메이션·부착 구조 작업** |
| **드론** | 서브유닛 | 필요 (`DroneWeapon` + `DroneUnit`) |

**가장 중요한 판단**: 기관단총과 스나이퍼는 **소총과 같은 클래스**다. 발사 간격·데미지·탄속·관통 수치만 다른 데이터일 뿐이다. 05번의 `WeaponData` SO를 만들어 두면 **코드 한 줄 없이** 두 무기가 생긴다.

반대로 **검이 가장 비싸다.** 코드보다 애니메이션과 무기 부착 구조가 문제다 (3-5 참조).

## 2. 투사체 3종 — 데이터만으로 완성

### 2-1. 수치 설계

기준은 현재 소총 값이다 (`Gun.cs:11-12`의 `bulletDamage = 10`, `bulletSpeed = 20`, `AutoAttack.cs:11`의 `attackRate = 0.5`, `Bullet.cs:9-10`의 크리티컬 2배 / 5%).

| 필드 | 소총 (기준) | 기관단총 | 스나이퍼 |
|---|---|---|---|
| `damage` | 10 | **4** | **36** |
| `fireInterval` | 0.5 | **0.12** | **1.6** |
| `projectileSpeed` | 20 | 25 | **60** |
| `projectileCount` | 1 | 1 | 1 |
| `spreadAngle` | 0 | **5°** | 0 |
| `critChance` | 0.05 | 0.03 | **0.25** |
| `critMultiplier` | 2.0 | 2.0 | **2.5** |
| `pierceCount` | 0 | 0 | **3** |
| `projectileLifeTime` | 3 | 2 | **5** |

### 2-2. 역할 분화 검증 (기대 DPS)

기대 데미지 배율 = `1 + critChance × (critMultiplier - 1)`

| 무기 | 단일 대상 DPS | 밀집 대상 DPS | 역할 |
|---|---|---|---|
| 소총 | **21.0** | 21.0 | 균형 기준선. 시작 무기 |
| 기관단총 | **34.3** | 34.3 | **단일 DPS 최고.** 스프레드 5°로 원거리 명중률이 낮다 |
| 스나이퍼 | **30.9** | **123.8** (4체 관통) | 단일은 중간, **밀집 적에게 압도적** |

계산 근거:

```
소총     : 10 × 1.05  / 0.5  = 21.0
기관단총 : 4  × 1.03  / 0.12 = 34.3
스나이퍼 : 36 × 1.375 / 1.6  = 30.9   (관통 3 → 최대 4체 → 30.9 × 4 = 123.8)
```

**세 무기가 서로 우열이 아니라 상황으로 갈린다**는 점이 중요하다. 기관단총이 단일 DPS는 가장 높지만 스프레드 때문에 멀리 있는 적을 놓치고, 스나이퍼는 한 발을 빗나가면 1.6초를 버린다. 소총은 둘 다 아니지만 안정적이다.

> **스프레드는 자동공격 게임에서 실제로 페널티가 된다.** 이 게임은 `EnemyDetector` 범위 안의 적에게 자동 발사하므로, 플레이어가 조준으로 스프레드를 보정할 수 없다. 기관단총의 5°는 근거리에서는 무해하고 원거리에서는 확실히 빗나가는 수치다.

### 2-3. 스나이퍼 관통 — `Bullet`에 추가할 것

05번 6-2에서 설계한 `ProjectileSpawnInfo.PierceCount`를 실제로 쓰는 첫 무기다.

```csharp
public class Bullet : MonoBehaviour, IPoolable
{
    int pierceRemaining;
    readonly HashSet<Transform> alreadyHit = new();   // 중복 히트 방지

    void OnTriggerEnter(Collider other)
    {
        if (!other.CompareTag("Enemy") && !other.CompareTag("Boss")) return;

        // 같은 적의 자식 콜라이더에 여러 번 맞는 것을 막는다
        Transform root = other.transform.root;
        if (!alreadyHit.Add(root)) return;

        SpawnHitEffect(other);
        other.GetComponent<IDamageable>()?.TakeDamage(BuildDamageInfo());

        if (pierceRemaining-- <= 0)
            ReturnToPool();
    }

    public void OnDespawn()
    {
        alreadyHit.Clear();      // ★ 반드시 비울 것
        rb.linearVelocity = Vector3.zero;
        CancelInvoke();
    }
}
```

> **⚠ `alreadyHit.Clear()`를 `OnDespawn`에서 빠뜨리면**, 풀에서 재사용된 총알이 **이미 맞힌 적을 다시 못 맞히는** 버그가 된다. 총알은 풀링되므로(`Bullet.cs:3` — `IPoolable`) 반드시 정리해야 한다. 증상이 "특정 적에게만 총알이 안 통한다"로 나타나 원인 추적이 매우 어렵다.

`other.GetComponent<IDamageable>()`은 자식 콜라이더에서는 `null`일 수 있다. 현재 코드도 같은 전제를 쓰고 있으나(`Bullet.cs:68`), 관통이 붙으면 히트 수가 늘어 노출 빈도가 올라간다. `GetComponentInParent<IDamageable>()`로 바꾸는 편이 안전하다.

### 2-4. 필요한 에셋 작업

| 항목 | 작업 |
|---|---|
| `WeaponData` 에셋 2개 | `SMG_Data`, `Sniper_Data` 생성 후 위 수치 입력 |
| 투사체 프리팹 | 기관단총은 소총 총알 재사용 가능. 스나이퍼는 **별도 프리팹 권장** (굵은 트레일로 관통을 시각화) |
| **`PoolManager.configs` 등록** | 새 투사체·이펙트 프리팹을 씬의 `PoolManager`에 등록. 누락 시 경고 로그와 함께 기본 풀이 생성되지만(`PoolManager.cs:40-45`) 초기 확장 때 프레임 스파이크가 생긴다 |
| 무기 모델 | 없으면 소총 모델을 재사용해도 로직 검증에는 충분하다 |

## 3. 검 — 근접 무기

### 3-1. 프로젝트에 이미 근접 판정 선례가 두 개 있다

새로 발명할 필요가 없다.

| 기존 코드 | 방식 | 참고할 점 |
|---|---|---|
| `Boss/BossAtkCol.cs` | 트리거 콜라이더 → `OnTriggerEnter`에서 `IDamageable.TakeDamage` | `DamageInfo`에 `cameraShake = 0.5f`를 채워 타격감을 준다 |
| `Enemy/Attack/MeleeAttack.cs` | **애니메이션 이벤트**에서 `PerformAttack()` 호출 → 단일 대상 | 이벤트 의존의 위험은 **M-3**에서 이미 지적됨 |

**권장은 제3의 방식이다** — `Physics.OverlapSphere` + 각도 필터.

| 방식 | 장점 | 단점 |
|---|---|---|
| 트리거 콜라이더 (`BossAtkCol`) | 물리적으로 정확 | 콜라이더 on/off 타이밍 관리 필요, 프리팹 작업 발생 |
| 애니메이션 이벤트 (`MeleeAttack`) | 타격 시점이 모션과 완벽히 일치 | **클립을 교체하면 이벤트가 사라진다** (M-3와 동일 위험) |
| **OverlapSphere + 각도** (권장) | 프리팹·이벤트 불필요, 사거리·각도가 데이터로 노출됨 | 시점이 모션과 미세하게 어긋날 수 있음 → `hitDelay`로 보정 |

세 번째를 권하는 이유: **검 애니메이션이 아직 없어서** 클립이 확정되기 전이다(3-5). 이벤트나 콜라이더에 묶으면 클립을 바꿀 때마다 재작업이 생긴다.

### 3-2. `MeleeWeaponData`

```csharp
[CreateAssetMenu(menuName = "Weapon/Melee Data")]
public class MeleeWeaponData : WeaponData
{
    [Header("Melee")]
    public float range = 3f;          // 사거리(m)
    public float arcAngle = 120f;     // 정면 기준 좌우 합산 각도
    public int maxTargets = 5;        // 한 번에 때릴 수 있는 최대 수
    public float hitDelay = 0.25f;    // 휘두르기 시작부터 판정까지 (모션 싱크)
    public LayerMask hitLayers;       // 적 레이어만
    public GameObject slashEffect;    // 참격 이펙트 (PoolManager 등록 필요)
}
```

### 3-3. `MeleeWeapon`

```csharp
public class MeleeWeapon : WeaponBase
{
    MeleeWeaponData Melee => (MeleeWeaponData)data;

    readonly Collider[] hits = new Collider[16];              // 할당 없는 재사용 버퍼
    readonly HashSet<Transform> struck = new();               // 1회 휘두르기 중복 방지

    protected override void OnFire(in WeaponRuntimeStats stats, in WeaponFireContext ctx)
    {
        // 휘두르는 모션 재생 → hitDelay 후 판정
        StartCoroutine(SwingRoutine(stats));
    }

    IEnumerator SwingRoutine(WeaponRuntimeStats stats)
    {
        // anim.SetTrigger("Slash") 등 — 3-5의 애니메이션 준비 후
        yield return new WaitForSeconds(Melee.hitDelay);
        ApplyHits(stats);
    }

    void ApplyHits(in WeaponRuntimeStats stats)
    {
        struck.Clear();

        Vector3 origin = transform.root.position;
        Vector3 forward = transform.root.forward;

        int count = Physics.OverlapSphereNonAlloc(
            origin, Melee.range, hits, Melee.hitLayers, QueryTriggerInteraction.Collide);

        int applied = 0;

        for (int i = 0; i < count && applied < Melee.maxTargets; i++)
        {
            Transform root = hits[i].transform.root;
            if (!struck.Add(root)) continue;              // 같은 적 중복 제거

            Vector3 dir = root.position - origin;
            dir.y = 0f;
            if (Vector3.Angle(forward, dir) > Melee.arcAngle * 0.5f) continue;   // 부채꼴 밖

            var d = root.GetComponentInParent<IDamageable>()
                 ?? hits[i].GetComponentInParent<IDamageable>();
            if (d == null) continue;

            bool crit = RollCritical(in stats);

            d.TakeDamage(new DamageInfo {
                damage = crit ? stats.Damage * stats.CritMultiplier : stats.Damage,
                isCritical = crit,
                hitPoint = hits[i].ClosestPoint(origin),
                hitDirection = dir.normalized,
                cameraShake = 0.15f,          // BossAtkCol 처럼 타격감 부여
            });

            applied++;
        }
    }
}
```

**설계 포인트**

- `OverlapSphereNonAlloc` + 고정 버퍼로 **매 휘두르기마다 할당이 생기지 않는다.** 이 프로젝트는 총알·이펙트·탄피를 전부 풀링할 만큼 할당에 신경 쓰고 있으므로(01번 5장) 일관성을 맞춘다.
- `transform.root`로 중복 제거하는 이유: 적이 자식 콜라이더(히트박스)를 여러 개 가지면 한 번 휘둘러 여러 번 때리게 된다. 관통탄과 같은 문제다(2-3).
- **`cameraShake`를 채우는 것**이 근접 무기 체감의 핵심이다. 현재 `Bullet`은 이 값을 비워두므로(기본값 0) 적을 때릴 때 화면이 흔들리지 않는다. 근접은 흔들어야 맞는 느낌이 난다. `CameraShakeManager`가 이미 있으나 **H-2(파괴된 싱글턴 참조)** 가 미해결이므로 함께 정리할 것.
- **크리티컬 판정을 `WeaponBase.RollCritical`에서** 한다 — 05번 3-6의 설계 그대로다. 투사체가 없는 무기도 같은 크리티컬 규칙을 쓸 수 있다는 것이 그 설계의 검증이다.

### 3-4. 검의 수치

| 필드 | 값 | 근거 |
|---|---|---|
| `damage` | 18 | |
| `fireInterval` | 0.7 | |
| `critChance` / `critMultiplier` | 0.10 / 2.0 | |
| `range` | 3 | `EnemyDetector` 범위보다 **작아야** 한다 (아래 주의) |
| `arcAngle` | 120° | 정면 위주. 360°로 두면 검이 아니라 오라가 된다 |
| `maxTargets` | 5 | |
| `hitDelay` | 0.25 | 클립 확정 후 조정 |

기대 DPS: `18 × 1.1 / 0.7 =` **28.3** (단일) / **141.4** (5체 동시)

> **⚠ `range`와 `EnemyDetector`의 관계**: `WeaponController`는 `detector.HasTarget`으로 발사 여부를 판단한다(05번 5장). 검의 `range`가 감지 범위보다 크면 **감지 밖의 적을 때릴 수 있고**, 작으면 **적이 감지됐는데 허공을 휘두른다.** 후자는 자동공격 게임에서 계속 발생하므로, `WeaponData.requiresTarget`과 별개로 **근접 무기는 자체 사거리 내 적 유무를 한 번 더 확인**하는 편이 낫다. 아니면 05번 4-3의 타겟 전략에 `WithinRange`를 두고 무기별 사거리를 넘기는 방식도 가능하다.

### 3-5. ⚠ 검의 진짜 비용 — 애니메이션과 부착 구조

코드는 위가 전부다. 문제는 그 바깥이다. 이 프로젝트에서 검을 넣으려면 **네 가지**를 해결해야 한다.

#### ① 휘두르기 애니메이션이 없다

`Assets/SciFiWarriorPBRHPPolyart/Animations/`는 **전부 소총(AR) 기준 클립**이다 — `Idle_gunMiddle_ar`, `Run_gunMiddle_AR`, `Shoot_AutoShot_AR`, `Reload` 등. 검 관련 클립은 하나도 없다.

→ [06-달리기구르기구현.md](06-달리기구르기구현.md) 2장과 **완전히 같은 절차**로 Mixamo에서 받아야 한다. 그 문서의 트러블슈팅(2-2)에 이미 정리된 함정들이 그대로 적용된다:
- `Copy From Other Avatar`가 아니라 **`Create From This Model`** (본 이름이 `mixamorig:*`로 달라서 실패한다)
- Bake Into Pose 설정 — 제자리 휘두르기라면 이동이 없으니 Rotation/Y만 신경 쓰면 된다
- `.meta` 직접 편집은 Unity가 덮어쓴다. **Inspector에서 할 것**

#### ② 무기 부착 구조가 계층이 아니라 애니메이션 커브다

이번 구르기 작업에서 밝혀진 사실이다. 프리팹 본 계층은 이렇다.

```
ArmPosition_Right  ←  Hips  ←  Player      ★ 손이 아니라 골반의 자식
  ├ Trigger_Right
  └ magazine_Right
```

소총(`AssaultRifle`)은 **스킨드 메시**이고, 위치를 결정하는 `ArmPosition_Right`는 **휴머노이드 본이 아니다.** 팩 클립들이 매 프레임 이 본에 커브를 넣어 손에 맞춰주기 때문에 붙어 보이는 것이다.

검은 이 구조를 쓸 수 없다. **`Hand_Right` 아래에 빈 소켓 오브젝트를 만들어 검 모델을 자식으로 붙이는 방식**으로 가야 한다.

```
Hand_Right
  └ WeaponSocket_R   ← 빈 GameObject (신설)
       └ Sword       ← 일반 MeshRenderer
```

이 방식은 **계층으로 손을 따라가므로 어떤 클립에서도 손에 붙어 있다.** 소총이 겪은 문제(Mixamo 클립에서 총이 골반을 따라 돌던 것, `WeaponHandFollower.cs`로 우회)가 애초에 발생하지 않는다.

> 장기적으로는 **소총도 이 소켓 방식으로 옮기는 것**이 맞다. 그러면 `WeaponHandFollower`라는 우회 장치가 필요 없어진다. 05번 3-3의 `WeaponData.socket` / `WeaponSocket` enum이 바로 이 구조를 전제한 설계다.

#### ③ ShootLayer가 상체를 덮어쓴다

`PlayerAnimator.controller`는 2개 레이어다.

| 레이어 | 내용 |
|---|---|
| Base Layer (0) | Idle / Run / Jump / Die / Roll |
| **ShootLayer (1)** | Idle ↔ Shoot_Autoshot_AR, **상체 마스크** |

검을 들면 상체가 소총 사격 자세로 덮어써지므로 **`SetLayerWeight(1, 0f)`로 꺼야 한다.** 구르기에서 이미 같은 처리를 했으므로(`PlayerMove.StartRoll`) 패턴은 동일하다.

→ 무기 종류가 바뀔 때 레이어 가중치를 관리하는 주체가 필요하다. **`WeaponController`가 현재 활성 무기의 `WeaponKind`에 따라 레이어를 제어**하는 것이 자연스럽다.

#### ④ 무기 모델 전환

소총 스킨드 메시를 숨기고 검을 보이게 해야 한다. 05번 3-7의 `WeaponController.TryEquip`이 `WeaponData.weaponPrefab`을 소켓에 인스턴스화하도록 설계되어 있으므로, **소총도 그 경로로 옮기면** 전환이 일관된다.

> **정리**: 검은 코드 1개 + 애니메이션 확보 + 소켓 신설 + 레이어 제어 + 모델 전환이다. **4종 중 가장 비싸므로 마지막에 하는 것을 권한다.**

## 4. 드론 — 서브유닛

### 4-1. 드론을 `IWeapon`으로 볼 것인가

| 안 | 내용 | 장점 | 단점 |
|---|---|---|---|
| **A. `DroneWeapon : WeaponBase`** (권장) | 무기가 드론들을 소유. 슬롯 하나를 차지 | 슬롯 UI·업그레이드·`WeaponModifier`를 **그대로 재사용** | 드론이 "손에 든 무기"가 아닌데 무기로 취급됨 |
| B. 별도 `SubUnitController` | 무기와 완전히 분리된 시스템 | 개념이 정확 | 슬롯 UI·업그레이드 경로를 **따로 다 만들어야 함** |

**A를 권장한다.** 뱀파이어 서바이벌류는 회전 오브·장판·소환물을 모두 무기 슬롯으로 취급하는 것이 표준이다. 05번 6-4에서 `OrbitWeapon`으로 이미 **투사체 없는 무기가 같은 계약에 들어맞는지 검증**해뒀고, 드론은 그 확장판이다.

`WeaponBase`의 쿨다운 기능이 곧 "드론 발사 주기"가 되므로 추가 타이머도 필요 없다.

### 4-2. 구조

```
WeaponController (플레이어 루트)
  └ DroneWeapon : WeaponBase          ← 슬롯 1개 차지, 드론 스폰/파괴/발사 지시
       ├ DroneUnit  (월드에 존재)      ← 궤도 이동, 발사 연출
       ├ DroneUnit
       └ ...                           (레벨 → 드론 수)
```

```csharp
public class DroneWeapon : WeaponBase
{
    DroneWeaponData Drone => (DroneWeaponData)data;

    readonly List<DroneUnit> units = new();
    int nextUnit;                     // 라운드로빈 발사

    void OnEnable()  => GameEvents.OnPlayerDeadStart += DespawnAll;
    void OnDisable() => GameEvents.OnPlayerDeadStart -= DespawnAll;

    public override void SetLevel(int level)
    {
        base.SetLevel(level);
        SyncUnitCount();              // 레벨 = 드론 수
    }

    protected override void OnFire(in WeaponRuntimeStats stats, in WeaponFireContext ctx)
    {
        if (units.Count == 0) return;

        // 드론을 번갈아 쏘게 해서 발사가 한 기에 몰리지 않게 한다
        for (int i = 0; i < units.Count; i++)
        {
            var u = units[(nextUnit + i) % units.Count];

            if (u.TryFire(in stats, ctx.Targets, Drone.droneRange))
            {
                nextUnit = (nextUnit + i + 1) % units.Count;
                return;
            }
        }
    }
}
```

### 4-3. ⚠ 드론을 플레이어의 자식으로 두면 함께 회전한다

이 프로젝트에서 반드시 걸리는 문제다.

`PlayerMove.FixedUpdate`는 **매 프레임 마우스 방향으로 캐릭터를 회전**시킨다(`PlayerMove.cs:264-276`). 드론을 플레이어의 자식으로 두면 마우스를 돌릴 때마다 드론이 **플레이어 주위를 휩쓸려 돌아간다.** 궤도 운동과 겹쳐 멀미가 날 정도로 어지러워진다.

**해결**: 드론을 플레이어의 **자식으로 두되**(씬 전환 시 `DontDestroyOnLoad`를 함께 상속받기 위해), **위치와 회전을 매 프레임 월드 좌표로 직접 지정**한다. 부모의 회전은 자동으로 무시된다.

```csharp
void LateUpdate()
{
    orbitAngle += data.orbitSpeed * Time.deltaTime;

    float rad = (orbitAngle + indexOffset) * Mathf.Deg2Rad;
    Vector3 target = owner.position
                   + new Vector3(Mathf.Cos(rad), 0f, Mathf.Sin(rad)) * data.orbitRadius
                   + Vector3.up * data.orbitHeight;

    // 월드 좌표로 직접 지정 → 부모(플레이어)의 회전에 영향받지 않는다
    transform.position = Vector3.Lerp(transform.position, target, data.followLerp * Time.deltaTime);

    if (currentTarget != null)
        transform.rotation = Quaternion.LookRotation(currentTarget.position - transform.position);
}
```

> `LateUpdate`를 쓰는 이유는 플레이어가 `FixedUpdate`에서 움직인 뒤에 따라붙어야 떨림이 없기 때문이다. `WeaponHandFollower`가 같은 이유로 `LateUpdate`를 쓴다.

### 4-4. 드론은 풀링 대상이 아니다

총알·이펙트와 달리 **드론은 런 전체에 걸쳐 살아 있다.** 장착 시 1회 `Instantiate`, 해제·사망 시 `Destroy`로 충분하다. `PoolManager`에 넣으면 오히려 관리가 복잡해진다.

단, **드론이 쏘는 총알은 기존 투사체 풀을 그대로 쓴다.**

### 4-5. 드론의 타겟팅

| 방식 | 평가 |
|---|---|
| 플레이어의 `EnemyDetector`(`ITargetProvider`) 공유 | **권장.** 감지 로직이 한 곳에 남고 성능이 좋다. 드론이 자기 사거리(`droneRange`)만 추가로 확인 |
| 드론마다 자체 트리거 콜라이더 | 드론 수만큼 감지 비용이 늘고, 감지 로직이 복제된다 |

05번 4장의 `ITargetProvider.GetTargets(from, max, buffer)`가 **`from`을 인자로 받는 이유가 바로 이것**이다. 드론은 자기 위치를 넘겨 가장 가까운 적을 찾는다.

> **`EnemyManager`에 질의 메서드가 없다.** `private List<Enemy> enemies`(`EnemyManager.cs:9`)로 닫혀 있어 외부에서 적 목록을 볼 수 없다. 드론이 플레이어 감지 범위 **밖**의 적까지 노리게 하려면 `EnemyManager`에 읽기 전용 접근이나 "가장 가까운 적" 질의를 추가해야 한다. 1차에는 플레이어 감지 범위로 한정하는 것이 간단하다.

### 4-6. 드론의 수치

| 필드 | 값 |
|---|---|
| `damage` | 6 |
| `fireInterval` | 0.8 |
| `projectileSpeed` | 18 |
| `critChance` / `critMultiplier` | 0.05 / 2.0 |
| `droneCount` | 1 (레벨당 +1, 최대 5) |
| `orbitRadius` / `orbitHeight` | 2.5 / 1.8 |
| `droneRange` | 12 |

기대 DPS: 드론 1기 **7.9** → 5기 **39.4**

드론은 **단독으로는 약하고 레벨업으로 강해지는** 무기다. 다른 무기와 달리 플레이어가 신경 쓸 필요 없이 계속 딜이 들어가므로, 단일 DPS를 낮게 잡는 것이 맞다.

### 4-7. 생명주기 주의

| 이벤트 | 처리 |
|---|---|
| `OnPlayerDeadStart` | 드론 전부 제거 (`AutoAttack.StopAttack`과 같은 패턴) |
| 씬 전환 | 플레이어가 `DontDestroyOnLoad`이므로 **자식이면 자동 유지** |
| `GameAppManager.OnPlayerDead` → `Destroy(Player)` | 자식이면 함께 파괴됨 |

**H-1의 교훈을 적용할 것**: 드론 스폰/해제를 코루틴으로 관리하면 컴포넌트가 비활성화될 때 중단되어 드론이 유령처럼 남는다. `SyncUnitCount()`처럼 **즉시 실행되는 동기 메서드**로 관리한다.

## 6. 업그레이드 연동

05번 7-2의 3종 `UpgradeEffect`를 그대로 쓴다. 무기별 업그레이드 예시다.

| 업그레이드 | 효과 | SO 종류 |
|---|---|---|
| 연사 강화 | `fireIntervalMul = 0.85` (전체 무기) | `WeaponModifierUpgrade` |
| 치명타 확률 +5% | `critChanceAdd = 0.05` | `WeaponModifierUpgrade` |
| 관통 +1 | `pierceAdd = 1` | `WeaponModifierUpgrade` — **스나이퍼와 궁합** |
| 스나이퍼 레벨업 | 특정 무기 강화 | `WeaponLevelUpUpgrade` |
| **드론 추가** | 드론 수 +1 | `WeaponLevelUpUpgrade` (드론은 레벨 = 수) |
| 기관단총 획득 | 새 무기 장착 | `EquipWeaponUpgrade` |

> **05번 7-3의 구멍을 먼저 막을 것.** 무기 획득 카드를 넣으면 `UpgradeManager.GetRandomUpgrades`에서 실제로 터진다 — 이미 보유한 무기를 필터링하면 풀이 줄어 `count > pool.Count`에서 예외가 나고, 슬롯이 가득 찬 상태로 무기 카드를 고르면 **EXP만 소모되고 아무 일도 일어나지 않는다**(`UpgradeManager.cs:42-46`이 `Apply` 결과를 보지 않고 `OnUpgradeSuccess`를 발행). 이 문서의 모든 무기가 그 경로를 타므로 **8장 1단계에 포함**했다.

## 9. 검증 항목

**투사체 3종**
1. 소총 이관 후 데미지·발사속도·크리티컬 빈도가 **이관 전과 동일**한가 (2단계)
2. 기관단총: 초당 8발 정도가 나가는가, 원거리에서 스프레드로 빗나가는가
3. 스나이퍼: 일렬로 선 적 4마리를 한 발로 관통하는가
4. **관통탄 풀 재사용** — 같은 총알이 재사용됐을 때 이전에 맞힌 적을 정상적으로 맞히는가 (2-3 경고)
5. 무기 2개 이상 장착 시 **각자 다른 주기로** 발사되는가

**검**
6. 부채꼴 밖(뒤쪽) 적은 안 맞는가
7. 자식 콜라이더가 여러 개인 적을 **한 번만** 때리는가
8. `maxTargets`를 넘는 적이 있을 때 정확히 그 수만 맞는가
9. 검을 들었을 때 상체가 소총 사격 자세로 돌아가지 않는가 (3-5 ③)
10. 검 모션이 어떤 클립에서도 손에 붙어 있는가 (3-5 ②)

**드론**
11. **마우스를 크게 돌렸을 때 드론이 함께 휩쓸려 돌지 않는가** (4-3 — 가장 놓치기 쉬움)
12. 레벨업으로 드론 수가 늘어나는가, 궤도에 균등 배치되는가
13. 사거리 밖 적에게는 쏘지 않는가
14. **스테이지 전환 후에도 드론이 유지되는가** (플레이어가 `DontDestroyOnLoad`)
15. 플레이어 사망 시 드론이 전부 사라지는가, 유령 드론이 남지 않는가

**공통**
16. "연사 +15%" 업그레이드 하나가 **모든 무기**에 적용되는가
17. 슬롯이 가득 찬 뒤 무기 획득 카드가 나오지 않는가 (6장 경고)
18. 업그레이드 3회 획득 후 **에디터를 멈췄을 때 `WeaponData` 에셋 값이 원래대로인가** (05번 3-5 경고)

### 값으로 정할 것

2·3·4장의 수치는 **역할 분화를 보여주기 위한 출발점**이지 정답이 아니다. 7장의 DPS 표를 기준으로 비교하며 조정하되, 조정할 때마다 다음을 확인한다.

- **단일 DPS 순위가 뒤집히지 않는지** — 기관단총이 최고, 소총이 기준선
- **스나이퍼의 관통 이득이 남아 있는지** — 밀집 DPS가 단일의 3배 이상
- **드론 1기가 다른 무기의 1/3 이하인지** — 성장형이므로 초기에 약해야 한다
