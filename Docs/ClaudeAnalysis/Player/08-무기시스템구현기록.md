# 08. 무기 시스템 구현 기록

> **성격**: [05-무기시스템설계.md](05-무기시스템설계.md)(기반 설계)와 [07-무기종류확장설계.md](07-무기종류확장설계.md)(무기 4종 설계)를 **실제로 구현한 결과**를 기록한다. 설계 문서가 아니라 **인수인계 문서**다.
> **작업 범위**: 플레이어 무기 스크립트만. 에셋(SO·프리팹·Animator)과 업그레이드 UI는 포함하지 않는다.
> **작업 일자**: 2026-09-12

## 검증 상태

프로젝트 전체 스크립트 **112개**를 Unity 6(6000.3.7f1) 런타임 어셈블리 184개에 대해 실제 컴파일했다.

```
Build succeeded.  0 Error(s)
```

유일하게 걸린 것은 기존 `PlayerStatsUI.cs:4`의 불필요한 using(`Unity.VisualScripting.Antlr3.Runtime.Misc`)이며, 이는 **L-7**로 이미 기록된 항목이고 Unity 안에서는 정상 컴파일되므로 손대지 않았다.

> 컴파일이 통과했다는 것은 **문법·타입·시그니처가 맞다**는 뜻이다. 런타임 동작(발사·판정·궤도)은 에셋을 붙인 뒤 플레이 검증이 필요하다. 절차는 6장에 있다.

## 1. 확정된 설계 결정

07번 10장의 W1~W7에 대한 답이다.

| # | 결정 | 구현에 반영된 방식 |
|---|---|---|
| **W1** | 드론을 무기 슬롯으로 | `DroneWeapon : WeaponBase`. `WeaponKind.SubUnit` |
| **W2** | 검은 `OverlapSphereNonAlloc` + 각도 필터 | `MeleeWeapon.ApplyHits`. 콜라이더·애니메이션 이벤트 의존 없음 |
| **W3** | **활성 1개 + 스왑** | `WeaponController`가 `held` / `subUnits` 두 목록을 분리 관리 |
| **W4** | 근접 무기가 자체 사거리를 재확인 | `MeleeWeapon`이 `stats.Range` 로 독립 판정 |
| **W5** | 드론 타겟은 플레이어 감지 범위로 한정 | `DroneUnit.TryFire`가 플레이어의 `ITargetProvider`를 받아 `stats.Range`로 한 번 더 필터 |
| **W6** | 소총도 소켓 방식으로 | `WeaponController.SocketBinding[]` + `ResolveSocket` |
| **W7** | `IEnemy`는 보류 | 손대지 않음 (플레이어 범위 밖) |

### ⚠ W1과 W3의 충돌을 이렇게 해소했다

**드론이 무기 슬롯인데 "활성 1개만 발사"라면 드론이 무용지물이 된다.** 손에 든 무기를 바꿀 때마다 드론이 멈추기 때문이다.

그래서 `WeaponKind`로 두 그룹을 분리했다.

| 그룹 | 종류 | 스왑 | 발사 | 모델 |
|---|---|---|---|---|
| **손에 드는 무기** | `Projectile` / `Melee` | 대상 | **활성 1개만** | 비활성은 숨김 |
| **서브유닛** | `SubUnit` | 제외 | **항상 전부** | 항상 표시 |

`WeaponData.IsAlwaysActive`(`Kind == SubUnit`)가 이 분기를 담당한다. `WeaponBase.SetActive`는 서브유닛에 대해 `active` 인자를 무시하고 항상 켜진 상태를 유지한다.

슬롯 수도 분리되어 있다 — `maxHeldSlots`(기본 4), `maxSubUnitSlots`(기본 2).

## 3. 핵심 동작

### 3-1. 스탯 3층 구조

```
WeaponData (SO)            ← 읽기 전용 기본값. 절대 수정하지 않는다
   +
WeaponModifier (누적)      ← 업그레이드 증분 + 레벨 보너스
   ↓ Compose()
WeaponRuntimeStats         ← 매 발사 시 만들어 쓰는 일회용 값
```

**SO 를 직접 수정하지 않는 것이 중요하다.** 수정하면 에디터에서 에셋에 영구 기록되어 플레이할 때마다 수치가 누적된다. `WeaponBase.accumulated`에만 쌓고 `data.Compose(TotalModifier)`로 매번 합성한다.

`WeaponModifier`의 곱셈 필드(`damageMul`, `fireIntervalMul`)는 항등원이 **1**이다. struct 기본값은 전 필드 0이므로, 인스펙터에서 직접 만든 값이 데미지를 0으로 만들 수 있다. 두 겹으로 막았다.

- `WeaponModifier.Sanitized()` — 0이면 1로 보정
- `WeaponData.OnValidate()` — `perLevelBonus`를 저장 시점에 보정

### 3-2. 발사 루프

```
WeaponController.Update()
  ├ HandleSwapInput()                      Q키 / 스크롤
  ├ WeaponFireContext 생성                 (detector, transform)
  │
  ├ held 순회
  │    ├ Tick(dt)                          비활성 무기도 쿨다운은 진행
  │    ├ i != activeHeldIndex → 건너뜀      ★ 활성 1개만 발사 (W3)
  │    ├ CanFire / ShouldFire 확인
  │    └ Fire(ctx)
  │
  └ subUnits 순회
       ├ Tick(dt)
       └ 전부 Fire(ctx)                     ★ 스왑 무관 (W1)
```

**무기별 독립 쿨다운**이 `Tick`/`CanFire`로 자연히 나온다. 기존 `AutoAttack`의 단일 `attackRate` 구조를 대체한다.

조준 방향은 `WeaponFireContext`가 **플레이어 루트의 `forward`** 로 계산한다. 이 프로젝트는 플레이어가 매 프레임 마우스 방향으로 회전하므로 별도의 `PlayerAim` 컴포넌트 없이 조준이 성립한다 (04번 설계의 `PlayerAim`은 도입하지 않았다).

### 3-3. 무기별 구현 요점

**`ProjectileWeapon`** — 소총·기관단총·스나이퍼 공용
- `stats.ProjectileCount` 만큼 반복 발사, `ApplySpread`로 퍼짐 적용
- **탄마다 크리티컬을 따로 판정**한다. 산탄이면 일부만 크리티컬이 될 수 있다
- 조준은 `ProjectileWeaponData.aimMode`로 정한다. 기본값 `AimDirection`은 캐릭터가 바라보는 방향(= 마우스 방향)으로 쏜다 — 기존 소총(`Gun`)과 같은 방식. `NearestTarget`은 감지 범위 안 최근접 적을 자동 조준한다
  - 2026-09-13 변경: 처음에는 최근접 적 자동 조준이었으나, 플레이 테스트에서 손에 든 총이 마우스를 따르지 않아 기본값을 바꿨다. 발사 조건(감지 범위 안에 적이 있을 때 자동 발사)은 그대로다

**`MeleeWeapon`** — 검
- `hitDelay` 후 `OverlapSphereNonAlloc` + 부채꼴 각도 필터
- `Collider[32]` 버퍼와 `HashSet<Transform>`을 재사용해 **휘두를 때마다 할당이 없다**
- `IDamageable`을 가진 루트 기준으로 중복 제거 → 자식 히트박스가 여러 개인 적을 **한 번만** 때린다
- `DamageInfo.cameraShake`를 채운다. 근접은 화면이 흔들려야 타격감이 난다
- 스왑으로 손에서 빠지면 진행 중인 스윙 코루틴을 중단한다 (안 하면 무기 교체 후에도 이전 판정이 들어간다)
- `Slash` 파라미터가 Animator에 없으면 조용히 건너뛴다 → **모션 확보 전에도 로직 검증 가능**

**`DroneWeapon` / `DroneUnit`** — 드론
- 레벨 = 드론 수. `OnStatsChanged` → `SyncUnitCount()`로 생성/제거
- 라운드로빈 발사 — 여러 대가 있어도 한 기에 몰리지 않는다
- 드론은 **풀링하지 않는다.** 런 전체에 걸쳐 살아 있으므로 `Instantiate`/`Destroy`로 충분하다
- 드론이 쏘는 총알은 기존 투사체 풀을 그대로 쓴다

### 3-4. ⚠ 드론이 플레이어 회전에 휩쓸리지 않게 한 처리

`PlayerMove.FixedUpdate`는 매 프레임 마우스 방향으로 플레이어를 회전시킨다. 드론을 플레이어의 자식으로 두고 `localPosition`으로 궤도를 만들면 **마우스를 돌릴 때마다 드론이 함께 휩쓸려 돌아간다.**

해결: 드론은 플레이어의 **자식이지만** `LateUpdate`에서 **위치·회전을 월드 좌표로 직접 지정**한다. 부모 회전이 자동으로 무시된다.

```csharp
// DroneUnit.LateUpdate
transform.position = Vector3.Lerp(transform.position, ComputeOrbitPosition(), ...);
```

자식으로 둔 이유는 별개다 — 플레이어가 `DontDestroyOnLoad`이므로 **씬 전환 시 드론도 함께 유지**되고, 플레이어 파괴 시 함께 정리된다.

`LateUpdate`를 쓰는 이유는 플레이어가 `FixedUpdate`에서 이동한 뒤에 따라붙어야 떨림이 없기 때문이다. `WeaponHandFollower`가 같은 이유로 `LateUpdate`를 쓴다.

### 3-5. 상체 사격 레이어 자동 제어

`PlayerAnimator.controller`의 ShootLayer(index 1)는 상체 마스크로 소총 사격 자세를 덮어쓴다. 검을 들었을 때 이게 켜져 있으면 상반신이 총을 겨눈다.

`WeaponController.ApplyShootLayerForActive()`가 스왑 시점에 자동 처리한다.

```
활성 무기가 Projectile  → 레이어 가중치 1
그 외 (Melee 등)        → 레이어 가중치 0
```

## 4. 기존 코드를 깨지 않은 방법

**어느 기존 파일도 동작이 바뀌지 않았다.** 새 시스템을 나란히 추가했다.

| 기존 코드 | 유지 방법 |
|---|---|
| `Gun.cs` | 손대지 않음 |
| `Bullet.Init(float, float)` | **오버로드로 남겨둠** → `Gun.cs:30`이 그대로 동작 |
| `AutoAttack.cs` | 손대지 않음. `detector.HasEnemy()` 계약 유지 |
| `PlayerMove.OnEnemyEntered` | `detector.OnEnemyEnter` 이벤트 계약 유지 |
| `DamageUpgrade` / `GunSpeedUp` | 손대지 않음 (`Gun` 참조가 살아 있음) |
| `PlayerStatsUI` | 손대지 않음 — `WeaponController`가 `OnBulletDamageChanged` / `OnBulletSpeedChanged`를 활성 무기 기준으로 발행한다 (`raiseLegacyStatEvents`로 끌 수 있음) |

### ⚠ 전환 시 반드시 할 것

`WeaponController`와 `AutoAttack`이 **동시에 켜져 있으면 총알이 두 번 나간다.** `WeaponController.Awake`가 이를 감지해 경고 로그를 띄운다.

```
[WeaponController] AutoAttack 이 켜져 있습니다. 이중 발사가 되므로
WeaponController 로 전환했다면 AutoAttack 컴포넌트를 비활성화하세요.
```

## 5. 업그레이드 담당자용 API

UI·카드 로직은 이번 범위가 아니다. `WeaponController`의 공개 메서드만 호출하면 된다.

```csharp
// 카드 후보 필터링 — 슬롯이 꽉 찼거나 이미 최대 레벨이면 false
bool CanAcquire(WeaponData data);

// 획득 시도. 이미 가진 무기면 레벨업한다.
WeaponAcquireResult Acquire(WeaponData data);
//   Equipped   : 새 무기 장착
//   LeveledUp  : 기존 무기 레벨업
//   NoFreeSlot : 슬롯 가득
//   MaxLevel   : 최대 레벨
//   Invalid    : 데이터 오류

// 전체 무기 강화 (연사 +15%, 치명타 +5% 등)
void ApplyGlobalModifier(in WeaponModifier modifier);

// 특정 무기만 강화
bool ApplyModifierTo(WeaponData data, in WeaponModifier modifier);

// 조회
bool Has(WeaponData data);
IWeapon Find(WeaponData data);
IReadOnlyList<IWeapon> HeldWeapons { get; }   // 스왑 대상
IReadOnlyList<IWeapon> SubUnits { get; }      // 드론
IWeapon ActiveWeapon { get; }
int ActiveIndex { get; }
bool HasFreeHeldSlot { get; }
bool HasFreeSubUnitSlot { get; }

// 스왑 (입력을 Input Action 으로 옮길 때 호출)
void SwapNext();
void SwapPrevious();
void SwapTo(int index);
```

### `Acquire`가 결과를 반환하는 이유

현재 `UpgradeManager.TryUpgrade`는 `SpendExp` 후 `UpgradeEffect.Apply`를 호출하고 **결과를 보지 않은 채** `OnUpgradeSuccess`를 발행한다. 그래서 슬롯이 가득 찬 상태로 무기 카드를 고르면 **EXP만 소모되고 아무 일도 일어나지 않는다.**

`Acquire`가 `WeaponAcquireResult`를 반환하므로 이 지점을 막을 수 있다. 권장 순서는 다음과 같다.

1. 카드 후보를 뽑을 때 `CanAcquire`로 먼저 걸러낸다
2. 걸러낸 뒤 `count = Mathf.Min(count, pool.Count)`로 클램프한다 — 안 하면 `GetRandomUpgrades`가 `Random.Range(0, 0)` 후 빈 리스트를 인덱싱해 예외가 난다
3. `Acquire` 결과가 성공이 아니면 EXP를 되돌리거나 애초에 소모하지 않는다

### 구독할 이벤트

```csharp
GameEvents.OnWeaponSwapped;       // Action<IWeapon> — 활성 무기가 바뀔 때
GameEvents.OnWeaponStatsChanged;  // Action<IWeapon> — 레벨업·모디파이어 적용 시
```

> **H-3 주의**: 슬롯 UI를 만들 때 `OnPlayerSpawned`로 참조를 다시 잇는 패턴을 쓸 텐데, **인스턴스 이벤트를 구독한다면 반드시 해제를 짝지어야 한다.** `PlayerStatsUI`가 이 짝을 맞추지 않아 스테이지를 넘길수록 핸들러가 누적되는 문제가 이미 있다.

## 6. 아직 남은 작업

스크립트는 끝났고 **에셋·프리팹·Animator 작업이 남았다.**

| # | 작업 | 종류 |
|---|---|---|
| 1 | `ProjectileWeaponData` / `MeleeWeaponData` / `DroneWeaponData` 에셋 생성 | SO |
| 2 | **`Hand_Right` 아래 빈 소켓 오브젝트 신설** → `WeaponController.sockets` 연결 | 프리팹 |
| 3 | 무기 프리팹에 `ProjectileWeapon` / `MeleeWeapon` / `DroneWeapon` 부착 | 프리팹 |
| 4 | Player 프리팹에 `WeaponController` 추가 + **`AutoAttack` 비활성화** | 프리팹 |
| 5 | 투사체·이펙트 프리팹을 씬 `PoolManager.configs`에 등록 | 씬 |
| 6 | 드론 프리팹에 `DroneUnit` 부착 | 프리팹 |
| 7 | Animator에 `Slash` Trigger 추가 (검 모션 확보 후) | Animator |
| 8 | 스왑 입력을 `.inputactions`의 `SwapWeapon` 액션으로 이관 | 입력 |

### 스왑 입력에 대한 임시 조치

`.inputactions` 편집은 에디터 왕복과 코드 재생성이 필요해 이번에는 하지 않았다. 대신 `WeaponController`가 **`Keyboard.current` / `Mouse.current`를 직접 읽는다.**

```
enableDirectSwapInput = true   (인스펙터에서 끌 수 있음)
swapKey = Q
swapWithScrollWheel = true
```

정석은 `.inputactions`에 `SwapWeapon` 액션을 추가하고 `SwapNext()`를 호출하는 것이다. 전환할 때 `enableDirectSwapInput`만 끄면 된다.

### 소켓 신설이 주는 부수 효과

현재 소총은 스킨드 메시이고 `ArmPosition_Right`(`Hips`의 자식, 비휴머노이드 본)가 위치를 결정한다. 팩 클립들이 이 본에 커브를 넣어 손에 맞춰주는 구조라, Mixamo 클립에서는 총이 골반을 따라 돌아버린다. 그래서 `WeaponHandFollower.cs`라는 우회 장치를 만들어 구르기 중에만 손에 고정하고 있다.

**소총을 소켓 방식(`Hand_Right` 자식)으로 옮기면 계층으로 손을 따라가므로 이 문제가 애초에 발생하지 않고, `WeaponHandFollower`를 제거할 수 있다.**

### `Prune`에 넣은 방어

적이 풀로 반환되면 `OnTriggerExit`이 오지 않을 수 있어, 조회 시 파괴/비활성 대상을 걸러낸다.

```csharp
if (t == null || !t.gameObject.activeInHierarchy)   // t?. 는 쓰지 않는다
```

`t?.`를 쓰지 않은 이유: C#의 null 조건 연산자는 Unity가 오버로드한 `==`를 우회해 **파괴된 객체(fake null)를 걸러내지 못한다.** **H-2**가 정확히 이 함정에 걸린 사례다.

## 8. 관통 구현 시 주의 (이미 반영됨)

`Bullet`은 풀링되므로 `alreadyHit` 집합을 **`OnDespawn`에서 반드시 비워야 한다.** 비우지 않으면 재사용된 총알이 이전에 맞힌 적을 못 맞힌다. 증상이 "특정 적에게만 총알이 안 통한다"로 나타나 추적이 매우 어렵다.

```csharp
public void OnDespawn()
{
    rb.linearVelocity = Vector3.zero;
    alreadyHit.Clear();       // ★
    pierceRemaining = 0;
    CancelInvoke();
}
```
