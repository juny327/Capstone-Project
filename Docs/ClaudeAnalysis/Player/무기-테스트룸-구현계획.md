# 무기 테스트 룸 구현 계획

> 작성: 2026-09-25 · 확인 브랜치: `player` · HEAD: `bb48ec0` (`사운드 입히기`)
> 기준: 커밋되지 않은 변경을 포함한 현재 코드·프리팹·씬·데이터 파일.
> 최초 설계 문서. 아래 ‘협업 제약 반영’이 후속 구현에서 기존 설계보다 우선한다.
> 관련 문서: [플레이어 시스템 정리](플레이어-시스템-정리.md) · [무기 3종 구현 계획](무기-3종-구현계획.md) · [플레이어 사운드 설계](플레이어-사운드-설계.md)

로비 오른쪽 아래 버튼으로 들어가서, 왼쪽에 놓인 무기를 획득하고 오른쪽의 무한 체력 해골을 공격하는 전용 공간을 만든다. 기존 플레이어·무기·피격·사운드 경로를 사용해 실제 게임에서 쓰는 동작을 반복 확인하는 것이 목적이다.

**사용자 확인 사항: 이번 범위는 주무기 7종이다. 드론은 배치하지 않고 서브유닛 구조도 변경하지 않는다.**

## 협업 제약 반영 — 후속 구현 기준

사용자 요청에 따라 **기존 C# 스크립트는 `Assets/Scripts/Player` 안에서만 수정한다.** 새 Test 관련 런타임·에디터 스크립트와 전용 에셋은 별도로 추가한다.

이에 따라 아래 최초 설계의 4·6·9장 중 공용 코드 수정 제안은 다음 방식으로 대체한다.

| 최초 제안 | 협업 제약을 반영한 구현 |
|---|---|
| `GameAppManager`·`LobyManager`에 테스트 진입 추가 | 새 `TestRoomEntry`가 로비 버튼을 받고, `TestRoomManager`가 씬 소유 플레이어를 생성·정리 |
| `Enemy`에 훈련 모드 추가 | 해골 모델·피격 크기·플래시를 재사용한 별도 프리팹과 `TestRoomDummy : IDamageable` 사용. 같은 계층에 Enemy를 두지 않음 |
| `SoundManager`에 효과음 정리 메서드 추가 | 공격·풀을 먼저 중지한 뒤 새 Test 매니저가 비반복 AudioSource를 정리. BGM은 기존 씬별 선택 사용 |
| 공용 플레이어를 테스트에 재사용 | 테스트 플레이어는 `GameAppManager.Player`에 등록하거나 `DontDestroyOnLoad`로 유지하지 않음. 로비 선택값도 변경하지 않음 |

기존 스크립트 수정 대상은 `WeaponController.cs`(시작 무기 지정·슬롯 선택/교체), `PlayerStatsUI.cs`(StageData 없는 HUD·무기 스탯 초기값), `PlayerMove.cs`(시험 구역 밖 안전 복귀)다. `Loby.unity`에는 새 버튼을 추가하고, 빌드 씬 목록 끝에 `TestRoom.unity`를 등록한다. 기존 Stage 씬·몬스터·무기 데이터는 수정하지 않는다.

## 구현 현황 — 2026-09-26

첫 버전의 씬·프리팹·버튼·런타임 연결까지 구현했다. 아래 1장부터는 구현 전 조사와 최초 설계 기록이며, 실제 변경 범위는 위 협업 제약과 이 절을 기준으로 한다.

### 실행 방법

1. `Assets/Scenes/Loby.unity`를 열고 Play → 오른쪽 아래 **테스트 룸**을 누른다. `Assets/Scenes/TestRoom.unity`를 직접 열어 Play해도 동작한다.
2. 소총 Lv.1로 시작한다. 왼쪽 청록색 구역에 **플레이어 몸이 들어가면** 표시된 무기를 즉시 장착한다. 주무기 4칸이 차면 현재 사용하는 칸만 교체한다. 이미 가진 무기는 기존 칸으로 전환하며 중복 강화하지 않는다.
3. 오른쪽 해골 쪽으로 이동한다. 기본 적 감지 반경은 10m이며, 검은 약 3m까지 접근해야 한다. 기존처럼 마우스 방향으로 조준하고 자동 공격한다. `Q`/휠 교체, `R` 장전도 그대로 사용한다.
4. 오른쪽 위 **측정 초기화**는 기록만 지우고, **룸 초기화**는 위치·무기·탄약·기록·잔여 탄을 초기 상태로 되돌린다. **로비로**를 누르면 테스트 플레이어를 정리하고 돌아간다.

씬과 프리팹은 이미 저장되어 있으므로 구성 도구를 먼저 실행할 필요는 없다. 새 에셋의 `.meta` 파일도 함께 공유해야 연결이 유지된다.

기존 C# 변경은 `PlayerMove.cs`, `PlayerStatsUI.cs`, `WeaponController.cs` **3개뿐이다.** `Enemy.cs`, Core·Audio·맵 생성 코드, 기존 플레이어/몬스터 프리팹, 무기 데이터는 수정하지 않았다. 로비 씬에는 진입 버튼을 추가하고 빌드 목록 마지막에 TestRoom을 추가했다.

### 검증과 유지보수

- Unity `6000.3.7f1`에서 컴파일·저장된 씬 참조 검사와 **Play Mode 통합 검증 98항목을 통과했다.** 직접 실행, 몸/센서 구분, 7종 실제 명중, 4칸 교체, 중복 선택, 장전 취소/완료, 소수 피해·5초 DPS, 룸 초기화, 로비 3회 왕복, 일반 게임의 선택 무기 반영을 확인했다. 검사 실행 중 런타임 Error/Exception/Assert는 없었다.
- 1920×1080·1920×1200·2520×1080으로 화면을 캡처해 버튼·측정 패널·탄약 HUD 배치를 확인했다. 작은 월드 이름표가 번지는 문제는 전용 텍스트 머티리얼과 크기 조정으로 보완했다. 공용 폰트는 변경하지 않았다.
- 기존 7개 씬과 TestRoom을 포함한 Windows x64 Development 빌드에 성공했다(오류 0개, 경고 3개). 결과물은 `Builds/TestRoomValidation/NoName.exe`, 요약은 `Logs/TestRoom/build.txt`다. 빌드 파일은 Git에서 제외된다. 빌드 생성과 Play Mode 검증을 완료했으며, 독립 실행 파일에서의 직접 조작·청취까지 자동 검증한 것은 아니다.
  - 경고는 기존 `StageRewardCard.tag`의 상속 멤버 숨김(2회)과 Unity Cloud 미로그인 상태에서 네이티브 심볼 업로드를 건너뛴 안내다. 협업 범위 밖의 기존 코드는 수정하지 않았다.
- 자동 검증은 `Tools > Test Room > 저장된 씬 자동 검증`에서 재실행할 수 있다. 결과는 `Logs/TestRoom/validation.txt`, 화면 캡처는 같은 폴더에 기록한다. `Logs`는 Git에서 제외된다.
- 기본 구성을 다시 생성할 때만 `Tools > Test Room > 테스트 룸 구성`을 사용한다. **테스트 씬·전용 프리팹의 수동 배치를 기본 구성으로 덮어쓰므로**, 일반 실행에는 사용하지 않는다.
- 피해 팝업은 기존 게임과 같은 정수 표시를 재사용하지만, 측정 패널은 원래 `DamageInfo.damage` 소수 값을 기록한다. DPS는 최근 5초 합계 ÷ 5이며 첫 5초는 `측정 중`으로 표시한다. 측정 초기화 당시 날아가던 탄은 새 측정에 포함된다.
- 해골 하나를 사용하므로 다중 대상 연쇄·관통·광역 효율은 검증 대상이 아니다. 소리의 청감·볼륨, 5분 이상 연사 시 체감, 실제 키보드·휠·구르기의 조작감은 아래 수동 체크리스트로 별도 확인한다.

## 1. 현재 프로젝트 구현 정도

아래의 ‘구현 확인’은 코드와 직렬화된 연결을 확인했다는 뜻이다. 전체 게임의 실행 안정성이나 밸런스가 검증되었다는 의미는 아니다.

| 영역 | 현재 확인된 구현 | 테스트 룸에서의 활용 |
|---|---|---|
| 실행 환경 | Unity `6000.3.7f1`, URP, Input System, Cinemachine, AI Navigation | 동일 환경 사용 |
| 게임 흐름 | `Loby` → `Stage1` 시작, `Stage1~3`, `IntroScene`, `StageBoss`, `EndingScene` 및 전환 코드 | 로비에 별도 진입 경로 추가 |
| 플레이어 수명 | `GameAppManager`가 플레이어를 생성하고 `DontDestroyOnLoad`로 유지 | 테스트 세션과 일반 플레이 세션 분리 필요 |
| 맵 | `MapGenerator`의 Cellular Automata 생성, 바닥·벽 렌더링, NavMesh 생성, 스포너 배치 | 테스트 룸은 고정 평지로 별도 구성 |
| 이동 | 이동·마우스 방향 회전·점프·스프린트·스태미나·구르기 | 그대로 사용 |
| 무기 | 주무기 7종 + 드론 1종, 데이터 기반 스탯·치명타·레벨·강화 | 주무기 7종의 실제 무기 에셋 사용 |
| 슬롯 | 주무기 4칸, 서브유닛 2칸, `Q`·휠 스왑 | 4칸 규칙 유지, 가득 찼을 때 교체 추가 |
| 탄창·장전 | 주무기별 탄창, 자동·수동 장전, 스왑·구르기 시 장전 취소 | 무제한 탄약을 기본 적용하지 않고 실제 동작 검사 |
| 적·전투 | 일반 적 A~D, 이동·공격·피격·처치·경험치, 보스 상태·스킬 코드 | 해골 `MonsterA`를 고정 표적으로 재사용 |
| 성장 | 경험치·레벨업 카드·강화 효과·파이어볼·스테이지 보상 | 초기 버전에서는 비활성, 무기 기본 상태 비교 |
| HUD | 체력·경험치·진행도·스태미나·구르기·주무기 슬롯·탄약 | 전투 HUD 재사용, 스테이지 진행도는 제외 |
| 사운드 | `SoundManager`, 믹서, 무기 발사·장전·명중·충전·이동 효과음 및 씬별 BGM 연결 | 같은 경로로 청취, 테스트 룸 기본 BGM은 없음 |
| 풀링 | 탄환·피격 이펙트·데미지 숫자 등의 `PoolManager` 경로 | 새 씬에도 필수 |
| 테스트 룸 | 전용 씬·입장 버튼·무기 픽업·무한 체력 표적·측정 UI 없음 | 이번 계획의 신규 작업 |

### 기존 문서와 달라진 점

- `플레이어-시스템-정리.md`의 ‘사운드 없음’은 현재 작업 파일 기준으로 오래된 설명이다. 사운드 코드와 에셋, 로비·스테이지 연결이 있다.
- 같은 문서의 ‘공격력·탄속 업그레이드가 옛 Gun만 변경’하는 문제는 현재 `DamageUpgrade`·`GunSpeedUp`에서 `WeaponController.ApplyGlobalModifier()`를 사용하도록 바뀌었다.
- 다만 `Player.prefab`의 `Gun`은 여전히 켜져 있고, `Gun.Start()`와 `PlayerStatsUI.SetPlayer()`에 옛 수치를 HUD에 넣는 경로가 남아 있다. 측정 UI는 반드시 `ActiveWeapon.Stats`를 읽는다.
- `SoundManager`는 현재 `DontDestroyOnLoad` 방식이다. 파일 상단의 ‘씬마다 독립’ 주석보다 실제 `Awake()`를 기준으로 설계해야 한다.
- `WeaponController.Start()`에는 시작 무기 폴백이 있지만, 이것만으로 씬 직접 실행 시 플레이어가 생기는 것은 아니다. `Stage1` 씬에는 `GameAppManager` 직접 배치가 확인되지 않아, 새 테스트 씬에는 직접 실행용 구성을 명시해야 한다.

## 2. 첫 버전의 동작 명세

| 항목 | 동작 |
|---|---|
| 입장 | 기존 중앙 게임 시작 버튼을 유지하고 로비 오른쪽 아래에 `테스트 룸` 버튼 추가 |
| 씬 | `Assets/Scenes/TestRoom.unity`라는 독립 씬 |
| 시작 상태 | 새 플레이어, 소총 Lv.1 한 자루, 기본 스탯·가득 찬 탄창. 로비의 일반 게임용 선택값과 분리 |
| 맵 | 현재 스테이지와 어울리는 바닥·조명·탑다운 시점. 이동을 막는 내부 장애물 없음 |
| 무기 선택 | 맵 왼쪽 세로 한 줄의 7개 구역 중 원하는 구역에 몸으로 진입하면 획득 |
| 빈 슬롯 | 새 무기를 빈 주무기 슬롯에 넣고 즉시 손에 듦 |
| 슬롯 가득 참 | **현재 손에 든 무기의 슬롯만** 새 무기로 교체하고 즉시 사용 |
| 이미 가진 무기 | 그 무기가 들어 있는 슬롯으로 스왑. 중복 획득·자동 레벨업 없음 |
| 이미 사용 중인 무기 | 아무 상태도 바꾸지 않음. 탄약 보충·쿨다운 초기화·반복 소리 없음 |
| 픽업 재사용 | 획득해도 전시물은 남음. 구역을 완전히 나갔다가 다시 들어오면 다시 선택 가능 |
| 적 | 맵 오른쪽에 해골 1마리. 무한 체력, 이동·공격·경험치 드롭·처치 카운트 없음 |
| 조작 | 기존 이동·마우스 조준·자동 공격·`Q`/휠 교체·`R` 장전 유지 |
| 측정 | 마지막 피해, 누적 피해, 명중 수, 치명타 수, 최근 5초 DPS, 표적 거리 |
| 초기화 | `측정 초기화`와 `룸 초기화`를 구분 |
| 퇴장 | 화면 오른쪽 위 `로비로` 버튼. 테스트 플레이어와 잔여 전투 상태 정리 후 복귀 |

‘몸으로 진입하면 획득’, ‘소총으로 시작’, ‘정지·비공격 표적’은 반복 테스트에 맞춘 기본 설계안이다. 별도 상호작용 키나 확인창은 첫 버전에 넣지 않는다.

## 3. 공간과 화면 배치

아래는 **맵의 배치도**다. 카메라는 기존처럼 플레이어를 따라가므로 전체 맵을 항상 한 화면에 표시하는 구성은 아니다.

```text
맵 왼쪽                                                맵 오른쪽
┌────────────────────────────────────────────────────────────┐
│ [소총]                                                      │
│ [기관단총]                                                  │
│ [스나이퍼]                 장애물 없는 평지                  │
│ [검]       플레이어 시작 →     거리 눈금     →   해골 1마리  │
│ [샷건]                                           HP: 무한    │
│ [전격 소총]                                                 │
│ [충전 레이저]                                               │
└────────────────────────────────────────────────────────────┘

화면 UI: 위쪽 측정 패널 / 오른쪽 위 초기화·로비 버튼
         왼쪽 아래 주무기 4칸·스태미나·구르기 / 오른쪽 아래 탄약
```

- 초안 치수: 시험 구역 약 `36 × 26m`, 바닥은 그보다 조금 넓게 만든다. 실제 카메라에서 확인 후 조정한다.
- 월드 `X`축을 좌우로 사용한다. 전시 구역 `x = -14`, 해골 `x = +14, z = 0`, 플레이어 시작 `x = -10, z = 0`을 초안으로 둔다. 높이는 실제 바닥·캐릭터 피벗에 맞춘다.
- 7개 구역은 `z = +9, +6, +3, 0, -3, -6, -9`에 배치한다. 구역 사이에 빈틈을 두고 옆으로 우회해 원하는 무기만 고를 수 있게 한다.
- 무기 아이콘·이름·바닥 표시와 Trigger만 사용한다. 전시대나 무기 모델에 이동을 막는 일반 Collider를 붙이지 않는다.
- 무기 전시는 `WeaponData.icon`을 우선 사용한다. 실제 `W_*.prefab`을 초기화 없이 바닥에 놓으면 실행 컴포넌트까지 복제되므로 장식은 별도 시각 요소로 만든다.
- 바닥은 `PlayerMove.groundLayer`가 참조하는 **Ground 레이어(현재 6번)**와 Collider를 가져야 한다. 이동뿐 아니라 마우스 조준·착지·구르기에도 필요하다.
- 시험 구역 밖으로 나가면 낙하 전에 안전 위치로 복귀시키고 이동 속도를 정리한다. 내부에 보이지 않는 벽을 추가하지 않는다.
- 거리 눈금은 표적에서 3·6·10·14·18m 지점에 두고, 실제 측정 패널에는 플레이어와 표적의 수평 거리를 표시한다.
- 무기 구역과 표적이 화면 밖으로 나가면 간단한 방향·거리 표시를 제공한다.

### 감지 범위와 사거리는 구분해야 한다

현재 `Player.prefab`의 `EnemyDetector`는 반경 **10m**다. `requiresTarget`이 켜진 무기는 감지된 적이 있어야 발사한다. 전격 소총 데이터의 14m, 충전 레이저의 18m는 감지 반경과 별개다.

따라서 처음 왼쪽에서 오른쪽 표적을 향해 서 있어도 자동 발사가 시작되지 않는 것이 현재 규칙이다. `표적 감지 밖 — 가까이 이동` 안내를 표시한다. 검은 약 3m까지 접근해야 한다. 첫 버전은 감지 반경을 몰래 넓히지 않고 실제 스테이지의 동작을 유지한다. 10m 밖의 빔 사거리 자체를 검증하는 기능은 후속 감지 범위 조절 옵션으로 구분한다.

## 4. 씬 진입·초기화·퇴장 설계

### 4-1. 책임 분리

`GameAppManager`가 플레이어 생성·파괴와 씬 전환을 계속 담당하고, 새 `TestRoomManager`는 전시 구역·표적·측정 UI를 관리한다. 두 매니저가 각각 플레이어를 만들지 않는다.

| 기존 코드의 조건 | 필요한 변경 |
|---|---|
| `OnSceneLoaded()`는 `StartsWith("Stage")`일 때만 플레이어 생성 | `TestRoom`을 명시적으로 처리하는 분기 추가 |
| `SetupPlayer()`는 고정 위치를 사용하며 기존 플레이어를 재사용 | 테스트 진입·룸 초기화에는 새 플레이어 생성, 테스트 시작점 적용 |
| `WeaponController.Start()`는 로비 선택값 또는 `starterWeapon`을 읽음 | 테스트에서는 소총을 고르는 시작 무기 정책 추가. `Start()`에서 한 번만 장착 |
| 플레이어 생성 후 `OnPlayerSpawned`·`OnCameraReady`로 연결 | 테스트에서도 같은 순서로 HUD·카메라·이동의 참조 연결 |
| `SoundManager`는 씬을 넘어 유지 | 입장·초기화·퇴장 시 이전 효과음과 충전음 잔류 정리 |
| `GameManager.LoadNextStage()`는 `buildIndex + 1` 사용 | 빌드 씬 목록 **마지막에** TestRoom 추가. 기존 순서 유지 |

`StartTestRoom()` 같은 진입 메서드를 추가하고 로비 버튼에서 호출한다. `TestRoom`을 인식시키려고 이름을 `StageTestRoom`으로 바꾸는 방식은 피한다. 테스트의 독립적인 세션 규칙을 코드에 명시한다.

### 4-2. 권장 진입 순서

1. 중복 클릭을 막고 `Time.timeScale = 1`로 복원한다.
2. 이전 플레이어가 있으면 입력·공격을 중지하고 파괴한다. `Player`, `PlayerStats`, `GameEvents.Player` 참조도 정리한다.
3. 테스트 진입 정보를 설정하고 `TestRoom`을 이름으로 로드한다. 일반 게임용 `SelectedWeapon`을 테스트 선택으로 덮어쓰지 않는다.
4. 씬의 카메라·풀·HUD가 준비된 상태에서 `GameAppManager`가 플레이어 한 명을 생성해 테스트 시작점에 둔다.
5. `GameEvents.Player` 설정 → `OnPlayerSpawned` → `OnCameraReady` 연결을 유지한다.
6. `WeaponController.Start()`에서 테스트 시작 무기를 한 번만 획득한다. 시작 무기 초기화가 끝난 뒤 픽업을 허용한다.
7. 테스트 매니저는 오른쪽 표적 한 마리를 생성하고 측정을 초기화한다.

생성 직후 `Acquire()`로 시작 무기를 바꾸고 나중에 `Start()`가 다시 추가하는 경쟁을 만들지 않는다. 준비 여부를 명시적으로 확인하며 ‘한 프레임 기다리면 항상 준비됨’에 의존하지 않는다.

### 4-3. 에디터에서 TestRoom 직접 Play

- TestRoom에도 `playerPrefab`이 연결된 `GameAppManager` 부트스트랩 오브젝트와 기존 설정의 `SoundManager`를 둔다. 로비에서 온 경우 각 싱글턴의 중복 방지 경로가 적용되어야 한다.
- 활성 씬 이름에서도 테스트 모드를 판별해, 로비 버튼을 누르지 않았어도 같은 시작 상태를 만든다.
- 플레이어 생성 책임은 항상 `GameAppManager` 하나에 둔다. 씬에 플레이어를 직접 배치하거나 `RunManager`·`PlayerSpawnPoint`를 함께 활성화하지 않는다.
- 씬 이벤트 구독·해제와 준비 처리를 중복 호출해도 플레이어·해골·HUD 구독이 늘어나지 않도록 한다.

### 4-4. 초기화와 복귀

- **측정 초기화:** 수치와 5초 기록만 삭제. 무기·탄약·위치는 유지한다. 이미 발사된 탄이 이후 맞으면 새 기록에 포함된다.
- **룸 초기화:** 공격·입력을 중지하고 테스트 플레이어를 파괴한 뒤 TestRoom을 다시 로드한다. 소총 한 자루·기본 스탯·시작 위치·해골 한 마리로 돌아간다. 씬 소유 풀의 탄·이펙트·데미지 숫자도 함께 제거한다.
- **로비로:** 같은 정리 후 기존 `ReturnToLobby()`를 확장·재사용한다. 일반 게임을 시작하면 로비에서 고른 무기로 새 플레이어를 생성한다.
- `GameAppManager` 자체는 유지하되 파괴된 플레이어 참조와 테스트용 상태를 남기지 않는다. `sceneLoaded` 구독 해제도 보강한다.
- 영속 `SoundManager`의 SFX 정리 메서드는 현재 없으므로 필요한 범위로 추가한다. 무기에 붙은 충전 AudioSource는 무기 비활성화·파괴 경로에서 정리한다.

## 5. 무기 획득과 교체

### 5-1. 기존 API를 그대로 연결하면 생기는 차이

현재 `WeaponController.Acquire()`는 이미 가진 무기를 **레벨업**시키고, 슬롯이 가득 차면 `NoFreeSlot`을 반환한다. 새 무기도 첫 무기를 제외하면 보유만 하고 바로 손에 들지 않는다.

테스트 픽업은 이 규칙과 다르므로 기존 보상·강화용 `Acquire()` 계약은 유지하고, 테스트 선택용 진입점과 ‘활성 슬롯 교체’ 기능을 추가한다. 아래 이름은 **신규 API 제안**이며 현재 존재하는 메서드가 아니다.

```text
SelectTestWeapon(data)
  ├─ null / 주무기 아님 / 잘못된 프리팹 → 실패 안내, 기존 상태 유지
  ├─ 현재 활성 무기와 같음 → 변경 없음
  ├─ 다른 슬롯에 이미 있음 → SwapTo(기존 슬롯)
  ├─ 빈 슬롯 있음 → Acquire(data) 성공 확인 → 새 슬롯으로 SwapTo
  └─ 4칸 모두 참 → TryReplaceActiveHeldWeapon(data)
```

예: `[소총] [기관단총*] [스나이퍼] [검]`에서 샷건 구역에 들어가면 `[소총] [샷건*] [스나이퍼] [검]`이 된다. `*`는 현재 사용 무기다. 슬롯 순서와 다른 세 무기의 상태는 유지된다.

### 5-2. 교체를 안전하게 완료하는 순서

1. `WeaponData`, `weaponPrefab`, 대응 `WeaponBase` 타입과 활성 인덱스를 검증한다.
2. 새 무기를 **발사 불가능한 상태로** 생성·초기화한다. 실패하면 새 인스턴스만 정리하고 기존 무기는 유지한다.
3. 기존 무기의 `SetActive(false)`를 호출한다. 장전·검의 지연 타격·빔 표시·충전음 정리 경로를 통과시킨다.
4. 현재 슬롯의 참조를 새 인스턴스로 바꾸고 활성화한다. 이전 무기는 제거한다. 새 무기는 Lv.1·기본 탄창으로 시작한다.
5. 상체 애니메이션 레이어, 무기 스탯, 슬롯 아이콘, 활성 테두리, 탄약 UI를 갱신한다.
6. 최종 상태가 완성된 뒤 `OnWeaponsChanged`, `OnWeaponSwapped`, `OnWeaponStatsChanged`, `OnAmmoChanged`를 기존 계약에 맞춰 통지한다. 중복 발행에 따른 효과음 중첩도 확인한다.

**같은 인덱스 교체에 주의:** 현재 `SwapTo(index)`는 인덱스가 같으면 즉시 반환한다. 참조만 교체한 뒤 `SwapTo(ActiveIndex)`를 호출하면 활성화·HUD·애니메이션 갱신이 생략될 수 있다. 교체 완료 처리를 따로 만들거나 기존 활성화 처리를 안전하게 공유해야 한다.

획득 처리는 무기 목록 순회 중에 끼어들지 않도록 한 지점에서 적용한다. 빠른 픽업·휠·`Q` 입력이 겹쳐도 그 프레임에 확정한 활성 슬롯을 기준으로 한 번만 교체한다.

이미 발사되어 날아가는 이전 무기의 탄은 일반적인 스왑처럼 남는다. 측정은 이를 포함한 표적 전체 피해로 정의하며, 현재 손에 든 무기의 피해로 잘못 분류하지 않는다.

### 5-3. 픽업 Trigger 처리

- `OnTriggerEnter`에서 **플레이어 본체의 충돌 Collider**만 받는다. `GetComponentInParent<WeaponController>()`만 확인하면 반경 10m의 자식 `EnemyDetector` Trigger도 픽업할 수 있다.
- `other.isTrigger`인 감지 센서는 제외하고, 등록된 플레이어의 본체 Collider인지 확인한다. 여러 본체 Collider를 허용하면 진입 집합으로 관리한다.
- 한 번 진입하면 해당 구역에서 계속 서 있어도 다시 획득하지 않는다. 모든 본체 Collider가 나간 뒤 재진입할 때만 다시 처리한다.
- 인접 구역의 Trigger는 겹치지 않게 배치한다. 구르기·빠른 이동 시에도 두 무기를 한 번에 선택하지 않는지 확인한다.
- 성공 시 짧게 `샷건 장착` 또는 `기관단총 → 샷건 교체`를 표시한다. 구역 자체는 제거하지 않는다.

## 6. 해골 무한 체력 표적

### 6-1. 기존 해골의 피해 경로를 재사용한다

`Assets/Prefabs/MonsterA.prefab`은 해골 모델(`Mini Simple Skeleton Armature`)과 `Enemy`, `HitFlashController`, `EnemyUI`, `EnemyEffectHandler`를 가진다. 이를 기반으로 테스트 전용 프리팹을 만든다.

**권장안: `Enemy`에 기본값이 꺼진 런타임 훈련 표적 모드와 전용 초기화 진입점을 추가한다.** 테스트 표적에서만 이 모드를 켜고, 일반 적 프리팹과 `EnemyA.asset`의 체력·공격력은 변경하지 않는다.

`Enemy.TakeDamage()`는 현재 `virtual`이 아니다. 파생 클래스에서 같은 이름의 메서드만 추가해 가로채는 설계는 사용하지 않는다. 또 한 오브젝트 계층에 `Enemy`와 별도의 `IDamageable` 구현을 동시에 두면 무기가 어느 쪽을 찾는지 불명확해지므로 피해 수신자는 기존 `Enemy` 하나로 유지한다.

### 6-2. 훈련 모드의 규칙

| 유지 | 생략 |
|---|---|
| `IDamageable.TakeDamage(DamageInfo)` 호출 | 체력 감소와 사망 판정 |
| 일반·치명타 피해 값 수신 | `Die()`, `OnDeath`, 경험치 드롭, 풀 반환 |
| 피격 플래시·데미지 숫자·치명타 데칼 | 추적·공격·상태 전이를 통한 이동 |
| 무기에서 호출하는 기존 명중 사운드 | 처치음·킬 카운트·클리어 이벤트 |
| 실제 Enemy 태그·레이어·피격 크기 | 표적 추가 자동 소환 |

- 체력은 정상적인 유한 값을 유지하고 **감소시키지 않는 방식**으로 구현한다. 큰 수로 버티거나 매 프레임 회복시키지 않는다. `Infinity / Infinity`로 체력 UI에 `NaN`이 생기는 방식도 사용하지 않는다.
- 표적 머리 위에는 `훈련용 해골 · HP: 무한`을 표시한다. 기존 체력 바는 가득 찬 상태로 표시하거나 훈련 모드에서 별도 라벨로 대체한다.
- 피해 수신 직후 `DamageInfo`를 전달하는 표적별 이벤트를 추가해 `TestRoomDummy`가 측정한다. 실제 수치 기록은 정수 데미지 팝업으로 변환하기 전에 한다.
- 피격음은 현재 무기 코드가 `SoundManager.ReportHit()`를 부른다. 표적에서도 다시 재생해 두 번 울리지 않는다.
- 치명타 데칼은 기존 이벤트를 유지하되, 훈련 모드에서 `ChangeState(Hit)`로 `EnemyBrain.HitRoutine()`에 들어가지 않는다. 해당 코루틴은 NavMesh 이동 정지와 추적으로 이어진다. 피격 모션이 필요하면 이동 상태와 분리된 짧은 연출로 처리한다.

### 6-3. 초기화·태그·물리 의존성

- 기존 `Enemy.Initialize()`는 `EnemyManager` 등록, AI 초기화, `NavMeshAgent` 활성화·Warp를 묶어서 수행한다. 고정 표적에서는 이 메서드를 그대로 호출하지 않고 훈련용 초기화에서 체력·참조·모드만 준비한다.
- `EnemyManager`에 등록하지 않고, 새 테스트 매니저가 표적 한 마리의 수명을 소유한다. 일반 스포너도 배치하지 않는다.
- `MonsterA`의 NavMeshAgent는 프리팹에서 꺼져 있다. 이 상태를 유지하고 AI의 수동 `Tick()`도 호출하지 않는다. MonoBehaviour의 `enabled = false`만으로 다른 코드의 직접 메서드 호출까지 막히지는 않는다.
- 표적 Rigidbody는 고정 상태로 유지하고 애니메이션 Root Motion으로 이동하지 않게 한다. 표적은 가까이 접근해 검을 시험할 수 있는 위치에 둔다.
- 실제 피격 Collider의 **Enemy 태그·Enemy 레이어(현재 7번)**를 유지한다. `EnemyDetector`, `Bullet`, 전격·충전 빔의 태그·레이어 필터를 모두 통과해야 한다.
- 같은 해골의 여러 Collider에 맞아도 일반 탄·검·빔은 각자의 중복 방지 규칙에 따라 한 번만 기록된다. 산탄은 탄 하나마다 별도 피해이므로 여러 번 기록되는 것이 정상이다.

## 7. 데미지 측정과 사운드 확인

### 7-1. 최소 측정 패널

| 표시 | 정의 |
|---|---|
| 현재 무기·레벨·기본 피해·발사 간격 | `WeaponController.ActiveWeapon`와 합성된 `Stats`에서 읽음 |
| 마지막 피해 | 가장 최근 수신한 `DamageInfo.damage`, 소수점 2자리 및 치명타 여부 |
| 누적 피해 | 측정 초기화 이후 표적이 받은 피해의 합 |
| 명중 수 | 유효 피해 수신 횟수. 발사 횟수나 명중률과 구분 |
| 치명타 수 | `isCritical == true`인 피해 수신 횟수 |
| 최근 5초 DPS | 최근 5초 동안 받은 피해 합계 ÷ 5초 |
| 표적 거리·감지 여부 | 수평 거리와 `EnemyDetector`의 실제 감지 상태 |

최근 5초 DPS는 첫 타격 직후에도 분모를 5초로 고정한다. 최초 5초는 창이 채워지는 구간으로 안내하고, 공격을 멈추면 기록이 빠져나가면서 0이 된다. 측정 초기화 시 시간 기록과 합계를 모두 비운다. 시간은 게임 진행 시간 기준으로 계산하며, 테스트 룸은 기본 배속 1이다.

`(time, damage)` 기록을 큐에 넣고 5초 밖의 항목을 제거하면 된다. 소수 피해를 유지하고 누적 합계는 장시간 테스트를 고려해 `double` 사용을 권장한다. UI는 일정 주기로 갱신해 산탄 명중마다 전체 텍스트를 재구성하지 않는다.

**측정은 표적이 받은 전체 피해다.** 현재 `DamageInfo`에는 발사 무기 식별자가 없다. 스왑 후 이전 총알이 맞을 수 있으므로 현재 활성 무기 이름을 명중 출처로 붙이지 않는다. 무기별 분리 통계는 추후 발사 시점의 출처를 탄·빔에 전달하는 작업으로 분리한다.

현재 `DamageTextManager.ShowDamage()`는 `int`를 받으므로 기관단총 1.33, 산탄 1.4 같은 피해가 팝업에서는 정수로 보인다. 첫 버전의 정확한 값은 측정 패널에서 확인한다. 공유 데미지 팝업까지 소수 표시로 바꾸는 작업은 별도 선택 사항이다.

### 7-2. 비교 조건

- 기본 비교는 Lv.1, 강화 없음, 같은 거리, 가득 찬 탄창에서 시작한다. 엄격한 비교 전에는 `룸 초기화`를 사용한다.
- 재진입 픽업으로 레벨·탄약을 바꾸지 않는다. 이미 가진 무기의 탄약은 보존한다.
- 기본 DPS에는 실제 치명타·장전·빗나감·충전 동작이 반영된다. 순간 피해만으로 무기의 우열을 결정하지 않는다.
- ‘무한 탄약’, ‘치명타 고정’, ‘레벨 조절’ 등은 재현 조건을 바꾸므로 첫 버전 이후 명시적인 옵션으로 추가한다.

### 7-3. 사운드

- 기존 무기 데이터와 믹서 연결을 그대로 사용한다. 테스트용 임시 발사음으로 대체하지 않는다.
- `MusicSet`에 없는 씬은 현재 음악이 꺼지는 구조다. TestRoom은 기본 무음 BGM으로 두어 효과음을 듣기 쉽게 한다. 로비 복귀 시 기존 씬별 음악 선택을 따른다.
- 발사·명중·장전 시작/완료·충전·교체·발소리를 각각 확인하고, 빠른 교체·룸 초기화·퇴장 때 잔류 소리를 확인한다.
- 특히 장전음은 현재 `SoundManager`의 공용 AudioSource 풀을 쓰므로 장전 로직 취소와 소리 중지가 항상 같지는 않다. 테스트에서 확인할 항목이며 이미 해결된 것으로 간주하지 않는다.
- 볼륨 슬라이더는 후속 기능으로 둔다. 현재 `SetSfxVolume()`은 풀 재생 볼륨을 바꾸지만 충전 레이저의 전용 AudioSource까지 동일하게 제어하지는 않는다. 믹서 그룹 경로로 통일할지 함께 검토해야 한다.

### 11-1. 무기별 첫 확인

다음 값은 현재 `WD_*.asset`의 Lv.1 기본값이다. 구현 중 밸런스가 변경되면 최신 에셋을 기준으로 다시 읽는다.

| 기관단총 | 1.33 / 0.12초 | 45 / 1.6초 | 소수 피해 보존·연사음 중첩·장시간 풀 사용 |

- [ ] 픽업 구역 안에 계속 서 있어도 획득·교체·소리가 반복되지 않는다.
- [ ] 검 지연 타격·장전·충전 중 교체와 `Q`·휠 연속 입력에서 이전 무기가 유령 공격하지 않는다.
- [ ] 해골은 어떤 피해·치명타를 받아도 죽거나 이동·공격하지 않고 경험치·킬·클리어 이벤트를 만들지 않는다.
- [ ] 기관단총 1.33, 산탄 1.4 같은 값이 측정에 그대로 누적된다. 프레임당 소리 한 번과 명중 수를 혼동하지 않는다.
- [ ] 5초 창이 채워진 뒤 DPS가 계산되고 공격 중단 5초 후 0으로 돌아온다.
- [ ] 측정 초기화는 무기 상태를 유지하고, 룸 초기화는 기본 소총·탄약·위치로 완전히 복귀한다.
- [ ] 5분 이상 연사해도 탄·데미지 숫자·피격 이펙트·오디오 오브젝트가 계속 누적되지 않는다.
- [ ] 로비와 테스트 룸을 여러 번 왕복해도 플레이어·표적·AudioListener·이벤트 소리가 중복되지 않는다.
- [ ] 테스트 룸을 나온 뒤 일반 게임에서 시작 무기·장전·강화·적 처치·다음 스테이지 진행이 정상이다.
- [ ] TestRoom 직접 Play와 빌드 실행 모두 확인한다. Console에 MissingReference·NullReference·NavMesh 오류가 없다.

### 11-3. 자동 검증을 붙인다면

슬롯 교체는 공유 전투 로직을 바꾸므로 핵심 계약을 검증할 가치가 있다. 테스트 범위는 다음에 집중한다.

- 4칸 중 활성 슬롯만 교체되며 새 프리팹 초기화 실패 시 기존 장비가 보존되는지.
- 중복 선택이 레벨업으로 이어지지 않는지, 동일 인덱스 교체 뒤 활성 상태·이벤트가 올바른지.
- 훈련 표적의 소수 피해 기록과 비사망, 일반 Enemy의 기존 사망 경로가 각각 유지되는지.
- 시간 경계가 있는 5초 DPS에서 초기화·오래된 기록 제거·무명중 구간이 올바른지.

소리의 자연스러움, 모델 위치, UI 배치, 자동 공격 감각은 Play Mode에서 직접 확인한다.

## 12. 이번 공간으로 확인할 수 있는 범위

**해골 한 마리는 단일 대상 피해·발사·장전·사운드·교체 버그를 확인하기에 적합하다.** 다만 전격 소총의 다른 적으로의 연쇄, 스나이퍼·충전 빔의 여러 적 관통, 검의 광역 효율, 다수 몬스터 성능·생존 밸런스는 이 구성만으로 검증되지 않는다.

이번에는 사용자 요청대로 한 마리만 유지한다. 후속 확장은 필요할 때 별도 항목으로 진행한다.

| 후속 기능 | 해결할 필요 |
|---|---|
| 다중 표적 모드 | 연쇄·관통·광역 비교 |
| 무기 레벨·임시 강화·치명타 옵션 | 성장 구간별 수치 재현 |
| 감지 범위·표적 거리 조절 | 감지 제한과 무기 사거리의 독립 검사 |
| 무기 출처가 포함된 피해 기록 | 교체 전 탄까지 올바른 무기로 분류 |
| 측정 결과 내보내기 | 버전별 밸런스 기록·공유 |
| 이동·공격하는 표적 | 추적·회피·플레이어 피격 사운드 검사 |

테스트 옵션을 추가하더라도 `WeaponData`·`EnemyData` 원본에 런타임 시험값을 기록하지 않는다. 무기 레벨·수치 변경은 인스턴스와 `WeaponModifier` 경로에서 처리한다.
