# 05. 무기 시스템 설계 (다중 무기 · 슬롯)

> **목적**: 무기를 여러 개 동시에 장착·성장시키는 뱀서류 핵심 구조를 설계한다.
> **범위**: `IWeapon`/`WeaponBase`/`WeaponController` 실체화, `WeaponData` SO, 타겟 제공 추상화, 투사체 계약, 업그레이드·HUD 연동.
> 이슈 번호는 [02-이슈목록.md](02-이슈목록.md)를 따른다. 이동 쪽 설계는 [04-이동확장설계.md](04-이동확장설계.md) 참조.

## ⚠ 선행 조건

| 선행 항목 | 이유 |
|---|---|
| **C-2 / C-3 / M-9** `EnemyDetector` 재작성 | 4장의 `ITargetProvider`가 **같은 파일을 다시 쓴다**. 03번 문서 1-1항(`HashSet` 전환)과 동일 작업이므로 반드시 먼저 처리할 것 |
| **M-10** `AutoAttack`/`Gun` 참조 검증 | 5장에서 `AutoAttack`의 역할이 바뀌면서 함께 정리된다 |

`EnemyDetector`가 현재 `int Count`만 노출하고 **타겟 `Transform`을 전혀 내보내지 않는다**는 점이 이 설계 전체의 병목이다. 이것을 고치지 않고 무기를 늘리면 각 무기가 자기 방식으로 적을 찾게 되어 감지 로직이 무기 수만큼 복제된다.

## 1. 현재 무기 구조와 확장 한계

### 1-1. 현재 경로

```
AutoAttack (플레이어 루트)
  ├ detector : EnemyDetector      → HasEnemy() 로 발사 여부만 판단
  ├ gun      : Gun                ← 구체 타입 단일 참조 (AutoAttack.cs:6)
  └ attackRate : float            ← 쿨다운을 AutoAttack이 소유
       ↓ timer >= attackRate
  Gun.Shoot()
    ├ PoolManager.Get(muzzleFlashPrefab)  → muzzle 위치
    ├ PoolManager.Get(bulletCasePrefab)   → bulletCase 위치
    └ PoolManager.Get(bulletPrefab)
         └ Bullet.Init(bulletSpeed, bulletDamage)
              ├ 크리티컬 자체 판정 (Bullet.cs:51 — Random.value < 0.05f)
              ├ rb.linearVelocity = transform.forward * speed   ← muzzle 방향 직진
              └ Invoke(ReturnToPool, 3f)
```

프리팹 구조 (`Assets/Prefabs/Player.prefab` 확인 결과):

```
Player (root)
 ├─ PlayerMove / PlayerStats / PlayerStatus / AutoAttack
 ├─ EnemyDetector           ← 자식 오브젝트 (트리거 콜라이더)
 └─ ... 본 계층 ...
      └─ Hand_Right
           └─ AssaultRifle  ← Gun 컴포넌트, 손 본에 직접 부착
                ├─ Muzzle
                └─ BulletCase
```

무기가 **본 계층에 하드코딩되어 있다**. 두 번째 무기를 붙일 부착점(socket)이 없다.

### 1-2. 다중 무기를 막는 5개 지점

| # | 지점 | 문제 |
|---|---|---|
| 1 | `AutoAttack.cs:6` — `public Gun gun;` | 구체 타입 단일 참조. 무기 배열로 바꿔도 `Gun` 이외의 무기는 못 들어옴 |
| 2 | `AutoAttack.cs:8` — `attackRate` | **쿨다운을 무기가 아닌 발사기가 소유**. 무기마다 발사 주기가 다른 뱀서 구조와 정면 충돌 |
| 3 | `Gun.cs:11-12` — `bulletSpeed`/`bulletDamage` 컴포넌트 필드 | 무기별 데이터 분리 불가. `AddDamage`가 필드를 **직접 증가**시켜 기본값과 업그레이드 누적분이 뒤섞임 |
| 4 | `Bullet.cs:8-10` — `critChance`/`critMultiplier` private 상수 | 무기별 크리티컬 차등 불가. `[SerializeField]`도 아니라 인스펙터 조정조차 안 됨 (**M-8**) |
| 5 | `EnemyDetector` — `Count`만 노출 | 유도·최근접 조준·다중 타겟 무기 전부 불가 |

### 1-3. 이름만 있는 추상화 (L-1, L-2)

```csharp
// Player/IWeapon.cs — 실제 내용
public class IWeapon : MonoBehaviour   // ← interface가 아니라 빈 MonoBehaviour
{
    void Start() { }
    void Update() { }
}
```

`WeaponBase.cs`, `WeaponController.cs`도 동일한 빈 Unity 템플릿이다. 세 파일 모두 **이 설계를 의도했던 흔적**이지만 내용이 없어 지금은 혼란만 준다. 이 문서는 그 셋을 채우는 것을 목표로 한다.

## 2. 계층 설계

```
PlayerAim (04번 문서) ──── AimDirection
        │
        ▼
WeaponController  (플레이어 루트, 슬롯 소유·구동)
   │  ├ ITargetProvider (= EnemyDetector)
   │  └ IReadOnlyList<IWeapon> weapons   ← 슬롯
   │
   ├── WeaponBase : MonoBehaviour, IWeapon   (추상 — 쿨다운·스탯합성·이펙트 공통)
   │     ├── ProjectileWeapon                 ← Gun 이관
   │     ├── ShotgunWeapon                    ← projectileCount + spread
   │     └── OrbitWeapon                      ← 투사체 없는 무기 (계약 검증용)
   │
   └── WeaponData : ScriptableObject          (밸런싱 데이터)
```

**`OrbitWeapon`을 예시에 넣은 이유**: 뱀서류에는 플레이어 주위를 도는 무기, 장판, 오라처럼 **투사체를 발사하지 않는** 무기가 반드시 나온다. `IWeapon` 계약이 "발사"에 너무 특화되면 이런 무기가 들어올 수 없다. 설계 단계에서 한 번 대입해보고 계약을 검증하는 용도다.

## 3. 핵심 타입 시그니처

### 3-1. `IWeapon` — 진짜 인터페이스로

```csharp
public interface IWeapon
{
    WeaponData Data { get; }
    int Level { get; }
    WeaponRuntimeStats Stats { get; }   // Data + 누적 Modifier 합성 결과

    bool CanFire { get; }               // 쿨다운 완료 여부
    void Tick(float deltaTime);         // 쿨다운 진행 (매 프레임)
    void Fire(WeaponFireContext ctx);   // 실제 발사

    void ApplyModifier(in WeaponModifier mod);
    void SetLevel(int level);
}
```

`Tick`과 `Fire`를 분리한 이유: `WeaponController`가 "쿨다운이 돈 무기만 발사"를 판정하려면 쿨다운 진행과 발사 시점이 분리되어야 한다. 현재 `AutoAttack.Update`(`:31-37`)는 이 둘이 붙어 있어 무기가 여러 개면 성립하지 않는다.

### 3-2. `WeaponFireContext`

무기가 발사에 필요한 것을 한 번에 받는다. 무기마다 `GetComponent`를 반복하지 않게 하는 것이 목적이다 (04번 문서의 `PlayerMoveContext`와 같은 발상).

```csharp
public readonly struct WeaponFireContext
{
    public readonly ITargetProvider Targets;
    public readonly Vector3 Origin;        // 플레이어 위치
    public readonly Vector3 AimDirection;  // PlayerAim에서 (y=0, 정규화)
    public readonly bool HasValidAim;
}
```

### 3-3. `WeaponData : ScriptableObject`

프로젝트에 이미 `EnemyData`, `StageData`, `UpgradeData` SO 패턴이 있으므로 동일하게 간다. 02번 문서가 지적한 "스탯이 프리팹 여러 컴포넌트에 흩어져 밸런싱이 어렵다"도 여기서 해소된다.

```csharp
[CreateAssetMenu(menuName = "Weapon/Data")]
public class WeaponData : ScriptableObject
{
    [Header("Identity")]
    public string weaponName;
    public string description;
    public Sprite icon;
    public GameObject weaponPrefab;      // WeaponBase 파생 컴포넌트를 가진 프리팹
    public WeaponSocket socket;          // 부착 위치 (enum: RightHand / LeftHand / Back / Root)

    [Header("Fire")]
    public float fireInterval = 0.5f;    // 초당 발사수가 아니라 '간격' — 기존 attackRate와 동일 의미
    public float damage = 10f;
    public int projectileCount = 1;
    public float spreadAngle = 0f;

    [Header("Critical")]
    [Range(0f, 1f)] public float critChance = 0.05f;
    public float critMultiplier = 2f;

    [Header("Projectile")]
    public GameObject projectilePrefab;
    public float projectileSpeed = 20f;
    public float projectileLifeTime = 3f;
    public int pierceCount = 0;

    [Header("Effects")]
    public GameObject muzzleFlashPrefab;
    public GameObject casingPrefab;

    [Header("Growth")]
    public int maxLevel = 5;
    public WeaponModifier perLevelBonus;  // 레벨업 시 누적되는 증분
}
```

기본값은 현재 코드의 값을 그대로 옮긴 것이다 — `fireInterval = 0.5f`(`AutoAttack.cs:8`), `damage = 10f` / `projectileSpeed = 20f`(`Gun.cs:11-12`), `critChance = 0.05f` / `critMultiplier = 2f`(`Bullet.cs:9-10`), `projectileLifeTime = 3f`(`Bullet.cs:17`). 이관 직후 밸런스가 그대로 유지된다.

### 3-4. `WeaponModifier` — 업그레이드 증분

```csharp
[System.Serializable]
public struct WeaponModifier
{
    public float damageAdd;
    public float damageMul;          // 기본값 주의: 0이 아니라 1이 항등원
    public float fireIntervalMul;    // 작아질수록 빨라짐. 항등원 1
    public float projectileSpeedAdd;
    public int   projectileCountAdd;
    public float critChanceAdd;
    public float critMultiplierAdd;
    public int   pierceAdd;

    public static WeaponModifier Identity => new() { damageMul = 1f, fireIntervalMul = 1f };
    public static WeaponModifier Combine(in WeaponModifier a, in WeaponModifier b);
}
```

> **⚠ 곱셈 필드의 항등원 함정**: `struct`의 기본값은 모든 필드가 0이다. `damageMul`을 초기화하지 않으면 데미지가 0이 된다. `Identity`를 반드시 거치게 하고, 인스펙터에서 만든 `WeaponModifier` 필드는 `[SerializeField]` 기본값을 1로 세팅해야 한다. `perLevelBonus`처럼 인스펙터에서 직접 채우는 필드가 특히 위험하다.

### 3-5. `WeaponRuntimeStats` — 합성 결과

```csharp
public readonly struct WeaponRuntimeStats
{
    public readonly float Damage;
    public readonly float FireInterval;
    public readonly float ProjectileSpeed;
    public readonly int   ProjectileCount;
    public readonly float SpreadAngle;
    public readonly float CritChance;
    public readonly float CritMultiplier;
    public readonly int   PierceCount;

    public static WeaponRuntimeStats Compose(WeaponData data, in WeaponModifier mod);
}
```

> **⚠⚠ SO 원본을 절대 수정하지 말 것**
>
> 현재 `Gun.AddDamage`(`Gun.cs:49-53`)는 `bulletDamage` 필드를 직접 증가시킨다. `Gun`이 **프리팹 인스턴스의 컴포넌트**라서 지금은 안전하다 — 플레이 종료 시 인스턴스가 사라진다.
>
> 그러나 데이터를 `WeaponData` SO로 옮긴 뒤 같은 방식으로 SO 필드를 증가시키면, **에디터에서 그 변경이 에셋에 영구 기록된다.** 플레이할 때마다 데미지가 누적되고 원본 밸런스를 잃는다. Unity 초보자가 SO를 도입할 때 가장 흔히 겪는 사고다.
>
> 그래서 `WeaponData`는 **읽기 전용 기본값 소스**, 누적분은 `WeaponBase`가 들고 있는 `WeaponModifier`, 실제 사용값은 매번 `Compose`한 `WeaponRuntimeStats` — 이 3층 구조를 지킨다.

### 3-6. `WeaponBase` — 공통 구현

```csharp
public abstract class WeaponBase : MonoBehaviour, IWeapon
{
    [SerializeField] protected WeaponData data;
    [SerializeField] protected Transform muzzle;
    [SerializeField] protected Transform casingPoint;

    WeaponModifier accumulated = WeaponModifier.Identity;
    float cooldownTimer;

    public WeaponData Data => data;
    public int Level { get; private set; } = 1;
    public WeaponRuntimeStats Stats => WeaponRuntimeStats.Compose(data, accumulated);
    public bool CanFire => cooldownTimer <= 0f;

    public void Tick(float dt) { if (cooldownTimer > 0f) cooldownTimer -= dt; }

    public void Fire(WeaponFireContext ctx)
    {
        var stats = Stats;
        OnFire(in stats, in ctx);
        cooldownTimer = stats.FireInterval;
        RaiseStatsChanged();
    }

    public void ApplyModifier(in WeaponModifier mod)
    {
        accumulated = WeaponModifier.Combine(accumulated, mod);
        RaiseStatsChanged();
    }

    protected abstract void OnFire(in WeaponRuntimeStats stats, in WeaponFireContext ctx);

    // 공통 헬퍼 — 현재 Gun.SpawnMuzzleFlash / SpawnBulletCase 이관
    protected void SpawnMuzzleFlash();
    protected void SpawnCasing();
    protected bool RollCritical(in WeaponRuntimeStats stats);
}
```

`RollCritical`을 여기 두는 것이 **M-8 해결의 핵심**이다. 크리티컬 판정 주체가 `Bullet`에서 무기로 올라오면 무기별 차등이 가능해지고, 투사체가 없는 무기(`OrbitWeapon`)도 같은 규칙을 쓸 수 있다.

### 3-7. `WeaponController` — 슬롯 소유·구동

```csharp
public class WeaponController : MonoBehaviour
{
    [SerializeField] int maxSlots = 6;
    [SerializeField] WeaponData starterWeapon;
    [SerializeField] EnemyDetector detector;       // ITargetProvider
    [SerializeField] PlayerAim aim;
    [SerializeField] SocketTable sockets;          // WeaponSocket → Transform 매핑

    readonly List<WeaponBase> weapons = new();
    public IReadOnlyList<IWeapon> Weapons => weapons;
    public bool HasFreeSlot => weapons.Count < maxSlots;

    public bool TryEquip(WeaponData data);         // 빈 슬롯에 새 무기 장착
    public bool TryLevelUp(WeaponData data);       // 이미 보유 시 레벨업
    public bool Has(WeaponData data);
    public IWeapon Find(WeaponData data);
    public void ApplyGlobalModifier(in WeaponModifier mod);   // 전체 무기에 적용

    void Update()
    {
        // 사망 시 조기 반환
        for (int i = 0; i < weapons.Count; i++)
        {
            weapons[i].Tick(Time.deltaTime);
            if (!weapons[i].CanFire) continue;
            if (!ShouldFire(weapons[i])) continue;
            weapons[i].Fire(BuildContext());
        }
    }
}
```

**무기별 독립 쿨다운**이 `Tick`/`CanFire`로 자연스럽게 나온다. 이것이 현재 `AutoAttack`의 단일 `attackRate`(1-2의 #2)를 대체한다.

`SocketTable`은 `WeaponSocket` enum → 부착 `Transform` 매핑이다. 현재 무기가 `Hand_Right` 본에 하드코딩되어 있으므로(1-1), 슬롯을 늘리려면 부착점을 데이터로 빼야 한다.

## 4. 타겟 제공 추상화 — `ITargetProvider`

### 4-1. 인터페이스

```csharp
public interface ITargetProvider
{
    bool HasTarget { get; }
    int  Count { get; }

    Transform GetNearest(Vector3 from);
    int GetTargets(Vector3 from, int max, List<Transform> buffer);  // 거리순, buffer 재사용
}
```

`GetTargets`가 `List<Transform>`을 **인자로 받아 채우는** 형태인 이유: 자동공격은 매 프레임 여러 무기가 호출한다. 매번 새 리스트를 반환하면 GC 압력이 생긴다. 이 프로젝트는 총알·이펙트·탄피를 전부 풀링할 만큼 할당에 신경 쓰고 있으므로(01번 문서 5장), 여기서 리스트를 새로 만드는 건 일관성에 어긋난다. 호출자(`WeaponBase`)가 필드로 버퍼를 하나 들고 재사용한다.

### 4-2. `EnemyDetector` 재작성 — 4개 이슈 동시 해결

현재 `int Count` 증감 방식은 enter / exit / 사망 콜백 **세 경로가 서로를 모르는 채** 증감해 C-2(보스 exit 누락)와 C-3(사망 시 이중 감소)을 만든다. 집합으로 바꾸면 전부 사라진다.

```csharp
public class EnemyDetector : MonoBehaviour, ITargetProvider
{
    readonly HashSet<Transform> targets = new();
    readonly List<Transform> scratch = new();   // 정리·정렬용 재사용 버퍼

    public event Action<bool> OnEnemyEnter;     // 기존 계약 유지

    void OnTriggerEnter(Collider other) { /* Enemy/Boss 구분 없이 Add */ }
    void OnTriggerExit(Collider other)  { /* Remove */ }
    // 사망 콜백도 같은 Remove 경로

    public bool HasTarget => Count > 0;
    public bool HasEnemy() => HasTarget;        // 기존 호출부 호환
}
```

| 이슈 | 해결 방식 |
|---|---|
| **C-2** 보스 exit 누락 | Enemy/Boss 태그 분기를 없애고 **한 경로**로 Add/Remove. 분기가 없으면 누락도 없다 |
| **C-3-A** 사망 시 이중 감소 | `HashSet.Remove`는 이미 없는 항목에 대해 조용히 `false`. 사망 콜백과 `OnTriggerExit`이 겹쳐도 무해 |
| **C-3-B** 애니메이션 고착 | 집합 크기가 1→0이 되는 지점을 **한 곳**에서 판정해 `OnEnemyEnter(false)` 발행 |
| **M-9** `GetComponent<Enemy>()` 무검증 | `Enemy`가 없으면 사망 구독만 건너뛰고 집합에는 추가 (또는 추가하지 않음). 어느 쪽이든 NRE는 안 남 |

**추가 방어 — 파괴/풀 반환된 대상**: 적이 풀로 반환되면 `OnTriggerExit`이 오지 않을 수 있다. 조회 시 Unity의 fake null을 걸러내야 한다.

```csharp
// ⚠ HashSet 순회 중 Remove는 예외를 던진다. scratch에 모았다가 일괄 제거할 것.
void Prune()
{
    scratch.Clear();
    foreach (var t in targets)
        if (t == null || !t.gameObject.activeInHierarchy)   // == 는 Unity 오버로드를 거침
            scratch.Add(t);

    foreach (var t in scratch) targets.Remove(t);
}
```

> `t == null`은 쓰되 **`t?.` 는 쓰지 말 것.** C#의 null 조건 연산자는 Unity가 오버로드한 `==`를 우회해 파괴된 객체(fake null)를 걸러내지 못한다. 02번 문서 H-2가 정확히 이 함정에 걸린 사례다.

### 4-3. 타겟 선택 전략 (선택 사항)

무기가 늘면 "어떤 적을 노릴지"가 무기 특성이 된다. `WeaponData`에 enum 하나를 추가하는 것으로 충분하다.

| 전략 | 용도 |
|---|---|
| `Nearest` | 기본. 최근접 |
| `AimDirection` | 조준 방향에 가장 가까운 적 — 플레이어 의도 반영 |
| `Random` | 산탄·다중 타겟 |
| `LowestHp` | 마무리 특화 무기 |

1차 구현에서는 `Nearest`만 있어도 된다. **`WeaponData`에 필드 자리만 잡아두면** 나중에 무기를 추가할 때 계약을 바꾸지 않아도 된다.

## 5. `AutoAttack`의 역할 재정의

`AutoAttack`은 현재 감지 게이트 + 쿨다운 + 발사를 전부 한다. `WeaponController`가 쿨다운과 발사를 가져가면 남는 건 "적이 있을 때만 쏜다"는 게이트뿐이다.

| 안 | 내용 | 장점 | 단점 |
|---|---|---|---|
| **A. `WeaponController`에 흡수** | `AutoAttack` 삭제, 게이트 판정을 `ShouldFire`로 내재화 | 파일 감소, 발사 경로가 한 곳 | 게이트 정책을 무기별로 다르게 하기 어려움 |
| **B. 게이트만 남김** | `AutoAttack`이 `bool IsCombatActive`만 노출, `WeaponController`가 참조 | 전투 활성/비활성 개념이 명시적 | 얇은 클래스가 하나 더 남음 |

**A를 권장한다.** 이유:

1. 무기마다 발사 조건이 다르다. `OrbitWeapon`은 적이 없어도 계속 돌아야 하고, 장판은 적 유무와 무관하다. "적이 있을 때만"을 **전역 게이트**로 두면 이런 무기가 들어올 수 없다.
2. 조건 판정을 `WeaponData` 쪽으로 내리는 편이 확장에 유리하다:

```csharp
bool ShouldFire(IWeapon w)
{
    if (isDead) return false;
    return w.Data.requiresTarget ? detector.HasTarget : true;
}
```

3. `AutoAttack`의 `GameEvents.OnPlayerDeadStart` 구독(`AutoAttack.cs:14-24`)은 `WeaponController`가 그대로 이어받으면 된다.

> **⚠ 삭제 전 확인**: `AutoAttack`은 `Player.prefab`의 루트 컴포넌트이고 인스펙터에서 `detector`/`gun`이 할당되어 있다. 삭제하면 그 참조가 사라지므로, `WeaponController`를 먼저 붙여 동작을 확인한 뒤 제거할 것.
>
> 또한 `PlayerMove.OnEnemyEntered`(`PlayerMove.cs:163-166`)가 `detector.OnEnemyEnter`를 구독해 `isAttack` 애니메이션을 켠다. 이 경로는 `AutoAttack`과 무관하므로 **그대로 유지**된다.

## 6. 투사체 계약 재설계

### 6-1. `ProjectileSpawnInfo`

현재 `Bullet.Init(float, float)`은 인자가 2개뿐이라 관통·유도·무기별 크리티컬을 넣을 자리가 없다. 인자를 늘리는 대신 struct로 묶는다.

```csharp
public readonly struct ProjectileSpawnInfo
{
    public readonly float Speed;
    public readonly float Damage;
    public readonly float LifeTime;
    public readonly bool  IsCritical;      // ← 무기가 판정한 결과를 전달 (M-8)
    public readonly int   PierceCount;
    public readonly Transform HomingTarget; // null 가능
}
```

```csharp
public void Init(in ProjectileSpawnInfo info);
```

### 6-2. `Bullet` 변경점

| 항목 | 현재 | 변경 |
|---|---|---|
| 크리티컬 판정 | `Bullet.Init`에서 `Random.value < critChance` (`:51`) | **삭제**. `info.IsCritical`을 그대로 사용 |
| `critChance`/`critMultiplier` 필드 | private 상수 (`:9-10`) | **삭제**. `WeaponData`로 이관 |
| `lifeTime` | public 필드 3f (`:17`) | `info.LifeTime` 사용 |
| 관통 | 없음 — 첫 충돌에 무조건 반환 (`:83`) | `PierceCount` 소진 전까지 유지, 맞은 대상 중복 방지용 집합 필요 |
| 지형 충돌 | Enemy/Boss 태그만 처리 (`:64`) | **벽/지형 레이어 충돌 시 이펙트 없이 반환** (M-7) |
| `ApplyDamageVisual` | `MaterialPropertyBlock` 사용 (`:112-139`) | **그대로 유지** — 머티리얼 인스턴싱 회피는 현행 장점 |
| `SpawnHitEffect` | Boss/일반 분기 (`:87-110`) | 그대로 유지 |

> **관통 구현 시 주의**: 하나의 큰 콜라이더를 관통할 때 `OnTriggerEnter`가 여러 번 불릴 수 있고, 자식 콜라이더를 가진 적은 한 마리인데도 중복 히트가 난다. 이미 맞힌 대상을 `HashSet<Collider>` 또는 루트 `Transform` 기준으로 기록하고, `OnDespawn`에서 반드시 비울 것. 비우지 않으면 풀에서 재사용될 때 **적을 못 맞히는** 버그가 된다.

### 6-3. `ProjectileWeapon` (기존 `Gun` 이관)

```csharp
public class ProjectileWeapon : WeaponBase
{
    protected override void OnFire(in WeaponRuntimeStats stats, in WeaponFireContext ctx)
    {
        SpawnMuzzleFlash();
        SpawnCasing();

        Vector3 baseDir = ResolveFireDirection(in ctx);   // 타겟 방향 또는 muzzle.forward

        for (int i = 0; i < stats.ProjectileCount; i++)
        {
            Vector3 dir = ApplySpread(baseDir, stats.SpreadAngle, i, stats.ProjectileCount);

            var obj = PoolManager.Instance.Get(data.projectilePrefab);
            obj.transform.SetPositionAndRotation(muzzle.position, Quaternion.LookRotation(dir));

            obj.GetComponent<Bullet>().Init(new ProjectileSpawnInfo(
                stats.ProjectileSpeed,
                stats.Damage,
                data.projectileLifeTime,
                RollCritical(in stats),      // ← 무기가 판정
                stats.PierceCount,
                null));
        }
    }
}
```

`ShotgunWeapon`은 별도 클래스가 필요 없다 — `WeaponData`에서 `projectileCount = 5`, `spreadAngle = 30f`로 설정한 **에셋만 만들면** 된다. 데이터로 표현되는 것은 클래스로 만들지 않는 편이 낫다.

> **⚠ `PoolConfig` 등록 필수**: 새 투사체 프리팹은 씬의 `PoolManager.configs`에 등록해야 한다. 등록하지 않아도 `PoolManager.Get`이 경고 로그와 함께 기본 풀(size 5, expandable)을 만들어주지만(`PoolManager.cs:40-45`), 초기 확장 때 프레임 스파이크가 생긴다.

## 7. 업그레이드 파이프라인 연동

### 7-1. 현재 구조

```csharp
// Upgrade/Effects/DamageUpgrade.cs
Gun gun = player.GetComponentInChildren<Gun>();   // ← 구체 타입 직접 탐색
if (gun != null) gun.AddDamage(amount);
```

`GunSpeedUp`도 동일하다. 무기가 여러 개면 `GetComponentInChildren`은 **첫 번째 무기만** 찾는다.

### 7-2. 신규 `UpgradeEffect` 3종

`UpgradeEffect`는 이미 `abstract ScriptableObject`이므로 매니저 수정 없이 추가된다 (01번 문서 5장이 평가한 장점).

```csharp
// (1) 전체 무기에 적용 — 기존 DamageUpgrade / GunSpeedUp 대체
[CreateAssetMenu(menuName = "Upgrade/Effects/WeaponModifier")]
public class WeaponModifierUpgrade : UpgradeEffect
{
    public WeaponModifier modifier = WeaponModifier.Identity;   // ⚠ 항등원 초기화

    public override void Apply(GameObject player)
        => player.GetComponent<WeaponController>()?.ApplyGlobalModifier(modifier);
}

// (2) 특정 무기 레벨업
[CreateAssetMenu(menuName = "Upgrade/Effects/WeaponLevelUp")]
public class WeaponLevelUpUpgrade : UpgradeEffect
{
    public WeaponData target;
    public override void Apply(GameObject player)
        => player.GetComponent<WeaponController>()?.TryLevelUp(target);
}

// (3) 새 무기 획득
[CreateAssetMenu(menuName = "Upgrade/Effects/EquipWeapon")]
public class EquipWeaponUpgrade : UpgradeEffect
{
    public WeaponData weapon;
    public override void Apply(GameObject player)
        => player.GetComponent<WeaponController>()?.TryEquip(weapon);
}
```

> `?.`를 여기서 쓰는 것은 안전하다. `GetComponent`는 파괴된 객체를 반환하지 않으므로 fake null 문제가 없다. (4-2에서 경고한 것은 **보관해둔 참조**를 나중에 검사하는 경우다.)

### 7-3. ⚠ 카드 선택 로직의 구멍

무기 획득 카드를 넣으면 `UpgradeManager.GetRandomUpgrades`(`UpgradeManager.cs:49-62`)의 기존 문제가 **실제로 터진다**.

```csharp
public List<UpgradeData> GetRandomUpgrades(int count)
{
    List<UpgradeData> pool = new(upgradePool);
    for (int i = 0; i < count; i++)
    {
        int index = Random.Range(0, pool.Count);   // pool이 비면 Random.Range(0,0) → 0
        result.Add(pool[index]);                   // → IndexOutOfRangeException
        pool.RemoveAt(index);
    }
}
```

- `count > upgradePool.Count`이면 **예외**. 지금은 풀이 5종이라 우연히 안 터지지만, "이미 보유한 무기 카드 제외" 같은 필터를 넣는 순간 풀이 줄어 즉시 재현된다.
- 슬롯이 가득 찼는데 `EquipWeaponUpgrade`가 나오면 **선택해도 아무 일도 일어나지 않고 EXP만 소모된다**. `TryEquip`이 `false`를 반환해도 `UpgradeManager.TryUpgrade`(`:42-46`)는 이미 `SpendExp`를 한 뒤이고 `OnUpgradeSuccess`까지 발행한다.

**대응 방향**:

1. `UpgradeData`에 `bool IsAvailable(GameObject player)` 판정 경로를 추가하고, `GetRandomUpgrades`가 후보를 먼저 걸러낸다.
2. 걸러낸 뒤 `count = Mathf.Min(count, pool.Count)`로 클램프한다.
3. `UpgradeEffect.Apply`가 `bool`을 반환하도록 바꿔, 실패 시 `SpendExp`를 되돌리거나 애초에 소모하지 않는다.

> 3번은 `UpgradeEffect` 시그니처 변경이므로 기존 5개 효과 전부에 영향을 준다. 무기 카드를 넣기 **전에** 처리하는 것이 싸다.

### 7-4. 기존 효과 이관

| 파일 | 조치 |
|---|---|
| `DamageUpgrade.cs` | `WeaponModifierUpgrade`(damageAdd)로 대체 후 삭제 |
| `GunSpeedUp.cs` | `WeaponModifierUpgrade`(projectileSpeedAdd)로 대체 후 삭제. 오타 `aomunt`(`Gun.cs:55`)도 함께 소멸 (L-8) |
| `SpeedUpgrade.cs` | 이동 속도이므로 **유지**. `Debug.Log` 3개만 제거 (L-9) |
| `ExpandHP.cs` / `Heal.cs` | 무기와 무관, 그대로 유지 |

**기존 `UpgradeData` 에셋의 `effect` 참조를 새 SO로 다시 연결해야 한다.** 에셋 파일이므로 코드만 바꾸면 참조가 끊긴다.

### 7-5. 크리티컬 업그레이드 (M-8 완결)

`critChance`/`critMultiplier`가 `WeaponData` → `WeaponModifier` 경로에 올라오면, 새 클래스 없이 **에셋만 만들어** 크리티컬 업그레이드가 생긴다.

```
UpgradeData "치명타 확률 +5%"  → WeaponModifierUpgrade { critChanceAdd = 0.05f, damageMul = 1f, fireIntervalMul = 1f }
UpgradeData "치명타 피해 +50%" → WeaponModifierUpgrade { critMultiplierAdd = 0.5f, damageMul = 1f, fireIntervalMul = 1f }
```

현재 업그레이드 풀이 5종뿐이라(공격력/탄속/이동속도/최대HP/회복) 선택지 확보 효과도 크다.

## 8. HUD / 이벤트 계약 마이그레이션

### 8-1. 현재 계약은 단일 무기 전제

| 이벤트 | 발행 | 구독 |
|---|---|---|
| `OnBulletDamageChanged(float)` | `Gun.cs:16`, `:52` | `PlayerStatsUI.UpdateBulletDamage` |
| `OnBulletSpeedChanged(float)` | `Gun.cs:58` | `PlayerStatsUI.UpdateBulletSpeed` |

`float` 하나만 실어 보내므로 "어느 무기의 값인지" 구분이 없다. 여기에 더해 `PlayerStatsUI.SetPlayer`(`:71-76`)가 `t.GetComponentInChildren<Gun>()`으로 **초기값을 직접 읽는다**. 무기가 여러 개면 첫 번째 것만 잡힌다.

> `Gun.Start()`는 `OnBulletDamageChanged`만 발행하고 `OnBulletSpeedChanged`는 발행하지 않는다. 초기 탄속 표시는 위의 직접 읽기가 우연히 메꾸고 있다 (01번 문서 3장). 즉 **현재 HUD는 이 우회 경로에 의존**하고 있으므로, 무기 리팩터링 시 함께 끊어진다.

### 8-2. 신규 계약

```csharp
// GameEvents

public static Action<IWeapon> OnWeaponStatsChanged;  // 레벨업·모디파이어 적용
```

### 8-3. 2단계 전환 — HUD를 깨뜨리지 않기

무기 구조와 HUD를 동시에 바꾸면 어디가 깨졌는지 알 수 없다. 나눈다.

**1차 — 기존 HUD 유지**

`WeaponController`가 **슬롯 0(주무기)** 기준으로 기존 이벤트를 계속 발행한다.

```csharp
void RaiseLegacyStats()
{
    if (weapons.Count == 0) return;
    var s = weapons[0].Stats;
    GameEvents.OnBulletDamageChanged?.Invoke(s.Damage);
    GameEvents.OnBulletSpeedChanged?.Invoke(s.ProjectileSpeed);   // 초기 발행 누락도 이때 해결
}
```

`PlayerStatsUI`는 **한 줄도 바꾸지 않는다.** 단, `SetPlayer`의 `GetComponentInChildren<Gun>()` 직접 읽기(`:71-76`)만 제거하고 `RaiseLegacyStats` 발행에 의존하도록 바꾼다.

**2차 — 슬롯 UI**

무기 아이콘 + 레벨을 표시하는 슬롯 UI를 만들고 신규 이벤트로 갈아탄 뒤, 레거시 이벤트와 `bulletDamageText`/`bulletSpeedText`를 제거한다.

> **H-3 주의**: `PlayerStatsUI`는 `OnPlayerSpawned`마다 `stats.OnHpChanged +=` 를 **해제 없이** 추가한다. 무기 슬롯 UI를 새로 만들 때 같은 패턴(스폰 이벤트로 참조 재연결)을 쓸 텐데, 인스턴스 이벤트를 구독한다면 **반드시 해제를 짝지을 것.** 03번 문서 2-3항 참조.

## 9. 마이그레이션 단계

### 9-1. 순서

| 단계 | 작업 | 씬/프리팹 작업 | 되돌리기 난이도 |
|---|---|---|---|
| 0 | **`EnemyDetector` 집합 기반 재작성 + `ITargetProvider`** (4장) | 없음 | 낮음 — 외부 계약 유지 |
| 1 | `WeaponData` / `WeaponModifier` / `WeaponRuntimeStats` 타입 추가 | 없음 (코드만) | 낮음 |
| 2 | `IWeapon` **인터페이스로 재작성**, `WeaponBase` 구현 (L-1, L-2) | 없음 | 낮음 |
| 3 | `Gun` → `ProjectileWeapon` 이관, `AssaultRifle`용 `WeaponData` 에셋 생성 | **프리팹 컴포넌트 교체 + muzzle/casing 재할당** | 중간 |
| 4 | `Bullet.Init(in ProjectileSpawnInfo)` 전환, 크리티컬 이관 (M-8) | 없음 | 중간 |
| 5 | `WeaponController` 도입, `AutoAttack` 흡수 (5장) | **프리팹 컴포넌트 추가/제거, 소켓 Transform 할당** | **높음** |
| 6 | 레거시 이벤트 발행을 `WeaponController`로 이관 (8-3 1차) | 없음 | 낮음 |
| 7 | 업그레이드 SO 3종 추가, 기존 `UpgradeData` 에셋 재연결 (7장) | **에셋 참조 재할당** | 중간 |
| 8 | `GetRandomUpgrades` 필터·클램프 수정 (7-3) | 없음 | 낮음 |
| 9 | 두 번째 무기 `WeaponData` + 프리팹 + `PoolConfig` 등록 | **씬 PoolManager 편집** | 낮음 |
| 10 | 슬롯 HUD (8-3 2차) | UI 신규 | 중간 |

**0번이 가장 먼저인 이유**: 외부 계약(`HasEnemy()`, `OnEnemyEnter`)을 유지한 채 내부만 바꾸므로 `AutoAttack`/`PlayerMove`를 건드리지 않는다. 단독 검증이 가능하고, C-2/C-3라는 실제 버그도 함께 잡힌다.

**3~5번 사이에 반드시 플레이 검증**을 끼울 것. 3번까지는 무기가 여전히 1개라 기존과 동일하게 동작해야 한다. 여기서 어긋나면 4·5번으로 가기 전에 잡는 편이 훨씬 싸다.

### 9-2. `Player.prefab` 영향 체크리스트

| 대상 | 조치 |
|---|---|
| 루트: `AutoAttack` | `WeaponController` 추가 후 동작 확인 → 제거 (5장 경고 참조) |
| 루트: `WeaponController` | 신규. `maxSlots`, `starterWeapon`, `detector`, `aim`, `sockets` 할당 |
| `Hand_Right/AssaultRifle`: `Gun` | `ProjectileWeapon`으로 교체. `data` / `muzzle` / `casingPoint` 재할당 |
| `AssaultRifle` 자체 | 무기 프리팹으로 분리 → `WeaponData.weaponPrefab`이 참조. 본에서 떼어내고 런타임 부착으로 전환 |
| 소켓 Transform | `Hand_Right` 외 부착점(`Hand_Left`, `Back` 등)을 본 계층에서 지정하거나 빈 오브젝트로 신설 |
| 씬 `PoolManager.configs` | 신규 투사체·이펙트 프리팹 등록 |
| `UpgradeData` 에셋들 | `effect` 참조를 새 SO로 재연결 |

### 9-3. 플레이 검증 항목

1. **기본 회귀** — 무기 1개 상태에서 데미지·발사속도·크리티컬 빈도가 이관 전과 같은가 (3-3의 기본값이 기존 값과 일치하는지 대조)
2. **보스 감지** — 보스에게 접근 후 멀어졌을 때 자동공격이 **멈추는가** (C-2 검증)
3. **적 사망 카운트** — 감지 범위 안에서 적을 죽였을 때 남은 적에게 계속 사격하는가 (C-3-A 검증)
4. **애니메이션 복구** — 범위 안 마지막 적이 죽으면 `isAttack`이 꺼지는가 (C-3-B 검증)
5. **무기 2개 동시** — 서로 다른 `fireInterval`을 가진 무기 2개가 각자 주기로 발사되는가
6. **업그레이드 누적** — 데미지 업그레이드를 3회 획득했을 때 값이 정확히 누적되는가, **에디터 정지 후 `WeaponData` 에셋 값이 원래대로인가** (3-5 경고 검증)
7. **슬롯 만석** — `maxSlots`를 채운 뒤 무기 획득 카드가 나오지 않는가 (7-3 검증)
8. **HUD** — 스테이지 전환 후 데미지/탄속 표시가 정확한가 (8-3 1차 검증)
9. **풀 재사용** — 관통 무기를 만들었다면, 같은 총알이 재사용됐을 때 적을 정상적으로 맞히는가 (6-2 경고 검증)

## 10. 이 설계가 열어두는 확장

| 확장 | 구현 방법 |
|---|---|
| 산탄총 | `WeaponData` 에셋만 생성 (`projectileCount`, `spreadAngle`) — **코드 0줄** |
| 관통탄 | `WeaponData.pierceCount` + `Bullet` 관통 처리 (6-2) |
| 유도탄 | `ProjectileSpawnInfo.HomingTarget` 채우기 + `Bullet`에 추적 로직 |
| 궤도 무기 / 오라 / 장판 | `WeaponBase` 파생 + `requiresTarget = false` (6-4) |
| 무기 진화 (뱀서식 합성) | `WeaponData`에 `evolvesInto` + 조건 추가, `WeaponController.TryEquip`에서 판정 |
| 무기별 타겟 전략 | `WeaponData`에 전략 enum (4-3) |
| 근접 무기 | `WeaponBase` 파생 — 투사체 대신 `OverlapSphere` 판정. `DamageInfo.cameraShake`를 채우면 타격감도 붙음 |
| 수동 발사 모드 | `Attack` Input Action([04번 문서](04-이동확장설계.md) 7장) → `WeaponController`가 자동/수동 전환 |
| 무기 강화 UI | `OnWeaponStatsChanged`(8-2) 구독 |
