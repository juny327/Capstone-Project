# 04. 이동 확장 설계 (대시 · 회피 · 이동 상태)

> **목적**: 대시/회피를 비롯한 이동 액션을 추가할 수 있는 구조를 설계한다.
> **범위**: `PlayerMove` 분해, 이동 상태 관리, 대시 데이터·모듈, 무적 프레임, 속도 배율 스택, Input Action 확장.
> 이슈 번호는 [02-이슈목록.md](02-이슈목록.md)를 따른다. 무기 쪽 설계는 [05-무기시스템설계.md](05-무기시스템설계.md) 참조.

## ⚠ 선행 조건

이 설계는 아래 두 항목과 **수정 지점이 겹친다**. 먼저 처리하지 않으면 같은 파일을 두 번 고치게 된다.

| 선행 항목 | 이유 |
|---|---|
| **C-1** 사망 가드 (`PlayerStats.TakeDamage`) | 5장 무적 프레임 가드와 **같은 진입부**에 들어간다 |
| **M-6** `speedModifiers` 초기화 경로 | 6장 속도 스택 재설계로 흡수된다 |

무기 시스템(05번)은 `EnemyDetector` 재작성(C-2/C-3)에 의존하지만, **이동 확장은 그와 독립**이므로 병렬 진행이 가능하다.

## 1. 현재 이동 구조의 한계

### 1-1. `PlayerMove` 하나가 가진 책임 9종

| # | 책임 | 위치 |
|---|---|---|
| 1 | Input Action 인스턴스 생성·바인딩·해제 | `PlayerMove.cs:55`, `:63-87` |
| 2 | 이동 입력 → 속도 적용 | `:120-122`, `:148-152` |
| 3 | 마우스 레이캐스트 조준점 계산 | `:94-103` |
| 4 | 조준점 기준 캐릭터 회전 | `:126-138` |
| 5 | 접지 판정 | `:124` |
| 6 | 점프 | `:154-161` |
| 7 | 속도 배율 스택 (슬로우/스턴) | `:13`, `:17-38` |
| 8 | 사망 시 정지 | `:15`, `:96`, `:107`, `:174-182` |
| 9 | Animator 파라미터 조작 (`isMove`/`isJump`/`isAttack`) | `:142`, `:151`, `:158`, `:165` |

책임 3(조준)은 이동이 아니라 **전투** 쪽 데이터다. 무기 시스템이 조준 방향을 필요로 하는데 지금은 `PlayerMove`의 private 필드(`targetLookPos`)에 갇혀 있다.

### 1-2. 대시를 넣을 때 정확히 어디가 막히는가

**(a) 속도를 얹을 자리가 없다**

```csharp
// PlayerMove.cs:119-122 — 매 FixedUpdate마다 무조건 덮어씀
Vector3 velocity = rb.linearVelocity;
velocity.x = move.x * speed;
velocity.z = move.y * speed;
rb.linearVelocity = velocity;
```

`rb.AddForce`로 대시를 밀어도 다음 `FixedUpdate`에서 x/z가 전부 덮어써진다. y만 보존되므로 대시는 **위로만** 가능한 셈이다. 대시를 넣으려면 이 4줄에 `if (isDashing)` 분기를 추가해야 하는데, 이후 넉백·이동 스킬·경직이 추가될 때마다 분기가 누적된다.

**(b) 회전을 잠글 수 없다**

```csharp
// PlayerMove.cs:126-138 — 조준점이 있으면 항상 회전
Vector3 direction = targetLookPos - transform.position;
```

대시 중에도 마우스를 따라 회전한다. 뒤로 구르는 중에 몸이 돌아가면 대시 방향과 캐릭터 정면이 어긋나 이동감이 무너진다.

**(c) 속도 배율 스택이 값 기반 제거다**

```csharp
// PlayerMove.cs:34
public void RemoveSpeedModifier(float multiplier)
{
    speedModifiers.Remove(multiplier);   // 값이 같은 첫 번째 항목을 제거
}
```

`List<float>.Remove(float)`는 **같은 값을 가진 첫 항목**을 지운다. 슬로우 두 개가 동시에 걸리면(둘 다 0.5f) 어느 것이 끝나든 하나가 사라지므로 우연히 맞아떨어진다. 그러나 대시 중 속도 오버라이드나 버프/디버프가 같은 배율로 겹치기 시작하면 **먼저 끝난 효과가 다른 효과의 배율을 지운다**. `StunEffect.cs:36,40`이 `AddSpeedModifier(0f)` / `RemoveSpeedModifier(0f)` 쌍을 쓰고 있어 스턴 2중첩에서 이미 잠재적으로 노출된 상태다.

**(d) 입력 액션이 2개뿐이다**

`Assets/PlayerInput.inputactions`에 `Move`(Vector2), `Jump`(Button)만 정의되어 있다. 대시 키를 받으려면 액션 자체를 새로 만들어야 한다.

## 2. 책임 분할 — `PlayerMove`를 셋으로

```
[분할 전]                       [분할 후]

PlayerMove                      PlayerInputReader  ── 입력 소유·수명 관리
 ├ 입력 바인딩                        ↓ (Move / OnJump / OnDash)
 ├ 조준 레이                    PlayerMove ──────── 이동·회전·접지
 ├ 이동                               ↑ (AimDirection)
 ├ 회전                         PlayerAim ───────── 조준점 계산
 ├ 접지/점프                          ↓
 ├ 속도 스택                    (05번 문서) WeaponController
 ├ 사망 정지
 └ Animator
```

### 2-1. `PlayerInputReader`

Input Action의 **생성·바인딩·해제·Dispose**를 한 곳으로 모은다. 현재 `PlayerMove.OnEnable`/`OnDisable`에 흩어진 6줄의 `+=`/`-=`와, 누락된 `Dispose()`(**M-4**)가 여기서 정리된다.

```csharp
public class PlayerInputReader : MonoBehaviour
{
    public Vector2 Move { get; private set; }

    public event Action OnJumpPressed;
    public event Action OnDashPressed;

    PlayerInput input;

    void Awake()    { input = new PlayerInput(); }
    void OnEnable() { /* 바인딩 후 input.Enable(); */ }
    void OnDisable(){ /* 해제 후 input.Disable(); */ }
    void OnDestroy(){ input.Dispose(); }          // ← M-4 해결

    public void SetInputEnabled(bool enabled);    // 사망·컷신용
}
```

> **주의**: 현재 `StopPlayer()`는 `playerInput.Disable()`을 호출하지만(`PlayerMove.cs:178`), 그 후 `OnDisable`이 다시 `Disable()`을 호출해도 무해하다. 다만 **부활/재시작 경로가 생기면 `Enable()`을 되돌릴 주체가 없다.** `SetInputEnabled`로 단일 창구를 만들어 두면 이 문제가 사라진다.

### 2-2. `PlayerAim`

조준 계산을 독립시킨다. 무기 시스템이 **조준 방향을 필요로 하는 유일한 소비자가 아니게** 되므로(대시 방향 폴백에도 쓰인다) 공용 컴포넌트로 두는 것이 맞다.

```csharp
public class PlayerAim : MonoBehaviour
{
    public bool HasValidAim { get; private set; }
    public Vector3 AimPoint { get; private set; }      // 지면상의 조준점
    public Vector3 AimDirection { get; private set; }  // y=0, 정규화됨

    [SerializeField] LayerMask groundLayer;
    [SerializeField] float maxRayDistance = 100f;

    Camera cam;

    void Update()
    {
        // cam == null 또는 Mouse.current == null 이면 HasValidAim = false 로 두고 조기 반환 (M-5)
        // 직전 유효값을 유지해 조준이 원점으로 튀지 않게 한다
    }

    public void SetCamera(Camera c);   // GameEvents.OnCameraReady 구독
}
```

**M-5 해결 포인트**: 현재 `PlayerMove.Update`(`:98`)는 `cam`과 `Mouse.current` 둘 다 무방비다. `HasValidAim = false`로 표현하면 소비자(이동 회전, 무기 조준)가 각자 폴백을 고를 수 있다 — 회전은 "직전 방향 유지", 무기는 "최근접 적 방향".

**이관 대상**: `PlayerMove`의 `cam`, `groundLayer`(레이캐스트용), `targetLookPos`, `SetCamera`, `GameEvents.OnCameraReady` 구독.

> `groundLayer`는 현재 **조준 레이캐스트**(`:99`)와 **접지 판정**(`:124`) 두 곳에서 함께 쓰인다. 분할 시 `PlayerAim`과 `PlayerMove`가 각각 자기 마스크를 갖게 되므로, 인스펙터에서 양쪽 모두 설정해야 한다. (마이그레이션 체크리스트 9장 참조)

### 2-3. `PlayerMove` (축소 후)

이동·회전·접지·속도스택만 남긴다. 상태 모듈 구동은 3장에서 다룬다.

## 3. 이동 상태 관리

### 3-1. 방식 선택 — 왜 BossState 패턴을 그대로 쓰지 않는가

프로젝트에는 이미 상태 패턴이 있다.

```csharp
// Boss/BossState.cs
public abstract class BossState
{
    public abstract void Enter(BossBrain brain);
    public abstract void Tick(BossBrain brain);
    public abstract void Exit(BossBrain brain);
}
// 구현체: BossIdleState / BossChaseState / BossAttackState / BossDieState / BossVictoryState
```

일관성만 보면 `PlayerState`를 같은 형태로 만드는 게 자연스럽다. 그러나 보스와 플레이어는 성격이 다르다.

| | 보스 | 플레이어 |
|---|---|---|
| 전이 주체 | AI가 스스로 판단 | 입력이 결정 |
| 상태 간 배타성 | 완전 배타 (Chase 중엔 Attack 아님) | **부분 중첩** (점프 중 이동, 스턴 중 낙하) |
| 갱신 시점 | `Tick()` (Update) | **`FixedTick()` (물리)** |
| 상태 수 | 5개, 증가 예정 | 3~5개, 안정적 |

특히 **부분 중첩**이 핵심이다. 완전 배타 FSM으로 만들면 `Jumping`인 동안 지상 이동 입력을 처리하기 위해 `JumpingState`가 `LocomotionState`의 코드를 복제하게 된다.

**권장**: 기본 이동은 항상 실행되는 **베이스 레이어**로 두고, 대시처럼 이동을 완전히 점유하는 액션만 **모듈**로 얹는다. 명칭은 `BossState`와 구분되도록 `IMovementModule`을 쓴다.

### 3-2. 상태 정의

```csharp
public enum MoveState
{
    Locomotion,   // 기본 (지상 이동 + 마우스 회전) — 베이스 레이어
    Dashing,      // 이동/회전 점유
    Stunned,      // 입력 무시, 중력만 유지
    Dead          // 모든 입력·물리 조작 정지
}
```

점프를 별도 상태로 두지 않는 이유: 현재 점프는 `AddForce` 한 번 + 접지 감지로 Animator를 복구하는 구조(`PlayerMove.cs:140-144`, `:154-161`)라 **공중에서도 지상과 동일하게 이동 입력을 받는다**. 이 동작을 유지한다면 점프는 `Locomotion`의 하위 사건이지 상태가 아니다. 만약 향후 공중 제어력을 낮추고 싶다면 `Locomotion` 내부에서 `currentGround` 여부로 계수를 곱하는 것이 상태를 늘리는 것보다 싸다.

### 3-3. 모듈 인터페이스

```csharp
public interface IMovementModule
{
    MoveState State { get; }

    bool CanEnter(PlayerMoveContext ctx);   // 쿨다운·접지 등 진입 조건
    void Enter(PlayerMoveContext ctx);
    void FixedTick(PlayerMoveContext ctx);  // rb 직접 조작은 여기서만
    bool WantsExit { get; }                 // 지속시간 종료 판정
    void Exit(PlayerMoveContext ctx);

    void Tick(float deltaTime);             // 쿨다운 진행 (비활성 중에도 호출)
}
```

`Tick`과 `FixedTick`을 나눈 이유: 대시 쿨다운은 **비활성 상태에서도** 흘러야 하고, 물리 조작은 `FixedUpdate`에서만 해야 한다.

### 3-4. `PlayerMoveContext`

모듈이 필요로 하는 것을 한 덩어리로 전달한다. 모듈마다 `GetComponent`를 반복하지 않게 하는 것이 목적이다.

```csharp
public class PlayerMoveContext
{
    public Rigidbody Rigidbody { get; }
    public Transform Transform { get; }
    public PlayerAnimator Animator { get; }        // 8장
    public PlayerInputReader Input { get; }
    public PlayerAim Aim { get; }
    public PlayerStats Stats { get; }              // 무적 요청용
    public bool IsGrounded { get; }
    public float CurrentSpeed { get; }             // 배율 합성 결과 (6장)

    public SpeedModifierHandle AddSpeedModifier(float multiplier);
    public void RemoveSpeedModifier(SpeedModifierHandle handle);
}
```

### 3-5. 전이 규칙

`PlayerMove`가 매 `FixedUpdate`에서 아래 순서로 판정한다.

| 순위 | 조건 | 결과 |
|---|---|---|
| 1 | 사망 | `Dead` — 다른 모든 전이 차단 |
| 2 | 스턴 적용 | `Stunned` — 진행 중인 대시를 **중단**시킬지 여부는 정책 결정 필요 (아래 참고) |
| 3 | 활성 모듈의 `WantsExit == true` | `Exit()` → `Locomotion` 복귀 |
| 4 | 대시 입력 + `CanEnter()` | `Dashing` 진입 |
| 5 | 그 외 | `Locomotion` 유지 |

> **정책 결정 필요 — 대시 중 스턴**: "대시로 스턴을 피할 수 있는가"는 게임 디자인 문제다. 두 안 모두 구조상 가능하다.
> - **중단시킴** — 스턴이 강력해지고 대시가 도박이 된다.
> - **대시를 끝까지 재생** — 대시가 확정 회피 수단이 되어 조작 신뢰도가 올라간다. 5장의 대시 무적과 결합하면 이쪽이 더 일관적이다.
>
> 현재 스턴은 `AddSpeedModifier(0f)`로 표현되므로(`StunEffect.cs:36`), 대시가 `CurrentSpeed`를 참조하지 않고 자체 속도로 움직이면 **아무것도 안 해도 후자(끝까지 재생)가 된다.** 전자를 원한다면 명시적으로 `Stunned` 전이에서 모듈을 강제 `Exit`시켜야 한다.

## 4. 대시 / 회피 설계

### 4-1. `DashData : ScriptableObject`

프로젝트에 이미 `EnemyData`, `StageData`, `UpgradeData` SO 패턴이 자리잡고 있으므로 동일하게 간다.

```csharp
[CreateAssetMenu(menuName = "Player/DashData")]
public class DashData : ScriptableObject
{
    [Header("Motion")]
    public float distance = 5f;
    public float duration = 0.15f;
    public AnimationCurve speedCurve = AnimationCurve.EaseInOut(0, 1, 1, 0);

    [Header("Cooldown")]
    public float cooldown = 1.5f;
    public int maxCharges = 1;          // 충전식

    [Header("Rules")]
    public bool groundedOnly = true;
    public bool lockRotation = true;    // 대시 중 마우스 회전 잠금
    public bool useAimAsFallback = true;// 입력 없을 때 조준 방향으로

    [Header("I-Frame")]
    public bool invulnerable = true;
    public float iFrameDuration = 0.2f; // duration보다 약간 길게 (착지 보정)

    [Header("Visual")]
    public GameObject trailPrefab;      // PoolManager에 등록 필요
}
```

> **`iFrameDuration > duration` 권장 이유**: 대시가 끝나는 프레임에 적 히트박스가 겹쳐 있으면 회피가 실패한 것처럼 느껴진다. 관용 구간을 두면 체감이 크게 좋아진다.

### 4-2. `DashModule`

```csharp
public class DashModule : IMovementModule
{
    public MoveState State => MoveState.Dashing;

    readonly DashData data;
    Vector3 dashDirection;
    float elapsed;
    float chargeTimer;
    int charges;

    public bool CanEnter(PlayerMoveContext ctx)
        => charges > 0 && (!data.groundedOnly || ctx.IsGrounded);

    public void Enter(PlayerMoveContext ctx)
    {
        dashDirection = ResolveDirection(ctx);
        elapsed = 0f;
        charges--;
        // data.invulnerable → ctx.Stats.SetInvulnerable(data.iFrameDuration)
        // ctx.Animator.TriggerDash()
        // trailPrefab → PoolManager.Instance.Get(...)
    }

    public void FixedTick(PlayerMoveContext ctx)
    {
        elapsed += Time.fixedDeltaTime;
        float t = Mathf.Clamp01(elapsed / data.duration);

        float baseSpeed = data.distance / data.duration;
        float speed = baseSpeed * data.speedCurve.Evaluate(t);

        Vector3 v = ctx.Rigidbody.linearVelocity;
        v.x = dashDirection.x * speed;
        v.z = dashDirection.z * speed;
        ctx.Rigidbody.linearVelocity = v;      // y 보존 → 중력 유지
        // lockRotation == true 이면 회전 갱신을 건너뛴다
    }

    public bool WantsExit => elapsed >= data.duration;

    public void Tick(float dt) { /* 충전 회복: chargeTimer 누적 → cooldown 도달 시 charges++ */ }
}
```

### 4-3. Rigidbody 구동 방식 — `linearVelocity` 오버라이드를 선택하는 이유

| 방식 | 장점 | 이 프로젝트에서의 문제 |
|---|---|---|
| `AddForce(Impulse)` | 물리적으로 자연스러움 | **거리 재현이 불가능**. 마찰·질량·기존 속도에 좌우되고, `FixedUpdate`가 x/z를 덮어쓰므로 애초에 남지 않음 |
| `MovePosition` 보간 | 거리 정확 | **중력·충돌 처리를 우회**해 벽을 뚫거나 공중에 뜬 채 멈출 수 있음. 현재 이동은 velocity 기반이라 방식이 이질적 |
| **`linearVelocity` 오버라이드** | 기존 이동과 **동일한 방식**, y 보존으로 중력 유지, 콜라이더가 정상 동작 | 곡선 적분 오차로 실제 거리가 `distance`와 미세하게 다름 (체감상 무시 가능) |

세 번째를 권장한다. 기존 `FixedUpdate`(`:119-122`)와 **완전히 같은 형태**이므로, `DashModule.FixedTick`이 `Locomotion`의 속도 계산을 대체하기만 하면 된다. 별도 분기가 필요 없다.

> `speedCurve`가 끝에서 0으로 떨어지면 대시 종료 시 속도가 0이 되어 급정지한다. 미끄러지는 느낌을 원하면 커브 끝값을 0.2~0.3 정도로 두거나, `Exit()`에서 이동 입력 방향의 속도로 부드럽게 이어받는다.

### 4-4. 대시 방향 결정

```
1. 이동 입력이 있다  → 입력 방향 (월드 기준, PlayerMove.cs:120-121과 동일한 매핑)
2. 입력이 없다
   ├ useAimAsFallback && Aim.HasValidAim → Aim.AimDirection  (조준 방향 대시)
   └ 그 외                                → transform.forward
```

현재 이동은 **월드 좌표계 기준**이다(`:116-122` — `velocity.x = move.x`, `velocity.z = move.y`). 카메라 상대가 아니므로 대시도 같은 매핑을 쓰면 입력과 결과가 일치한다.

> **회피(백스텝)를 별도로 만들 필요는 없다.** "입력 없을 때 뒤로"가 회피이고, "입력 방향으로"가 대시다. `DashData` 인스턴스를 두 개 만들어 다른 키에 바인딩하면 같은 모듈로 둘 다 구현된다.

## 5. 무적 프레임 (i-frame)

### 5-1. `PlayerStats` 진입부 가드

**C-1(사망 가드)과 정확히 같은 위치**에 들어간다. 반드시 함께 처리할 것.

```csharp
public class PlayerStats : MonoBehaviour, IDamageable
{
    bool isDead;                    // ← C-1
    float invulnerableUntil;

    public bool IsInvulnerable => Time.time < invulnerableUntil;

    public void SetInvulnerable(float duration)
    {
        // 더 긴 쪽을 유지 — 짧은 요청이 긴 무적을 깎지 않게
        invulnerableUntil = Mathf.Max(invulnerableUntil, Time.time + duration);
    }

    public void TakeDamage(DamageInfo info)
    {
        if (isDead) return;         // ← C-1
        if (IsInvulnerable) return; // ← 이번 설계
        // ... 기존 로직
    }
}
```

`Time.time` 기반을 쓰면 코루틴이 없어 **중단으로 인한 무적 고착이 원천 차단**된다. H-1(코루틴 중단으로 상태이상 영구화)과 같은 유형의 버그를 피할 수 있다.

> `Time.timeScale`이 0이 되는 구간(업그레이드 UI, `GameAppManager.StartGame`에서 1로 복구하는 것으로 보아 일시정지 사용 중)에서 `Time.time`은 멈추므로, 일시정지 중 무적 시간이 흐르지 않는다. 이것이 오히려 올바른 동작이다.

### 5-2. 무적 소스 통합

| 소스 | 호출 지점 | 지속 |
|---|---|---|
| 대시 | `DashModule.Enter` | `DashData.iFrameDuration` |
| 피격 후 무적 | `PlayerStats.TakeDamage` 말미 | 별도 `hitIFrameDuration` 필드 |
| 부활/스폰 보호 | `GameAppManager.SetupPlayer` 이후 | 스폰 직후 짧게 |

전부 `SetInvulnerable(float)` 하나를 거치므로 소스가 늘어도 로직이 늘지 않는다.

> **피격 후 무적을 넣을지는 정책 결정 사항이다.** 뱀서류는 적이 몸통으로 밀고 들어오는 게임이라 i-frame이 길면 난이도가 급락한다. 02번 문서가 지적한 "다단 히트 순삭"만 막을 정도(0.1~0.3초)면 충분하다.

## 6. 속도 배율 스택 재설계

### 6-1. 핸들 방식으로 전환

값 기반 제거(1-2 (c))를 없앤다.

```csharp
public sealed class SpeedModifierHandle
{
    public float Multiplier { get; }
    internal SpeedModifierHandle(float multiplier) { Multiplier = multiplier; }
}

public class PlayerMove : MonoBehaviour
{
    readonly List<SpeedModifierHandle> speedModifiers = new();

    public float CurrentSpeed { get; }   // baseSpeed × 모든 핸들의 Multiplier

    public SpeedModifierHandle AddSpeedModifier(float multiplier);
    public void RemoveSpeedModifier(SpeedModifierHandle handle);  // null 허용 (이미 제거됨)
    public void ClearSpeedModifiers();                            // ← M-6
}
```

`RemoveSpeedModifier`가 `null`과 **이미 제거된 핸들**을 조용히 무시하도록 하는 것이 중요하다. 코루틴이 중단되었다가 나중에 정리 코드가 도는 경로에서 예외가 나지 않는다.

### 6-2. `ClearSpeedModifiers` 호출 지점

플레이어가 `DontDestroyOnLoad`로 유지되므로 배율이 스테이지를 넘어 살아남는다(**M-6**).

- `GameEvents.OnPlayerDeadStart` 구독 시점 (`StopPlayer` 내부)
- `GameEvents.OnPlayerSpawned` 또는 스테이지 전환 시점

### 6-3. 호출부 영향 — 핸들 보관

| 파일 | 현재 | 변경 |
|---|---|---|
| `Player/SlowEffect.cs:27,43` | `AddSpeedModifier(multiplier)` / `RemoveSpeedModifier(multiplier)` | 반환된 핸들을 지역변수에 보관 후 해제 |
| `Boss/BossSkill/StunEffect.cs:36,40` | `AddSpeedModifier(0f)` / `RemoveSpeedModifier(0f)` | 동일 |

두 파일 모두 **코루틴 지역변수**로 보관하면 되므로 변경량은 각 2줄이다.

> 이 두 파일은 H-1(코루틴 호스트가 `GetComponent<MonoBehaviour>()`)도 함께 안고 있다. 03번 문서 2-2항과 같이 손보면 한 번에 정리된다.

### 6-4. `AddSpeed` 이벤트 수정 (M-1)

```csharp
public void AddSpeed(float amount)
{
    baseSpeed += amount;
    GameEvents.OnMoveSpeedChanged?.Invoke(CurrentSpeed);   // baseSpeed → CurrentSpeed
}
```

`Debug.Log($"real Speed : {baseSpeed}")`(`:170`)도 함께 제거한다 (L-9).

## 7. Input Action 확장

### 7-1. ⚠ 편집 규칙

`Assets/PlayerInput.cs`는 **`.inputactions`에서 자동 생성된 코드**다 (`PlayerInput` 클래스는 이 파일이 정의한다). 직접 편집하면 다음 재생성 때 전부 날아간다.

> **반드시** Unity 에디터에서 `Assets/PlayerInput.inputactions`를 열어 액션을 추가하고, 인스펙터의 `Generate C# Class`가 켜진 상태로 Apply해 `PlayerInput.cs`를 재생성할 것.

### 7-2. 추가할 액션

현재 `Player` 맵에 `Move`(Value/Vector2), `Jump`(Button) 2개만 있다.

| 액션 | 타입 | 권장 바인딩 | 용도 |
|---|---|---|---|
| `Dash` | Button | `<Keyboard>/leftShift`, `<Mouse>/rightButton` | 4장 대시 |
| `Aim` | Value / Vector2 | `<Mouse>/position` | 현재 `Mouse.current`를 직접 읽는 것(`PlayerMove.cs:98`)을 액션 경유로 바꾸면 패드 대응이 열린다 |
| `Attack` | Button | `<Mouse>/leftButton` | 향후 수동 발사 (05번 문서) |
| `SwapWeapon` | Button | `<Keyboard>/q` | 향후 무기 교체 (05번 문서) |

`Dash`만 이번 범위이고, 나머지 3개는 **자리만 미리 잡아두는 것**을 권장한다. `.inputactions` 편집은 에디터 왕복이 필요해 한 번에 처리하는 편이 싸다.

> `Assets/InputSystem_Actions.inputactions`(Unity 기본 템플릿, `Move`/`Look`/`Attack`/`Sprint` 등 포함)가 별도로 존재하지만 **어떤 스크립트도 사용하지 않는다.** 이쪽으로 갈아탈지, 아니면 삭제할지 한 번 정리하는 것이 좋다. 두 개가 공존하면 어느 것을 고쳐야 하는지 매번 헷갈린다.

## 8. Animator 파라미터 계약

### 8-1. 현재 상태 — 문자열이 두 파일에 흩어져 있음

| 파라미터 | 위치 |
|---|---|
| `"isMove"` | `PlayerMove.cs:151`, `PlayerStats.cs:103` |
| `"isJump"` | `PlayerMove.cs:142`, `:158`, `PlayerStats.cs:105` |
| `"isAttack"` | `PlayerMove.cs:165`, `PlayerStats.cs:104` |
| `"Die"` (state name) | `PlayerStats.cs:107` |
| Layer 1 weight | `PlayerStats.cs:102`, `:122` |

`PlayerStats.Die()`가 이동 관련 파라미터를 직접 끄고 있다(`:103-105`). 사망 처리가 이동 표현까지 알고 있는 구조라, 대시 파라미터를 추가하면 **여기도 같이 고쳐야 한다**는 것을 기억해야 한다. 잊으면 사망 시 대시 애니메이션이 남는다.

### 8-2. `PlayerAnimator` 래퍼

```csharp
public class PlayerAnimator : MonoBehaviour
{
    static readonly int IsMove   = Animator.StringToHash("isMove");
    static readonly int IsJump   = Animator.StringToHash("isJump");
    static readonly int IsAttack = Animator.StringToHash("isAttack");
    static readonly int DashTrig = Animator.StringToHash("Dash");   // 신규 (Trigger)

    public void SetMove(bool v);
    public void SetJump(bool v);
    public void SetAttack(bool v);
    public void TriggerDash();
    public void PlayDie();          // Layer weight 처리 포함
    public void ResetAll();         // 사망 시 일괄 정리 — 파라미터 추가 시 여기만 고침
}
```

`ResetAll()`이 있으면 8-1에서 말한 "파라미터를 추가할 때마다 `PlayerStats.Die()`도 고쳐야 하는" 결합이 사라진다.

`Animator.StringToHash`는 문자열 해싱을 매 호출마다 하지 않아 성능상으로도 유리하지만, 여기서는 **오타 방지와 변경 지점 단일화**가 더 큰 이득이다.

### 8-3. 대시 애니메이션

Trigger 방식(`TriggerDash()`)을 권장한다. 대시는 `duration`이 짧고(0.15초) 한 번 재생 후 끝나는 동작이라 bool 상태로 관리할 이유가 없다. Animator에는 Dash 클립을 **Any State → Dash** 전이로 걸고, Exit Time으로 `Locomotion`에 복귀시킨다.

> Dash 클립 길이와 `DashData.duration`이 다르면 애니메이션과 실제 이동이 어긋난다. 클립 길이를 맞추거나, `Enter()`에서 `anim.SetFloat("dashSpeed", clipLength / data.duration)`으로 재생 속도를 보정한다.

## 9. 마이그레이션 단계

### 9-1. 순서

| 단계 | 작업 | 씬/프리팹 작업 | 되돌리기 난이도 |
|---|---|---|---|
| 1 | **C-1 사망 가드** + `PlayerStats.SetInvulnerable` (5장) | 없음 | 낮음 |
| 2 | **속도 스택 핸들 전환** (6장) + `SlowEffect`/`StunEffect` 호출부 | 없음 | 낮음 |
| 3 | `PlayerAnimator` 도입 (8장) | 없음 (파라미터 추가 전까지) | 낮음 |
| 4 | `PlayerInputReader` 분리 (2-1) | **프리팹에 컴포넌트 추가** | 중간 |
| 5 | `PlayerAim` 분리 (2-2) | **프리팹 추가 + `groundLayer` 재할당** | 중간 |
| 6 | `.inputactions`에 `Dash` 추가 + 코드 재생성 (7장) | 에디터 작업 | 낮음 |
| 7 | `IMovementModule` + `PlayerMoveContext` 도입, `Locomotion` 이관 (3장) | 없음 | **높음** |
| 8 | `DashData` 에셋 + `DashModule` (4장) | **SO 생성 + 프리팹 할당 + Animator 클립/전이** | 중간 |

1~3은 이동 확장과 무관하게 **단독으로 가치가 있으므로** 먼저 넣어도 손해가 없다. 7이 가장 위험하므로 그 앞에서 한 번 플레이 검증할 것.

### 9-2. `Player.prefab` 영향 체크리스트

현재 프리팹 구조 (확인 결과):

```
Player (root)
 ├─ PlayerMove / PlayerStats / PlayerStatus / AutoAttack  ← 루트 컴포넌트
 ├─ EnemyDetector          ← 자식 오브젝트 (트리거 콜라이더)
 └─ ... 본 계층 ...
      └─ Hand_Right
           └─ AssaultRifle  ← Gun 컴포넌트
                ├─ Muzzle
                └─ BulletCase
```

| 항목 | 조치 |
|---|---|
| `PlayerInputReader` | 루트에 신규 추가 |
| `PlayerAim` | 루트에 신규 추가. **`groundLayer` 할당 필수** (`PlayerMove`에서 값 복사) |
| `PlayerAnimator` | 루트에 신규 추가. `Animator` 참조 연결 |
| `PlayerMove.cam` | `PlayerAim`으로 이관 — 기존 필드 제거 후 남은 참조 확인 |

| `DashData` 에셋 | `Assets/Data/Player/` 등에 생성 후 `PlayerMove`(또는 `DashModule` 보유자)에 할당 |
| Animator Controller | `Dash` Trigger 파라미터 + Any State 전이 추가 |

### 9-3. 플레이 검증 항목

1. **기본 회귀** — 이동/점프/마우스 회전/자동공격이 분할 전과 동일한가
2. **대시 거리** — `DashData.distance`를 5로 두고 눈금과 대조. 커브가 끝에서 0이 아니면 실제 거리가 더 길다
3. **대시 중 회전 잠금** — 대시 중 마우스를 크게 돌려도 캐릭터가 방향을 유지하는가
4. **대시 무적** — 자폭 몹 폭발 순간에 대시로 통과 시 피해가 0인가
5. **슬로우 중 대시** — 슬로우(`BossSlowSkill`) 상태에서 대시 거리가 줄지 않는가 (4-2의 `dashDirection` 속도는 `CurrentSpeed`와 무관해야 함 — 이것이 의도인지 확인)
6. **스턴 중첩** — 스턴 2개를 겹쳐 걸고 하나가 풀렸을 때 여전히 못 움직이는가 (6-1 핸들 방식 검증)
7. **스테이지 전환** — 슬로우 상태로 스테이지를 클리어하면 다음 스테이지에서 속도가 정상인가 (M-6 검증)
8. **사망** — 사망 후 추가 피격 시 `Die()`가 한 번만 도는가 (C-1 검증), 대시 애니메이션이 남지 않는가

## 10. 이 설계가 열어두는 확장

당장 구현하지 않아도, 위 구조를 따르면 아래가 **모듈 추가만으로** 가능해진다.

| 확장 | 구현 방법 |
|---|---|
| 백스텝 / 구르기 | `DashData` 인스턴스를 하나 더 만들고 다른 키에 바인딩 |
| 넉백 | `KnockbackModule : IMovementModule` — `Enter`에서 방향·세기를 받는 형태 |
| 이동 스킬 (돌진 공격) | `DashModule`을 상속해 `FixedTick`에서 히트박스 판정 추가 |
| 벽 대시 / 이단 대시 | `DashData.maxCharges` 증가 + `groundedOnly = false` |
| 대시 강화 업그레이드 | `UpgradeEffect`가 `DashModule`의 쿨다운/충전 수를 수정 — [05번 문서](05-무기시스템설계.md)의 `WeaponModifier`와 동일한 패턴 |
| 이동 속도 버프 아이템 | `AddSpeedModifier` + 핸들 보관 (6장) |
