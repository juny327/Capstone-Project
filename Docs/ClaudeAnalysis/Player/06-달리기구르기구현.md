# 06. 달리기 · 구르기 구현 가이드

> **목적**: WASD 걷기만 있는 현재 이동에 **달리기(스프린트)** 와 **구르기(회피)** 를 추가한다.
> **성격**: [04-이동확장설계.md](04-이동확장설계.md)가 "구조를 어떻게 잡을까"라면, 이 문서는 **"지금 코드에 어떻게 넣을까"** 다. 바로 따라 칠 수 있는 수준으로 쓴다.
> 이슈 번호는 [02-이슈목록.md](02-이슈목록.md)를 따른다.

---

## 0. 시작 전에 알아야 할 3가지

프로젝트를 실제로 열어 확인한 내용이다. 이걸 모르고 시작하면 헛수고가 생긴다.

### ① 지금 "걷기"로 보이는 건 사실 **Run 클립**이다

`Assets/Animations/Player/PlayerAnimator.controller`의 Base Layer는 이렇게 되어 있다.

```
Idle_gunMiddle_AR  ──[isMove == true]──▶  Run_gunMiddle_AR
                   ◀─[isMove == false]──
```

즉 이미 **달리기 클립을 걷기 속도(`baseSpeed = 3`)로 재생**하고 있다. 그래서 "그냥 걷는 것처럼" 밋밋해 보인다. 달리기를 추가한다는 건 새 클립을 넣는 게 아니라, **지금 것을 걷기로 내리고 그 위에 진짜 달리기를 얹는** 작업에 가깝다.

### ② 구르기 애니메이션이 **프로젝트에 없다**

`Assets/SciFiWarriorPBRHPPolyart/Animations/`를 전수 확인했다.

```
Die, Idle_Ducking_ar, Idle_Shoot_ar, Idle_guard_ar, Idle_gunMiddle_ar,
Jump, Reload, Run_guard_AR, Run_gunMiddle_AR,
Shoot_AutoShot_AR, Shoot_BurstShot_AR, Shoot_SingleShot_AR,
WalkBack_Shoot_ar, WalkFront_Shoot_ar, WalkLeft_Shoot_ar, WalkRight_Shoot_ar
```

**구르기(Roll/Dodge/Dive) 클립이 없다.** 이게 이 작업의 유일한 실질적 장애물이다. 해결책은 2장에 정리했다.

### ③ 안 쓰고 있는 클립이 **10개** 있다

팩의 FBX는 16개인데 `Assets/Animations/Player/`에 임포트된 건 6개다 — `Idle_gunMiddle_AR`, `Run_gunMiddle_AR`, `Jump`, `Die`, `Reload`, `Shoot_Autoshot_AR`. 그중 `Reload`는 임포트만 되고 컨트롤러에 상태가 없다.

특히 **`WalkFront / WalkBack / WalkLeft / WalkRight_Shoot_ar` 4방향 걷기가 통째로 놀고 있다.** 이 게임은 마우스를 보면서 옆으로 이동하는 트윈스틱 방식인데, 지금은 **어느 방향으로 움직이든 정면 달리기 클립 하나만** 재생된다. 옆걸음·뒷걸음이 정면 달리기로 나오는 것이 "이동이 밋밋한" 체감의 큰 부분이다.

> 달리기·구르기를 넣기 전에 **4방향 블렌드만 적용해도** 이동 표현이 크게 좋아진다. 5-3에서 다룬다.

## 1. 현재 이동 코드 진단

### 1-1. 관련 코드

```csharp
// PlayerMove.cs:116-122 — 이동 (월드 좌표계 기준)
float speed = CurrentSpeed;

Vector3 velocity = rb.linearVelocity;
velocity.x = move.x * speed;
velocity.z = move.y * speed;
rb.linearVelocity = velocity;   // y는 보존 → 중력 유지
```

```csharp
// PlayerMove.cs:126-138 — 마우스 방향으로 회전 (이동 방향과 독립)
Vector3 direction = targetLookPos - transform.position;
direction.y = 0;
if (direction.sqrMagnitude > 0.001f) { ... rb.MoveRotation(newRot); }
```

**이동 방향과 바라보는 방향이 분리**되어 있다. 이게 트윈스틱 구조이고, 달리기·구르기 설계에 그대로 영향을 준다.

### 1-2. Animator 실측

| 항목 | 실제 값 |
|---|---|
| 파라미터 | `isMove`(bool), `isJump`(bool), `isAttack`(bool), `isDead`(bool) |
| Base Layer (index 0) | `Idle_gunMiddle_AR` ↔ `Run_gunMiddle_AR`, `Jump`, `Die` |
| ShootLayer (index 1) | `Idle_gunMiddle_AR` ↔ `Shoot_Autoshot_AR`, **상체 마스크 적용** |
| 레이어 가중치 조작 | `anim.SetLayerWeight(1, ...)` — `PlayerStats.cs:102`, `:122` |

> **`isDead` 파라미터는 컨트롤러에 있지만 코드가 한 번도 세팅하지 않는다.** 사망은 `anim.Play("Die")`(`PlayerStats.cs:107`)로 직접 재생한다. 죽은 파라미터이므로 정리 대상이다.

**ShootLayer가 상체 마스크로 분리되어 있다**는 점이 중요하다. 덕분에 달리면서 사격하는 표현이 되지만, **구르는 중에도 상체는 총을 쏜다.** 구르기 구현에서 반드시 처리해야 한다 (4-4 참조).

## 2. 구르기 애니메이션 확보

세 가지 길이 있다. 표에서 하나를 고르고 시작하면 된다.

| 방법 | 비용 | 품질 | 비고 |
|---|---|---|---|
| **A. Mixamo에서 받기** (권장) | 무료 / 20분 | 높음 | `Dodge Roll`, `Stand To Roll` 등. Humanoid 리타게팅으로 이 캐릭터에 바로 적용됨 |
| **B. 코드로 흉내내기** | 0원 / 1시간 | 낮음 | 캡슐을 굴리듯 모델을 X축 회전. 총 든 캐릭터라 어색함 |
| **C. `Jump` 클립 임시 사용** | 0원 / 5분 | 매우 낮음 | **프로토타입 전용.** 로직 먼저 검증하고 나중에 교체 |

### 2-1. A안 진행 순서 (Mixamo)

1. mixamo.com 접속 → 캐릭터 업로드 불필요, 기본 캐릭터로 검색
2. `Roll` 또는 `Dodge` 검색 → 원하는 모션 선택
3. Download 설정: **Format = FBX for Unity**, **Skin = Without Skin**, FPS 30
4. `Assets/Animations/Player/`에 넣기
5. Inspector → **Rig 탭 → Animation Type = `Humanoid`**, **Avatar Definition = `Create From This Model`** → Apply
6. **Animation 탭 → `Loop Time` 끄기, `Root Transform Position (XZ) → Bake Into Pose` 켜기**

> **⚠ 5번에서 `Copy From Other Avatar`를 쓰면 안 된다.** 다음 에러가 난다.
>
> ```
> Rig Error: Invalid copied Avatar Rig Configuration:
>     No human bone found. Ensure both rig type match
> ```
>
> `Copy From Other Avatar`는 **본 이름 기준으로 매핑을 복사**한다. 그런데 두 리그의 본 이름이 전혀 다르다.
>
> | | SciFiWarrior | Mixamo |
> |---|---|---|
> | 골반 | `Hips` | `mixamorig:Hips` |
> | 왼쪽 허벅지 | `UpperLeg_Left` | `mixamorig:LeftUpLeg` |
> | 왼쪽 어깨 | `Shoulder_Left` | `mixamorig:LeftShoulder` |
>
> 복사해온 매핑이 가리키는 이름이 Mixamo FBX에 하나도 없으니 "human bone을 못 찾았다"가 된다. **둘 다 Humanoid인데도** 나는 에러라 헷갈리기 쉽다.
>
> `Create From This Model`을 쓰면 Unity가 Mixamo 스켈레톤을 보고 **자체 Humanoid 아바타를 새로 만든다.** Humanoid끼리는 본 이름과 무관하게 **머슬(Muscle) 추상화를 통해 리타게팅**되므로, 이렇게 해야 정상 동작한다.
>
> 참고로 **이 프로젝트의 기존 팩 애니메이션들도 전부 `Create From This Model`** 이다 (`Animations/*.fbx.meta`의 `copyAvatar: 0`). 원래 쓰던 방식과 동일하다.
>
> > `Copy From Other Avatar`가 맞는 경우는 **FBX가 원본 모델과 완전히 같은 스켈레톤**일 때다 — 같은 리그에서 뽑아낸 애니메이션 전용 FBX 같은 경우. Mixamo는 리그가 다르므로 해당되지 않는다.

> **6번이 핵심이다.** Bake Into Pose를 켜지 않으면 클립의 루트 이동이 살아 있어, 코드로 미는 속도(4장)와 **이중으로 겹쳐** 구르기 거리가 2배가 된다.
>
> 같은 이유로 Player 프리팹의 **Animator 컴포넌트에서 `Apply Root Motion`은 꺼진 상태를 유지**해야 한다. 현재 이동이 전부 `rb.linearVelocity` 기반이므로 루트 모션이 켜지면 서로 싸운다.

### 2-2. Mixamo 임포트 트러블슈팅

| 증상 | 원인 | 해결 |
|---|---|---|
| `No human bone found. Ensure both rig type match` | `Copy From Other Avatar` 사용 (본 이름 불일치) | **`Create From This Model`로 변경** (2-1의 5번) |
| Apply는 됐는데 캐릭터가 T포즈로 굳음 | Humanoid 자동 매핑 실패 | Rig 탭 → **Configure...** → 본 매핑이 전부 초록인지 확인. 빨간 곳은 수동 지정 |
| 모델이 거대하거나 아주 작게 나옴 | FBX `Scale Factor` 불일치 | Model 탭 → `Scale Factor` 조정 (Mixamo는 보통 0.01 또는 1.0) |
| 구르기 중 캐릭터가 **제자리에서만** 구름 | 정상이다 | 이동은 4장 코드가 담당한다. `Bake Into Pose`가 켜져 있으면 이게 맞는 동작 |
| 구르기 거리가 의도의 **2배** | `Bake Into Pose` 꺼짐 + 루트 모션 중복 | 2-1의 6번 확인 + 프리팹 Animator의 `Apply Root Motion` 끄기 |
| 총을 든 손 모양이 풀림 | Mixamo 클립에 총 그립 포즈가 없음 | 구르는 0.45초 동안만이라 대개 문제되지 않는다. 거슬리면 상체에 `Upper.mask`를 씌운 레이어로 그립 포즈를 덮어쓴다 |

> **Configure 화면을 한 번은 열어볼 것.** `Create From This Model`로 바꿔 에러가 사라져도, 자동 매핑이 일부 본을 놓쳤을 수 있다. Configure에서 실루엣이 초록이면 정상이다.

### 2-3. C안으로 먼저 갈 때

로직부터 검증하고 싶다면 `Roll` 트리거를 `Jump` 상태에 임시로 연결해도 된다. **4장 코드는 애니메이션과 무관하게 동작**하므로, 클립만 나중에 갈아끼우면 된다. 실제로 이 순서가 효율적이다 — 이동감 튜닝(거리·시간·커브)이 애니메이션보다 훨씬 오래 걸린다.

## 3. 달리기(스프린트) 구현

### 3-1. 최소 구현

`PlayerMove`에 추가한다.

```csharp
[Header("Sprint")]
[SerializeField] float sprintMultiplier = 1.6f;   // 3 → 4.8
bool isSprinting;
```

```csharp
// OnEnable
playerInput.Player.Sprint.performed += OnSprint;
playerInput.Player.Sprint.canceled  += OnSprint;

// OnDisable — 반드시 짝 맞춰 해제
playerInput.Player.Sprint.performed -= OnSprint;
playerInput.Player.Sprint.canceled  -= OnSprint;
```

```csharp
void OnSprint(InputAction.CallbackContext context)
{
    isSprinting = context.performed;   // performed=누름, canceled=뗌
}
```

```csharp
// FixedUpdate — 기존 speed 계산 한 줄만 교체
bool sprinting = isSprinting && move != Vector2.zero;
float speed = CurrentSpeed * (sprinting ? sprintMultiplier : 1f);
```

> **`move != Vector2.zero` 조건이 필요한 이유**: 제자리에서 Shift를 눌러도 스프린트 상태가 되면, 5장의 애니메이션 블렌드에서 **가만히 선 채 달리는 모션**이 나온다.

### 3-2. ⚠ `AddSpeedModifier`를 쓰면 안 된다

"스프린트도 배율이니 기존 `speedModifiers`에 넣으면 되지 않나?" — 안 된다.

```csharp
// PlayerMove.cs:34 — 값으로 제거한다
public void RemoveSpeedModifier(float multiplier)
{
    speedModifiers.Remove(multiplier);   // 같은 값을 가진 '첫 번째' 항목을 지움
}
```

`List<float>.Remove(float)`는 **값이 같은 첫 항목**을 지운다. 스프린트 배율을 이 리스트에 넣으면, 슬로우가 풀리는 순간 `Remove`가 **스프린트 배율을 대신 지워버리는** 경우가 생긴다. Shift를 누르고 있는데도 느려지는데, 원인을 찾기가 매우 어렵다.

그래서 스프린트는 **`speedModifiers`와 무관한 별도 필드**로 두고 `CurrentSpeed`에 곱하기만 한다. 위 3-1이 그렇게 되어 있다.

> 이 값 기반 제거 자체가 잠재 버그다(**M-6**과 함께). 근본 해결(핸들 방식)은 [04-이동확장설계.md](04-이동확장설계.md) 6장에 있다. 지금은 **스프린트를 그 리스트에 넣지 않는 것만으로 회피**된다.

### 3-3. 스태미나 (선택)

무한 스프린트는 걷기를 무의미하게 만든다. 넣을 거라면 이 정도면 충분하다.

```csharp
[Header("Stamina")]
[SerializeField] float maxStamina = 100f;
[SerializeField] float sprintCost = 25f;      // 초당 소모
[SerializeField] float staminaRegen = 15f;    // 초당 회복
[SerializeField] float regenDelay = 1f;       // 소모 후 회복까지 대기

float stamina;
float regenTimer;

public event Action<float, float> OnStaminaChanged;   // HUD 연동용

void TickStamina(float dt)
{
    bool sprinting = isSprinting && move != Vector2.zero && stamina > 0f;

    if (sprinting)
    {
        stamina -= sprintCost * dt;
        regenTimer = regenDelay;
    }
    else if (regenTimer > 0f) regenTimer -= dt;
    else stamina += staminaRegen * dt;

    stamina = Mathf.Clamp(stamina, 0f, maxStamina);
    OnStaminaChanged?.Invoke(stamina, maxStamina);
}
```

`FixedUpdate`의 `sprinting` 판정에 `&& stamina > 0f`를 추가하면 연결된다.

> **뱀서류에 스태미나가 맞는지는 한 번 생각해볼 문제다.** 이 장르는 계속 도망다니는 게 기본이라, 스태미나가 있으면 플레이어가 항상 게이지를 쳐다보게 된다. **구르기에만 쿨다운을 두고 스프린트는 무제한**으로 가는 설계도 흔하다. 넣지 않기로 해도 3-1은 그대로 유효하다.
>
> 반대로 스태미나를 넣으면 "스태미나 최대치 증가 / 회복 속도 증가" 업그레이드 카드가 생겨 성장 선택지가 늘어난다. 현재 업그레이드 풀이 5종뿐이라 이 점은 매력적이다.

### 3-4. HUD 연동

스태미나를 넣었다면 `GameEvents`에 이벤트를 추가하고 `PlayerStatsUI`가 받는다. 기존 이동속도 표시(`moveSpeedText`)와 같은 패턴이다.

```csharp
public static Action<float, float> OnStaminaChanged;   // GameEvents
```

> **주의**: `PlayerStatsUI`는 `OnPlayerSpawned`마다 구독을 추가하면서 해제하지 않는 문제(**H-3**)가 있다. 스태미나 구독을 **인스턴스 이벤트**(`stats.OnStaminaChanged`)로 붙이면 같은 누적 버그에 걸린다. `GameEvents` 정적 이벤트로 가거나, 구독 전에 해제를 먼저 하도록 처리할 것.

## 4. 구르기 구현

### 4-1. 달리기와 근본적으로 다른 점

| | 달리기 | 구르기 |
|---|---|---|
| 입력 | 누르고 있는 동안 (hold) | 한 번 누름 (press) |
| 지속 | 무제한 | **고정 시간** (0.4~0.5초) |
| 제어 | 이동 중 자유롭게 방향 전환 | **진입 시 방향 확정, 중간 변경 불가** |
| 이동 방식 | `CurrentSpeed` 곱셈 | **자체 속도로 덮어씀** (슬로우 영향 없음) |
| 회전 | 마우스 추적 | **잠금** |
| 무적 | 없음 | **있음** (핵심 가치) |
| 취소 | 즉시 | 불가 (커밋) |

**"커밋(commit)"이 구르기의 본질**이다. 0.45초 동안 조작을 포기하는 대신 무적을 얻는 거래다. 중간에 취소되면 이 거래가 성립하지 않으므로, 취소 가능하게 만들면 안 된다.

### 4-2. 필드

```csharp
[Header("Roll")]
[SerializeField] float rollDistance = 4f;
[SerializeField] float rollDuration = 0.45f;
[SerializeField] float rollCooldown = 1.2f;
[SerializeField] float rollIFrame  = 0.35f;    // duration보다 짧게 (뒷부분은 무방비)
[SerializeField] AnimationCurve rollCurve = AnimationCurve.EaseInOut(0f, 1f, 1f, 0.2f);
[SerializeField] bool rollNeedsGround = true;

bool  isRolling;
float rollElapsed;
float rollCdTimer;
Vector3 rollDir;

public bool IsRolling => isRolling;   // AutoAttack이 참조 (4-4)
```

> **`rollIFrame < rollDuration`으로 둔 이유**: 무적이 구르기 전체를 덮으면 "일단 구르면 안전"이 되어 판단이 사라진다. 앞 78%만 무적이고 뒷부분은 무방비여야 타이밍을 재는 재미가 생긴다. 반대로 [04번 문서](04-이동확장설계.md)의 **대시**는 짧고 잦은 이동기라 무적을 조금 **길게** 주는 게 맞다 — 성격이 다르다.
>
> **커브 끝값을 0이 아닌 0.2로 둔 이유**: 0이면 구르기 종료 순간 속도가 0이 되어 뚝 끊긴다. 약간 남겨두면 자연스럽게 이어진다.

### 4-3. 코드

```csharp
void OnRoll(InputAction.CallbackContext context)
{
    if (!context.performed) return;
    if (isDead || isRolling) return;
    if (rollCdTimer > 0f) return;
    if (rollNeedsGround && !currentGround) return;

    StartRoll();
}

void StartRoll()
{
    rollDir     = ResolveRollDirection();
    isRolling   = true;
    rollElapsed = 0f;
    rollCdTimer = rollCooldown;

    // 구르는 방향을 바라보게 고정 (클립이 정면 구르기 하나뿐이므로)
    rb.MoveRotation(Quaternion.LookRotation(rollDir));

    anim.SetBool("isMove", false);
    anim.SetTrigger("Roll");
    anim.SetLayerWeight(1, 0f);          // 상체 사격 레이어 끄기 ★

    stats.SetInvulnerable(rollIFrame);   // ★ PlayerStats에 추가 필요 (4-4 ③)
}

Vector3 ResolveRollDirection()
{
    // 이동 입력이 있으면 그 방향 — 현재 이동과 동일한 월드 매핑 (PlayerMove.cs:120-121)
    if (move != Vector2.zero)
        return new Vector3(move.x, 0f, move.y).normalized;

    // 입력이 없으면 뒤로 (백스텝)
    return -transform.forward;
}

void TickRoll()
{
    rollElapsed += Time.fixedDeltaTime;
    float t = Mathf.Clamp01(rollElapsed / rollDuration);

    float speed = (rollDistance / rollDuration) * rollCurve.Evaluate(t);

    Vector3 v = rb.linearVelocity;
    v.x = rollDir.x * speed;
    v.z = rollDir.z * speed;
    rb.linearVelocity = v;               // y 보존 → 중력 유지, 낭떠러지에서 정상 낙하

    currentGround = Physics.Raycast(transform.position, Vector3.down, GroundCheckDis, groundLayer);

    if (rollElapsed >= rollDuration) EndRoll();
}

void EndRoll()
{
    isRolling = false;
    if (isDead) return;                  // 구르는 도중 사망한 경우 (4-4 ① 주의)
    anim.SetLayerWeight(1, 1f);          // 상체 레이어 복구
}
```

`FixedUpdate` 앞부분을 이렇게 고친다.

```csharp
void FixedUpdate()
{
    if (isDead) return;

    if (rollCdTimer > 0f) rollCdTimer -= Time.fixedDeltaTime;

    if (isRolling)
    {
        TickRoll();
        return;              // ★ 일반 이동·회전을 통째로 건너뜀
    }

    // ... 기존 이동 로직 그대로 ...
}
```

**`return` 한 줄이 회전 잠금과 이동 차단을 동시에 해결한다.** 기존 코드를 건드리지 않아도 되는 게 이 방식의 장점이다.

### 4-4. 반드시 처리해야 할 4가지 함정

#### ① 상체가 구르면서 총을 쏜다

ShootLayer(index 1)가 상체 마스크로 분리되어 있어서(1-2), 구르는 중에도 `isAttack`이 true면 **상반신은 사격 자세를 유지**한다. 몸은 구르는데 팔은 총을 겨누는 그림이 나온다.

→ `StartRoll`에서 `anim.SetLayerWeight(1, 0f)`, `EndRoll`에서 `1f`로 복구. 위 코드에 반영되어 있다.

> **주의**: `PlayerStats.Die()`도 `SetLayerWeight(1, 0f)`를 한다(`:102`). **구르는 도중에 죽으면** `EndRoll`이 나중에 실행되면서 죽은 캐릭터의 상체 레이어를 `1f`로 되살린다. 4-3 코드의 `if (isDead) return;`이 이걸 막는다. `StopPlayer()`에서 `isRolling = false`로 함께 정리해두면 더 확실하다.

#### ② 구르는 중에도 자동으로 총알이 나간다

`AutoAttack.Update`(`:26-38`)는 `detector.HasEnemy()`만 보므로 구르는 중에도 계속 발사한다. 총구가 엉뚱한 데를 향한 채 총알이 나온다.

→ `AutoAttack`에 `PlayerMove` 참조를 추가하고 게이트를 건다.

```csharp
// AutoAttack.Update 맨 앞
if (playerMove != null && playerMove.IsRolling) return;
```

> **정책 결정**: 구르는 중 사격을 막을지는 취향이다. 막으면 "회피와 딜의 트레이드오프"가 생기고, 안 막으면 조작이 편해진다. 다만 **애니메이션이 어색해지는 건 확실**하므로, 막지 않기로 했다면 ①의 레이어 끄기도 하지 말고 상체를 유지해야 그림이 맞는다. 둘 중 하나로 통일할 것.

#### ③ `SetInvulnerable`이 아직 없다

`PlayerStats`에 무적 개념 자체가 없다. 추가해야 한다. **이 수정은 C-1(사망 가드 부재)과 정확히 같은 자리**이므로 함께 처리하는 게 맞다.

```csharp
// PlayerStats.cs
bool  isDead;                 // ← C-1 해결
float invulnerableUntil;

public bool IsInvulnerable => Time.time < invulnerableUntil;

public void SetInvulnerable(float duration)
{
    invulnerableUntil = Mathf.Max(invulnerableUntil, Time.time + duration);
}

public void TakeDamage(DamageInfo info)
{
    if (isDead) return;           // ← C-1
    if (IsInvulnerable) return;   // ← 구르기 무적
    // ... 기존 로직
}
```

`Time.time` 기반이라 코루틴이 없다. 코루틴이 중간에 끊겨 무적이 영구화되는 사고(**H-1**과 같은 유형)가 원천적으로 불가능하다.

> `Die()` 진입 시 `isDead = true`를 반드시 세팅할 것. 안 하면 C-1이 그대로 남는다.

#### ④ 트리거가 두 번 걸린다

`anim.SetTrigger("Roll")`을 **Any State → Roll** 전이로 받을 때, 전이의 **`Can Transition To Self`를 꺼야 한다.** 켜져 있으면 구르는 도중 트리거가 한 번 더 소비되면서 애니메이션이 처음부터 재생된다. 코드의 `if (isRolling) return;` 가드가 대부분 막아주지만, Animator 쪽에서도 막아두는 게 안전하다.

또한 `Roll` 상태에서 나가는 전이는 **`Has Exit Time` 체크 + Exit Time 1.0**으로 두어 클립이 끝나야 빠져나가게 한다.

### 4-5. 입력 버퍼 (선택, 체감 개선 큼)

쿨다운이 0.1초 남았을 때 누른 입력이 그냥 씹히면 "안 눌렸다"고 느낀다. 짧은 버퍼를 두면 체감이 크게 좋아진다.

```csharp
[SerializeField] float rollBufferTime = 0.15f;
float rollBufferedAt = -999f;

void OnRoll(InputAction.CallbackContext context)
{
    if (!context.performed) return;
    rollBufferedAt = Time.time;      // 일단 기록만
}

// FixedUpdate의 구르기 판정부
bool buffered = Time.time - rollBufferedAt <= rollBufferTime;
if (buffered && !isRolling && !isDead && rollCdTimer <= 0f
    && (!rollNeedsGround || currentGround))
{
    rollBufferedAt = -999f;          // 소비
    StartRoll();
}
```

## 5. Animator 재구성

### 5-1. 추가할 파라미터

| 파라미터 | 타입 | 용도 |
|---|---|---|
| `Roll` | **Trigger** | 구르기 진입 |
| `moveSpeed` | Float | 0=Idle, 0.5=Walk, 1=Run 블렌드 |
| `moveX` / `moveY` | Float | 4방향 블렌드 (5-3) |

기존 `isDead`는 코드가 쓰지 않으므로(1-2) **삭제하거나**, `PlayerStats.Die()`에서 실제로 세팅하고 `anim.Play("Die")`를 전이 기반으로 바꾸는 것 중 하나를 택한다. 지금처럼 방치하면 다음 사람이 혼란스럽다.

### 5-2. 걷기/달리기 블렌드 — 가장 쉬운 방법부터

**(a) 클립 재생 속도만 조절** — 5분, 클립 추가 없음

`Run_gunMiddle_AR` 상태의 Speed에 `moveSpeed` 파라미터를 곱하게 설정(Inspector의 Speed → Multiplier 체크 → `moveSpeed` 선택)하고, 코드에서:

```csharp
anim.SetFloat("moveSpeed", sprinting ? 1.4f : 1f);
```

달릴 때 다리가 더 빨리 움직인다. 조잡하지만 **속도가 올라간 게 눈에 보인다.** 프로토타입엔 충분하다.

**(b) Walk / Run 블렌드 트리** — 30분, 제대로

1. `Assets/SciFiWarriorPBRHPPolyart/Animations/WalkFront_Shoot_ar.fbx`에서 클립을 추출해 `Animations/Player/`에 배치
2. Base Layer에 **Blend Tree**(1D, 파라미터 `moveSpeed`) 생성
3. Threshold: `0 → Idle_gunMiddle_AR`, `0.5 → WalkFront`, `1.0 → Run_gunMiddle_AR`
4. 코드:

```csharp
float target = move == Vector2.zero ? 0f : (sprinting ? 1f : 0.5f);
anim.SetFloat("moveSpeed", target, 0.1f, Time.deltaTime);   // 0.1초 댐핑
```

> `SetFloat`의 **damping 오버로드**를 쓰는 게 요령이다. 값이 즉시 튀지 않고 부드럽게 따라가서, 걷기↔달리기 전환이 자연스럽다. 직접 `Mathf.Lerp`를 짤 필요가 없다.

### 5-3. 4방향 블렌드 — 이동 표현을 가장 크게 바꾸는 작업

0장 ③에서 말한 부분이다. 이 캐릭터는 **마우스를 보면서 옆으로 이동**하는데 지금은 항상 정면 달리기만 나온다.

`WalkFront / WalkBack / WalkLeft / WalkRight_Shoot_ar` 4개를 임포트하고 **2D Freeform Directional** 블렌드 트리를 만든다.

| 클립 | moveX | moveY |
|---|---|---|
| Idle | 0 | 0 |
| WalkFront | 0 | 1 |
| WalkBack | 0 | -1 |
| WalkLeft | -1 | 0 |
| WalkRight | 1 | 0 |

코드에서 **이동 방향을 캐릭터 로컬 기준으로 변환**해 넣는 것이 핵심이다.

```csharp
Vector3 worldMove = new Vector3(move.x, 0f, move.y);
Vector3 localMove = transform.InverseTransformDirection(worldMove);

anim.SetFloat("moveX", localMove.x, 0.1f, Time.deltaTime);
anim.SetFloat("moveY", localMove.z, 0.1f, Time.deltaTime);
```

`InverseTransformDirection`이 "월드 이동 방향"을 "내 몸 기준 앞/뒤/좌/우"로 바꿔준다. 마우스로 몸을 돌리면 같은 A키 입력이 옆걸음에서 뒷걸음으로 자연스럽게 바뀐다.

> 달리기까지 같이 넣으려면 3D 블렌드(`moveX`, `moveY`, `moveSpeed`)가 되어 복잡해진다. **Walk 4방향 트리와 Run 4방향 트리를 각각 만들고 `moveSpeed`로 두 트리를 1D 블렌드**하는 2단 구성이 관리하기 쉽다. Run 4방향 클립이 없으므로, 1차에는 **Walk만 4방향 + Run은 정면 하나**로 두고 나중에 채워도 된다.

### 5-4. Roll 상태 배치

```
Any State ──[Roll (Trigger)]──▶  Roll
                                  │ Has Exit Time = 1.0
                                  ▼
                              Idle / Locomotion
```

- Any State 전이: **`Can Transition To Self` 끄기** (4-4 ④)
- 전이 Duration: 0.05~0.1초 (짧게 — 구르기는 즉발감이 중요)
- Roll 상태: **Loop Time 끄기**
- 클립 길이와 `rollDuration`(0.45초)이 다르면 어긋난다. 맞추거나, Roll 상태 Speed에 배수를 넣어 보정한다.

## 6. Input Action 추가

### ⚠ 편집 규칙

`Assets/PlayerInput.cs`는 **`.inputactions`에서 자동 생성된 코드**다. 직접 편집하면 다음 재생성 때 전부 날아간다.

> Unity 에디터에서 `Assets/PlayerInput.inputactions`를 더블클릭 → 액션 추가 → **Save Asset** → Inspector의 `Generate C# Class`가 켜져 있으면 `PlayerInput.cs`가 자동 갱신된다.

### 추가할 액션

현재 `Player` 맵에는 `Move`(Value/Vector2), `Jump`(Button) 2개뿐이다.

| 액션 | 타입 | 권장 바인딩 | 비고 |
|---|---|---|---|
| `Sprint` | Button | `<Keyboard>/leftShift` | **Interactions 비워둘 것** — `performed`/`canceled`로 hold 판정 |
| `Roll` | Button | `<Keyboard>/space` 또는 `<Mouse>/rightButton` | press 판정 |

> **`Sprint`에 `Hold` Interaction을 걸지 말 것.** `Hold`는 "일정 시간 누르고 있어야 performed 발동"이라 스프린트가 늦게 걸린다. 아무 Interaction 없이 기본 동작(누르는 순간 `performed`, 떼는 순간 `canceled`)이 정확히 원하는 것이다.

> **`Roll`을 Space로 할지 결정 필요.** 현재 Space는 `Jump`다. 뱀서류 탑다운에서 점프는 쓰임이 적으니 **Space를 구르기로 바꾸고 점프를 빼거나 다른 키로 옮기는** 선택지도 진지하게 고려할 만하다. 점프를 유지한다면 구르기는 마우스 우클릭이 자연스럽다.

## 8. 검증 항목

구현 후 이 순서로 확인한다.

**스프린트**
1. Shift를 누르면 실제로 빨라지는가 — HUD의 `Speed` 표시로 확인 (`PlayerStatsUI.moveSpeedText`)
2. 제자리에서 Shift를 눌러도 달리기 모션이 나오지 않는가 (3-1)
3. **슬로우 상태에서 스프린트** → 슬로우가 풀린 뒤 스프린트가 여전히 동작하는가 (3-2 검증)
4. 스태미나를 넣었다면 — 스테이지를 넘어가도 값이 정상인가

**구르기**

5. 이동 입력 방향으로 구르는가, 입력 없으면 뒤로 구르는가 (4-3)
6. 구르는 중 마우스를 크게 돌려도 **방향이 유지**되는가 (회전 잠금)
7. **구르는 중 상체가 총을 겨누지 않는가** (4-4 ①)
8. **자폭 몹 폭발 순간에 구르기로 통과 시 피해가 0인가** (무적 검증)
9. 구르기 끝나고 0.1초 뒤에 맞으면 **피해를 받는가** (`rollIFrame < rollDuration` 검증)
10. 쿨다운 중 연타해도 두 번 구르지 않는가
11. **구르는 도중 사망** → 상체 레이어가 되살아나지 않는가 (4-4 ① 주의사항)
12. 낭떠러지에서 구르면 정상적으로 떨어지는가 (y 보존 검증)

**회귀**

13. 기존 이동·점프·자동공격이 그대로 동작하는가
14. 사망 후 추가 피격 시 `Die()`가 한 번만 도는가 (**C-1** 검증)

## 9. [04번 문서](04-이동확장설계.md)와의 관계

04번은 `PlayerMove`를 분해하고 `IMovementModule` 기반으로 재구성하는 **구조 설계**다. 이 문서는 **현재 `PlayerMove`에 직접 얹는 실전 구현**이다.

| | 04번 (모듈 방식) | 06번 (이 문서) |
|---|---|---|
| 초기 비용 | 높음 (구조 개편 선행) | 낮음 (바로 시작) |
| 3번째 이동기 추가 시 | 모듈 하나 추가 | `FixedUpdate` 분기 증가 |
| 대시·구르기·넉백 공존 | 깔끔 | 플래그가 늘어 지저분해짐 |

**이 문서대로 먼저 만들고, 이동기가 3개를 넘어가면 04번 구조로 옮기는 것을 권한다.** 이유:

- 구르기의 실제 값(거리·시간·커브)은 **직접 굴려보기 전엔 모른다.** 구조부터 잡으면 튜닝 사이클이 느려진다.
- 4-3의 `TickRoll` / `StartRoll` / `EndRoll`은 **거의 그대로 `RollModule.FixedTick` / `Enter` / `Exit`가 된다.** 나중에 옮길 때 버리는 코드가 거의 없다.
- 반대로 지금 구조 개편부터 시작하면, 눈에 보이는 결과가 나오기까지 오래 걸린다.

**옮겨야 할 신호**: `FixedUpdate` 최상단의 `if (isXxx) { ...; return; }` 분기가 **3개를 넘어가면** 04번으로 갈 때다.

## 10. 결정해야 할 것들 (체크리스트)

이 문서는 여러 곳에서 선택지를 열어뒀다. **무엇을 정해야 하는지**와 **언제까지 정해야 하는지**를 모아둔다.
괄호 안은 근거가 있는 원래 장·절 번호다.

### 10-1. 지금 정해야 한다 — 안 정하면 1단계가 막힌다

| # | 결정 | 선택지 | 권장 | 왜 지금인가 |
|---|---|---|---|---|
| **D1** | `Roll` 키 배치 | ① Space (점프 제거)<br>② Space (점프를 다른 키로)<br>③ 마우스 우클릭 (점프 유지) | **③** | `.inputactions`는 에디터를 열고 코드를 재생성하는 왕복 작업이라 **한 번에 끝내야 한다** (6장) |
| **D2** | 점프를 유지할지 | 유지 / 제거 | **유지** | D1과 한 몸. 지금 빼면 Animator 상태·접지 판정·`isJump` 처리까지 함께 건드려야 해 회귀 위험이 커진다 |

### 10-4. 값으로 정한다 — 플레이하며 맞추는 것

문서의 기본값은 **현재 `baseSpeed = 3` 기준으로 잡은 출발점**이지 정답이 아니다. 7장의 5단계(튜닝)에서 실제로 굴려보고 정한다.

| 값 | 기본값 | 조정 기준 |
|---|---|---|
| `sprintMultiplier` | 1.6 (3 → 4.8) | 크면 걷기가 무의미해지고, 작으면 누를 이유가 없어진다 |
| `rollDistance` | 4 | **적의 공격 범위를 벗어날 만큼**인지가 기준 |
| `rollDuration` | 0.45 | 길수록 커밋이 무거워진다. 0.3~0.5 사이 |
| `rollCooldown` | 1.2 | 아래 ⚠ 참조 |
| `rollIFrame` | 0.35 | `rollDuration`보다 **짧게** 유지 (D5) |
| `rollCurve` 끝값 | 0.2 | 0이면 구르기 종료 시 급정지한다 |
| `rollBufferTime` | 0.15 | D8을 넣기로 한 경우만 |

> **⚠ `rollCooldown`이 가장 중요하다.** 너무 짧으면 플레이어가 **구르기 연타로만 이동**하게 되어, 걷기·달리기를 만든 의미가 통째로 사라진다.
>
> 판정 기준: **구르기 연타 평균 속도 < 스프린트 속도**여야 한다.
>
> ```
> rollDistance / (rollDuration + rollCooldown)  <  baseSpeed × sprintMultiplier
> ```
>
> 기본값으로 계산하면 `4 / (0.45 + 1.2) = 2.4` vs `3 × 1.6 = 4.8` — 여유 있게 통과한다.
> 튜닝 중 `rollCooldown`을 줄이거나 `rollDistance`를 늘릴 때는 이 식을 다시 확인할 것.

### 부록. 권장안대로 갈 경우 (참고용)

전부 권장안을 따르면 1차 구현은 이렇게 확정된다.

- 입력: `Sprint` = LeftShift, `Roll` = 마우스 우클릭, **점프는 Space 그대로**
- 구르기: 지상에서만, 앞 0.35초 무적, 구르는 동안 **사격 정지 + 상체 레이어 off**
- 스태미나·입력 버퍼: **넣지 않음**
- 애니메이션: 구르기는 Mixamo, 달리기는 **재생속도 배수로 시작**
- 구조: 현재 `PlayerMove`에 직접 구현, 04번 이관은 보류

이 조합이면 7장의 **1~8단계**만 하면 되고, 9~11단계는 나중으로 미룰 수 있다.
